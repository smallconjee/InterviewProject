## 1. 系统规模数字

### 业务量
- 上线医院：**3 家**（1 家三甲约 1500 床 + 2 家二甲），另有 2 家试点中
- 日检查量：三甲日均 **~1200 例**（CT 500 / MR 120 / DR 400 / 其他 180），3 家合计 **~1800 例/日**
- 日导入 DICOM 对象（instance）：**~15 万个/日**，峰值 20 万（上午 9–11 点集中）（推导：CT 500 例×~250 张 + MR 120×~200 张 + DR 400×2 张 + 其他）
- 单对象大小：**平均 ~0.7MB**（CT 层图 512×512×2B≈0.5MB；MR 层图 ~0.13MB；DR 单张 30–50MB）
- 单次 CT 检查（整个 study）：**100–500MB**
- 日增量存储：**~120GB**（15 万 × 平均 0.7MB + DR 大文件）
- 在线存量：**~25TB**（系统 2025 年底上线至今约 7 个月增量）；更早的历史影像仍在医院旧 PACS，按需迁移，不在在线范围

### 接口与性能
- 导入接口：上游网关**逐对象推送**（单 DICOM 对象/请求），峰值 **~15 QPS**（=对象速率，上午集中），设计吞吐余量 50 对象/秒
- 导入同步链 **P99 < 300ms**（落盘 + 解析 + 两事务入库，不含备份）
- DICOM 解析与文件大小解耦（tag 升序 + 遇像素即停）：500MB 的 CT 元数据解析 **<5ms**

### 备份链
- 备份任务量 = 对象量：日均 15 万
- 单消费者吞吐 **~10 任务/秒**（单线程逐条：OSS 上传 0.7MB ~50ms + ACK/状态更新）；多消费者实例时 broker 轮询分发
- 高峰积压 **1–2 万任务**（上午集中导入的潮汐），**通常 1 小时内回落**，当日清零
- 告警规则：**积压 >2 万且持续 1 小时不回落**（区分"正常潮汐"和"异常积压"；事故复盘后从单看队列深度改成"深度+持续时间"双条件）

### RIS
- 报告量：3 家合计日增 **~1500 份**，存量 **~80 万份**（含从旧 RIS 迁移的历史报告——文本小、迁移易，和影像形成对比）
- 索引：**80 万文档、~35 万词项、内存 ~2GB、全量重建 ~12 分钟**（每日凌晨 2 点定时，双版本切换不停服务）
- 检索：峰值 **~20 QPS**（~200 个医生工作站、低频查询），走索引 **P99 < 80ms**，L1 命中 **~5ms**
- 两级缓存命中率合计 **~70%**（L1 ~30% + L2 ~40%）

### 部署
- 生产 **4 台虚机（4C8G）**：PACS 主服务 ×1（**兼 HTTP 入口，鉴权内嵌**，srpc 调认证服务）、备份消费者 ×1（可横向扩）、RIS ×1（可横向扩）、运维监控机 ×1（Zabbix + 日志收集）
- MySQL **单实例 + 每日全量备份（mysqldump）+ binlog 归档**（主从为演进项——医院内网峰值 ~15 QPS，单实例够用）；Redis 单实例（哨兵为演进口径）；RabbitMQ 单实例 + DLQ；医院内网机房，公司实施团队驻场部署
- 开发/测试环境各 1 套（Docker Compose 起 MySQL/Redis/RabbitMQ/Consul）

## 3. 一次可控的小事故（背熟，讲 90 秒）

- **现象**：某院夜间批量导入叠加 OSS 侧限流，早高峰消息积压冲到 3 万+ 且持续上涨，影像列表页变慢。
- **发现**：积压告警（深度+持续时间双条件，当时只看队列深度，阈值偏松）。
- **定位**：消费者日志大量 OSS 429 限流响应，单消费者吞吐掉到 ~3 任务/秒。
- **处理**：临时拉起第二个消费者进程分流（消费端独立进程 + 非独占消费，现成论据）；向 OSS 提工单临时提额。
- **复盘**：告警改成"积压 >2 万且持续 1 小时"双条件；消费者并发参数化；DLQ 纳入人工巡检。
- **讲法**：这个事故正好串起"为什么消费端独立部署、为什么消费要非独占（否则第二个实例 403 连不上）、为什么告警要看趋势不只是深度"。
