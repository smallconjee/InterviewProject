# 架构总览

> 全项目的"地图"：开发每做一小步，先回到这张图确认自己在哪、上下游是谁。
> 维护约定：架构发生实质变化（新增模块/链路）时同步更新本文件。

---

## 一句话系统观

- **PACS 归档系统（03_）**：同步链把 DICOM 文件的元数据在**毫秒级事务内**落库，重 IO 的 OSS 云备份扔给**异步消息链**慢慢做——核心命题是"请求快返回 + 备份不丢不重"。
- **RIS 检索系统（04_）**：离线把 XML 报告建成**不可变的倒排索引**，在线用 muduo 常驻服务接收 TLV 协议查询——核心命题是"索引可原子切换 + 查询可缓存可纠错"。
- **联动点**：RIS 报告里若含 StudyInstanceUID，可关联到 PACS 库里的 Study，实现"查报告 → 找到影像"。

## PACS 归档系统全景

### 同步导入链（请求线程内，毫秒级返回）

```
上游 PACS/DICOM 网关
      │
      │ POST /api/v1/images/import  (HTTP multipart, 带 JWT)
      ▼
┌─────────────────┐    srpc (Protobuf)    ┌──────────────────┐
│  wfrest 网关     │◀─────────────────────▶│  认证服务(srpc)   │──▶ Consul 注册/健康检查
│  (端口 8080)     │      ① 验签 + RBAC     └──────────────────┘
└───────┬─────────┘
        │ SeriesWork 串联以下步骤（本进程内）
        ▼
   ② 临时文件落盘   staging/ 目录（中断后可续传的抓手）
        ▼
   ③ DicomReader   手写轻量解析：提取 PatientID / Issuer /
        │           StudyInstanceUID / SeriesInstanceUID /
        │           SOPInstanceUID / SOPClassUID / Modality
        ▼
   ④ SHA-256       分块读取流式计算（RAII 管理文件句柄与 EVP_CTX）
        ▼
   ⑤ MySQL 单事务   四层表按 UID upsert（幂等键=SOPInstanceUID）
        │           + backup_event 本地消息表插入 ★与归档同事务★
        ▼
   ⑥ 返回 201      {task_id, status: ARCHIVED}（重复导入幂等返回，UID 冲突 409）
```

### 异步备份链（消费端，OSS 写入不阻塞请求线程）

```
   ⑤ 事务提交后
        │
        ▼ ⑦ Publisher 发布消息（publisher confirm 确认）
┌─────────────────┐
│  RabbitMQ        │  exchange: pacs.backup  queue: backup.queue
└───────┬─────────┘  DLX → dead-letter 备份死信队列
        ▼
┌─────────────────┐
│  BackupConsumer  │  ⑧ 手动 ACK + task_id 唯一约束去重（防重复消费）
│                 │     有界重试（指数退避，超限置 DEAD 终态；
└───────┬─────────┘      DLQ 只收毒消息——两条失败路径刻意分开）
        ▼ ⑨ OSS PutObject（aliyun-oss-cpp-sdk，凭据走环境变量）
┌─────────────────┐
│  阿里云 OSS      │
└─────────────────┘
        │
        ▼ ⑩ 更新 instance.backup_status = SUCCESS → 手动 ACK

  兜底：定时扫描本地消息表，补发"事务已提交但消息没发出去/没消费成功"的任务
```

### 为什么要这样拆（面试核心理由）

1. **OSS 上传放消费端**：远端对象存储写入耗时不可控（网络抖动、限流），放请求线程会把导入接口拖到秒级；放消费端后接口只做"落盘+解析+入库"，毫秒级返回。
2. **本地消息表与归档同事务**：解决"业务成功了但消息丢了"的第一个丢失窗口——事务提交意味着"业务+待发消息"原子落地，剩下的窗口交给 confirm + 定时扫描兜底。
3. **task_id 幂等**：RabbitMQ 只保证 at-least-once，重复投递必然发生，消费端必须靠唯一约束去重。

### 自测题（费曼关样本）

1. 为什么 OSS 写入不放请求线程？放的话最坏会发生什么？
2. 本地消息表为什么必须和归档状态在**同一个事务**？分开会怎样？
3. 消息从产生到消费成功，一共有几个"丢失窗口"？各靠什么机制堵住？
4. 同一个 SOPInstanceUID 导入两次，系统内每个环节分别发生什么？

## RIS 检索系统全景

### 离线链（独立子命令 `ris_report_search --build-index data/reports/`）

```
  报告 XML 文件集（上游 RIS/PACS 导出）
        │
        ▼ ① ReportParser (TinyXML2)
     提取患者/检查/设备/报告字段；字段缺失、格式异常、
     重复记录 → 坏记录进 bad-case 日志，不阻塞整批
        │
        ▼ ② 关联（可选）
     数据源提供 StudyInstanceUID 时 → 查 pacs_db.study 建立报告-影像关联
        │
        ▼ ③ cppjieba 分词 (Mix 模式) + 停用词过滤
        │
        ▼ ④ TF-IDF 权重计算并归一化
        │
        ▼ ⑤ 倒排索引构建（term → [(doc_id, weight)]）
     索引整体不可变；新版本构建完成后 shared_ptr 原子切换（双缓冲思想）
```

### 在线链（常驻服务，muduo 4 线程 Reactor，端口 9090）

```
客户端（RIS 工作站）
      │  TCP + TLV 帧 [Type 1B][Length 4B 网络字节序][Value]
      ▼
┌──────────────────┐
│  TLV 增量解码器   │  处理：半帧缓存 / 连续多帧 / 非法类型 /
│  (muduo 回调内)   │  超长帧拒绝——TCP 是字节流，没有"消息"边界
└───────┬──────────┘
        ▼ 查询词
┌──────────────────┐
│  BK-tree 纠错    │  从领域词典召回编辑距离 ≤N 的候选，
│  (可选触发)       │  优先队列选 Top-K 建议词
└───────┬──────────┘
        ▼
┌──────────────────┐
│  检索执行器       │  查询分词 → 倒排召回 → 余弦相似度 TopK
│                  │  → 命中位置生成上下文摘要
└───────┬──────────┘
        ▼
┌──────────────────┐
│  二级缓存         │  ①进程内线程安全 LRU（mutex+list+unordered_map）
│                  │  ②Redis 跨进程缓存；缓存键含索引版本号，
│                  │  索引切换自动读新版本，旧版本靠 TTL 回收
└───────┬──────────┘
        ▼
   TLV 响应帧（TopK 结果 / 纠错建议）
```

### 为什么要这样拆（面试核心理由）

1. **索引不可变 + 版本切换**：读路径永远面对完整一致的索引快照，构建新索引不阻塞查询；切换是 O(1) 的 shared_ptr 原子替换。
2. **TLV 自定义协议**：报告检索是长连接低频请求场景，自定义二进制协议比 HTTP 轻；Length 字段用网络字节序解决跨平台字节序问题。
3. **缓存键带版本号**：索引切换后旧缓存键天然不命中，避免"新索引查出旧结果"的一致性 bug，旧版本交给 TTL 自然回收。

### 自测题（费曼关样本）

1. 为什么倒排索引做成不可变的？重建期间查询怎么办？
