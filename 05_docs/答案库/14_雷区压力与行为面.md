## §16.5 💣 上线后出过什么线上事故？（绝不答"没有"）

**逐字口径稿**（90 秒，背熟）：出过一次可控的。现象：某院夜间批量导入叠加 OSS 侧限流，早高峰消息积压冲到 3 万多还在涨，影像列表页变慢。发现靠积压告警——但当时只看队列深度、阈值偏松。定位看消费者日志：大量 OSS 429 限流响应，单消费者吞吐从每秒约 10 个任务掉到约 3 个。处理两步：临时拉起第二个消费者进程分流——这里有个前提，消费端是非独占消费，不然第二个实例 403 根本连不上；同时向 OSS 提工单临时提额。积压当天消化完。复盘改了三件事：告警从单看队列深度改成"积压超 2 万且持续 1 小时不回落"的双条件，区分正常潮汐和异常积压；消费者并发参数化；DLQ 纳入人工巡检。这个事故正好串起三个设计：为什么消费端要独立部署、为什么消费要非独占、为什么告警要看趋势不只是深度。

**追问预演**：
- ↳ 为什么夜间导入早高峰才炸？——上午 9 到 11 点本来就是集中导入的潮汐高峰，夜间积压叠加上午洪峰，队列深度才冲出正常区间。
- ↳ 高峰积压多少算正常？——1 到 2 万，通常 1 小时内回落、当日清零——这正是告警必须加持续时间条件的原因，单看深度天天误报。
- ↳ 影像列表页变慢和积压什么关系？——列表页要查备份状态，消息和状态堆积拖慢了状态查询——现象到根因的链路要能讲通。

**雷点**：答"没出过事"（不可信）或编一个大事故（细节接不住）；三个数字（3 万多 / 10 掉到 3 / 双条件 2 万+1 小时）一个都不能变。

## §16.6 💣 "避免远端写入阻塞请求线程"——wfrest 本身全异步，这句是不是有问题？

**逐字口径稿**：这句表述我认账——"阻塞"确实只是最直白的入门说法，真实动机有三个。第一，**解耦**：OSS 的速率和故障特征跟导入完全不同，限流、网络抖动是常态，放进同一条请求链路，远端的毛刺全变成导入接口的毛刺。第二，**削峰**：上午 9 到 11 点集中导入，高峰 1 到 2 万的积压、1 小时内回落，本来就是消息链设计内的潮汐，消费者按自己的节奏消化。第三，**失败隔离加可靠性语义**：重试、指数退避、死信这套在消费端是现成的，放请求链路就得自己造。至于 wfrest 全异步——对，它不阻塞线程，但挂起等待的任务占着内存和连接，而且同步链 P99 300 毫秒的预算，不应该花在耗时不可控的远端写入上；独立消费者进程还能单独扩缩容，这是后来事故分流时真用上的能力。

**追问预演**：
- ↳ 那为什么不直接用异步任务上传、非要过 MQ？——异步任务还在同一进程里：扩缩容绑定、重启互相影响、没有削峰缓冲和重试死信语义；独立消费者进程加 MQ 四样全有。
- ↳ 削峰的代价是什么？——延迟和积压：备份从"同步完成"变"最终一致"，当日清零；用双条件告警盯着，业务可接受。
- ↳ 如果面试官继续挑"阻塞"字眼？——直接说：简历那句是"为什么不能放请求线程"的最短解释，展开就是我这三条——不纠缠字眼，展示层次。

**雷点**：被挑刺后慌了改口"其实也能放请求线程"——前功尽弃；正确姿势是认下表述直白、立刻给三层真实动机。

## §16.7 💣 技能栏写"熟练使用 Codex / Claude Code 等 AI 工具"——用它们做了什么？这个项目是不是 AI 写的？

**逐字口径稿**：我的用法基本三类：读第三方库源码先让它讲结构和调用关系、生成测试数据和脚本、解释编译报错和排障思路。架构设计和核心代码我自己写，AI 的产出一律 review 之后才会用。对我来说它是个随叫随到的初级同事——用好它的前提是我自己能看懂、能兜底。所以这个项目不是 AI 写的：事务边界、消息可靠性这些核心设计是我和组里定的，AI 帮我省的是查文档、造测试数据的时间，不是替我做工程判断。

**追问预演**：

**雷点**：全认（"很多模块是 AI 写的"——技术深挖立刻穿帮）或全否（与技能栏"熟练使用"自相矛盾）；红线是不主动提"AI 生成代码"话题——被问到才按三句话答，答完就停。

## §16.11 💣 反问环节你问什么？

**逐字口径稿**：我一般问三个。第一，团队现在主要负责什么业务、这个岗位进去是补哪个位置——判断和我现在的积累匹不匹配。第二，团队的技术栈和开发流程，比如有没有 code review 文化、迭代节奏什么样——我在现在组里受益最大的就是 MR review，很在意下家有没有这个机制。第三，新人成长机制，有没有 mentor 或者轮岗机会。薪资和加班这类我留到 HR 面，反问环节不问。

**追问预演**：
- ↳ 面试官反问"你有什么缺点"？——备一个真实且可改进的：比如"容易在细节上抠太久，现在学着先定优先级、给深挖设时间盒"——不要说"追求完美"这种伪缺点。
- ↳ 什么都不问行不行？——不行，反问是最后的加分位；实在没有就用第三个问题兜底。
- ↳ 能不能问技术债？——能，换个说法："团队目前最大的技术挑战是什么"——既显格局也能听出真实状态。

**雷点**：问薪资加班假期（显得只关心待遇）；说"没什么想问的"（显得没兴趣）；问题过于宏大（"公司五年战略"）显得空。

# 第二部分：§17 行为面与软性问题

## §17.1 🟡 最有挑战的技术难题（四选一背熟，按面试官口味切换）

> 四个故事全部出自弹药库踩坑实录，每个 60–90 秒，结构：现象 → 定位 → 修复 → 一句话复盘。默认讲故事一（最有"生产味"）；面试官偏底层/运维讲故事二；偏文本处理/缓存讲故事三；偏编译/跨平台讲故事四。

### 故事一：mysql_insert_id 在 COMMIT 后返回 0（默认）

**口语答案**：现象：导入链联调时，一部分实例卡在 PARSED 状态，本地消息表插不进去，日志报外键错误 instance_fk=0。定位：顺着日志反查调用时序——我在事务一里 INSERT 实例之后，先发了 COMMIT 再调 mysql_insert_id 取 id；而 insert_id 绑定的是"本连接最后一条语句"，COMMIT 之后它返回 0，事务二就拿 0 去插消息表，被外键拒绝。修复只有一行顺序调整：INSERT 后立即取 id 再 COMMIT。一句话复盘：这个 bug 让我吃透了 MySQL C API 的会话语义；更值钱的是状态机兜住了我自己埋的 bug——卡在 PARSED 的实例第二次导入时靠续传分支自动收尾、没产生脏数据，幂等设计反过来兜住了写代码的人。

**追问预演**：怎么发现的（联调日志外键错误 + 状态不符，顺着 instance_fk=0 反查时序）/ 为什么测试没拦住（只在特定语句顺序下触发，正常路径都过）/ 之后怎么防（对账检查加进巡检 SQL）。

### 故事二：排他消费僵尸进程

**口语答案**：现象：做消费者重启演练，kill 掉进程后新实例起不来，日志 403 ACCESS_REFUSED。定位：新进程被拒说明队列上还挂着消费者——老进程没死透。回代码看：SimpleAmqpClient 2.5.1 的 BasicConsumeMessage 是无限阻塞的、没有超时重载，SIGTERM 到了只是设了个软退出标志，主线程卡在等消息里永远轮不到检查它，进程变僵尸；连接没断、排他消费者还占着队列，新实例注册就被 broker 拒绝。修复看起来糙但正确：信号处理器里直接 _exit——用 async-signal-safe 的 write 打一行日志就退。一句话复盘：**幂等设计反过来简化了关闭语义**——敢这么粗暴退出，正因为未 ack 的消息 broker 会重投、重复被幂等吸收。

**追问预演**：信号处理器里为什么不能走正常退出路径（printf/锁都非 async-signal-safe，且主线程阻塞中）/ 这个坑和"非独占消费"什么关系（同源：排他消费既挡分流实例又放大僵尸的影响）/ 怎么验证的（杀进程重演，新实例正常接入）。

### 故事三：UTF-8 截断两连击

**口语答案**：现象：检索结果的摘要偶发乱码，前端 JSON 解析直接失败。定位：摘要按命中位置截取上下文，截断按字节算——UTF-8 一个汉字 3 字节，从中间切开就是非法字节序列。坑在"两连击"：term 命中路径一处截断、term 未命中路径的 substr(0,48) 又一处；修完第一处测试仍偶发，差点误判方向。修复是写一个码点边界对齐函数——向前向后跳过 10 开头的续字节——两处都换掉。还有个尾巴：修完后坏结果还在 Redis 里躺着，缓存 TTL 300 秒，FLUSHALL 才看到修复生效。一句话复盘：多字节文本的一切字节操作都要过"码点对齐"这道检查；以及"改了代码没生效，先想缓存"。同一周我还在编辑距离上踩了同款坑——中文按字节算一字距离 3，纠错整个失效，同一个教训吃了两遍才长记性。

**追问预演**：为什么 JSON 会解析失败（非法 UTF-8 字节序列）/ 缓存为什么没跟着修好（键没变、值还是旧的，TTL 300 秒内继续命中）/ 编辑距离那个怎么修的（utfcpp 切码点后按码点算，"肺节结"到"肺结节"距离恢复为 2）。

### 故事四：ARM64 上编 muduo 的 long double

**口语答案**：现象：在 ARM64 容器里源码编译 muduo，static_assert 直接编译失败，断言是数字缓冲区长度必须大于 long double 能表示的十进制位数。定位：读报错——x86-64 的 long double 是 80 位、digits10 是 18；aarch64 的 long double 是 128 位、digits10 约 33，muduo 预设的 32 字节缓冲区在 ARM 上不够。这不是代码 bug，是平台 ABI 差异。修复走最小补丁：kMaxNumericSize 从 32 调到 48，用 sed 打进安装脚本，以后每次安装自动带上。一句话复盘：跨平台编译错误的正解是读报错、查 ABI 根因、做最小修复，而不是绕开断言硬编——顺带记住 long double 的位数是平台相关的，不能想当然。

**追问预演**：为什么 x86 上从来没炸过（80 位 long double，digits10=18，32 够用）/ 为什么改缓冲区而不是换类型（不动上游逻辑、影响面最小）/ sed 进安装脚本的意义（补丁可重放，环境重建不丢）。

## §17.2 🟡 和同事技术意见分歧怎么解决的？

**口语答案**：讲一个真实的：连接池用同步 MySQL 客户端还是 workflow 自带的异步客户端。有同事主张异步——workflow 生态内、彻底不阻塞 worker 线程；我主张同步池，理由三条：异步客户端的结果集解析是回调式的，复杂度高一截；按我们的量——峰值约 15 QPS、设计余量 50 对象/秒——同步池加"IO 线程数略大于核数"完全够用；同步池还是脱离 workflow 可移植的通用组件。收敛方式是拿数据说话：算吞吐余量、写小 demo 对比两边的代码复杂度，最后组长拍板用同步池，同时把"高并发时演进到异步客户端"的路径写进了代码注释——分歧的结论变成了代码里的文档。我的原则：分歧对事不对人，用数据和原型收敛，最终决策交给 review 机制，定了就全力执行。

**追问预演**：
- ↳ 后来证明谁对了吗？——目前量级下同步池没成为瓶颈，验证了当时的判断；但如果吞吐真涨几十倍，注释里的演进路径就是答案——不争一时对错，留好升级的路。
- ↳ 有没有你输的时候？——有，联动查询走直查库而不是接口就是组里的决定，我当时提过跨服务耦合的顾虑——保留意见、执行决议，后来把"演进成 exists 接口"写进了技术债清单。
- ↳ 和测试有分歧怎么处理？——缺陷优先对事：先复现、给日志和最小用例，不争责任归属。

**雷点**：编一个"我说服了所有人"的完胜故事（一年经验的真实分歧应该是小的、机制化的）；说"从没分歧"（要么没干活要么不诚实）。

## §17.3 🟡 你的学习方法是什么？

**口语答案**：三件套。第一，**小步开发**：一步只做一件事、每步产物可验证，出问题 diff 一眼定位——我的项目全程这么推进，节奏本身就是方法。第二，**费曼自测**：每完成一个模块，把设计取舍脱稿讲一遍，讲不顺的地方就是没懂的地方——组里的模块文档就是这么写的，讲稿沉淀下来直接是复习材料。第三，**读原文优先**：DICOM 的 tag 对着原始标准核对——我抓过建表注释里 tag 写错的坑；第三方库的行为读源码确认——比如 SimpleAmqpClient 没暴露 confirm API、BasicConsumeMessage 没有超时重载，都是读源码发现的。现在再加一条：AI 当效率工具，读陌生源码前先让它讲结构，但我必须自己看得懂、能兜底。

**追问预演**：
- ↳ 最近在学什么？——把项目里用过的中间件从"会用"补到"懂原理"：MySQL 的索引和 MVCC、Redis 持久化、RabbitMQ 的确认机制——边补边和项目里的用法互相印证。
- ↳ 怎么检验学会了？——费曼自测加自建题库：能脱稿讲、能预判追问，才算过。
- ↳ 有输出习惯吗？——模块文档和技术笔记一直在写，工作产物本身就是输出。

**雷点**：说"看视频教程/跟着做项目"这类被动学习；方法里全是输入没有验证机制。

## §17.4 🟡 职业规划三年？

**口语答案**：第一年把深度补上：把项目里用过的中间件——MySQL、Redis、RabbitMQ——从"会用"练到"懂原理"，索引、复制、持久化这些底层机制我正在系统过，这是当下最明确的缺口。第二三年希望能独立负责一个核心子系统，从方案设计、开发到上线运维完整闭环，再往后带一两个新人做技术传承。方向上我想深耕分布式存储和消息中间件这一侧——归档和备份这条链让我对这个方向最有手感，存储和可靠性也是通用后端的硬通货，换场景不贬值。

**追问预演**：
- ↳ 为什么不转管理？——三年内技术深度优先，管理是能力自然延伸出来的，不是规划出来的。
- ↳ 和这个岗位怎么衔接？——岗位的后端方向正是我积累的延续，第一年补深度的目标在岗内就能完成。
- ↳ 五年呢？——成为某个基础方向上"问题到我为止"的那个人，其余不预设太多。

**雷点**：说"三年当架构师/带团队"（好高骛远）；规划和技术积累完全脱钩（显得只是想要 title）。

## §17.5 🟡 为什么坚持 C++ 不转 Go/Java？

**口语答案**：两个原因，一个是能力匹配，一个是资产理性。能力匹配：我做的是存储和检索——2GB 常驻内存的索引、百纳秒级的缓存命中、毫秒级的入库事务链路，这些对内存布局和延迟敏感的场景是 C++ 的主场，我在这里的积累最深、继续深耕边际收益最大。资产理性：C++ 在基础设施领域——数据库、存储引擎、网络框架——短期内不可替代，壁垒高。但我不教条：业务 CRUD 用 Go、Java 写效率就是更高，这是真实的工具理性；我的定位是性能敏感路径和基础软件这条线，所以坚持 C++。

**追问预演**：
- ↳ Rust 呢？——方向上认同，内存安全不牺牲性能；但生态位还集中在新建系统，我的存量技能在 C++ 上变现更快，Rust 保持关注。
- ↳ C++ 的坑你怎么防？——RAII 和智能指针管资源、开告警和静态检查、Valgrind/ASan 排查——项目里就是这么实践的。
- ↳ 让你写 Go 你抵触吗？——不抵触，语言是工具；有 C++ 底子转 Go 主要是学生态和惯例，成本可控。

**雷点**：贬低 Go/Java 抬 C++（显得视野窄）；答不出"我为什么适合 C++"（只说语言好没用，要说自己的积累在哪）。

## §17.6 🟡 期望薪资 / 还面了哪些 / 我们排第几意愿？

**口语答案框架**（个人数据需提前填好，不能临场编）：①薪资——报区间不报单点，锚定"1 年 C++ + 完整上线项目经验"的市场位：'我目前薪资是 X，期望在 Y 到 Z 这个区间，具体看重整体 package。'②还面了哪些——说方向不报名单：'同方向的后端岗都有在看，也有在流程中的'，绝不点评其他公司。③排第几——不给名次给匹配度：'技术栈和业务方向对口是我最看重的，贵司这个岗位和我积累的匹配度很高。'三条底线：不在技术面主动谈钱；不拿 offer 压价或抬价；不表现出"哪里都行"。

**追问预演**：
- ↳ 为什么值这个数？——用产出说话：完整负责过一条上线的核心链路（归档加消息可靠性），不是只做过模块修补。
- ↳ 现在公司涨薪挽留怎么办？——'感谢认可，但我的决定基于技术成长方向，不是薪资情绪'——不贬前司、不留谈判破绽。
- ↳ 手上有 offer 会被问细节？——只说状态（流程中/终面），不报公司名和数字——保密是职业素养的展示位。

**雷点**：技术面主动问薪资加班（时机错位）；报精确单点数字（没有回旋）；说"你们是我唯一选择"（贬值）或"我还有很多选择"（施压）。
