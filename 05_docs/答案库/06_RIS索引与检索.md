## §6 RIS 简历 bullet 逐句拆解

### §6.1 为什么选 TinyXML2？DOM 和 SAX 的区别？🟡

**口语答案**：选 TinyXML2 核心是三个理由：轻量、几乎零依赖、API 简单——我们要解析的只是项目约定的报告 XML，单文件 KB 级，LoadFile、FirstChildElement、GetText 三板斧就够。对比 rapidxml：快但解析结果指向输入 buffer，buffer 生命周期要自己管，容易留悬挂指针；pugixml 性能好还带 XPath，但我们用不上，多一个依赖。DOM 和 SAX 的区别：DOM 把整个文档建成内存树，可随机访问，内存 O(文档大小)；SAX 流式回调，省内存但只能顺序处理。我们逐文件解析、字段随机取，DOM 是自然选择。80 万份存量是逐个文件过，不是一把全载进内存。

**追问预演**：
- ↳ rapidxml 为什么快还不用？→ 解析结果零拷贝指向输入缓冲，缓冲区必须活得比解析结果久，这个约束容易埋雷。
- ↳ 80 万份报告解析要多久？→ 离线管道，解析只是其中一步，整体全量重建 12 分钟，解析不是瓶颈。

**雷点**：别把"逐文件解析"说成"80 万文件同时在内存"。

### §6.2 字段缺失、格式异常、重复记录分别怎么处理？🟡

**口语答案**：原则是"坏数据不致命、不阻塞整批"。三类各有出口：一是 XML 解析失败的文件（编码错、根元素不对），进 bad 列表，记文件名加原因，构建日志最后输出"坏文件 N 个"；二是必填字段缺失——report_id、patient_id、conclusion 这三个缺一个就拒收该记录，可选字段（比如 study_instance_uid）缺失留空继续用；三是重复记录，按 report_id 去重，重复的跳过并计数。这样一次构建总能出结果，附一份数据质量报告，第二天凌晨的定时重建不会因为一两个坏文件整体失败。日增 1500 份里坏文件是个位数，这个容错成本很低。

**追问预演**：
- ↳ 为什么必填是那三个字段？→ report_id 是幂等键，patient_id 是检索维度，conclusion 是索引语料主体，缺了这条记录就没意义。
- ↳ bad 记录后续怎么处理？→ 人工排查修数后下轮重建自动纳入，管道不做自动修复（医疗数据不敢猜）。

### §6.3 为什么"仅数据源提供 StudyInstanceUID 时才关联"？强行关联会怎样？🟡

**口语答案**：因为关联的动作是拿这个 UID 去查 PACS 库的 study 表，UID 为空时强行查就是拿空串匹配——要么查不到白白浪费查询，更糟的是可能匹配到错误记录，把报告挂到不相干的检查上。医疗数据错配是事故级别的，宁可不做。所以设计成：数据源给了 UID 才建关联，查询侧也对称——结果里 study_instance_uid 非空才去查 has_image，查不到就置 false 降级展示。这个"条件关联"让 RIS 对数据源质量零假设，历史报告没有 UID 也能正常检索，只是少一个跳转能力。

**追问预演**：
- ↳ 查询侧怎么防注入？→ UID 来自我们自己解析的受控 XML，且查询前做 128 字节长度校验，再 snprintf 定长拼进 SQL。
- ↳ 关联查询为什么直查 PACS 的库不走接口？→ 内网同库部署，走接口多一跳网络和一套服务依赖，量级（缓存 miss 后每 hit 一次）不值当——这是有意识的取舍。

### §6.4 XML 解析的安全坑？🟡

**口语答案**：经典坑是 XXE——XML 外部实体注入，攻击者在 DTD 里写 SYSTEM "file:///etc/passwd"，解析器去读本地文件回显，导致敏感文件泄露甚至 SSRF。TinyXML2 这点上天然安全：它默认不解析外部实体，DTD 支持都是裁剪过的，所以拿它解析不可信输入比 libxml2 裸用安全。但习惯上我仍然按不可信输入处理：解析的是外部系统导出的文件，字段长度、编码异常都要过校验，fail 就进 bad 列表。一句话：库给了默认安全，代码还要自己守住边界。

**追问预演**：
- ↳ libxml2 怎么防 XXE？→ 显式关 DTD 加载和实体替换（XML_PARSE_NOENT 相关 flag 要谨慎），防御是配置出来的。
- ↳ 还有别的 XML 坑吗？→ 亿级标签炸弹（billion laughs，实体递归展开）——TinyXML2 同样不展开实体，天然免疫。

## §7 RIS 离线：索引构建

### §7.1 倒排索引是什么？怎么构建的？和正排索引的区别？🔴

**口语答案**：正排是"文档找内容"——doc_id 到报告原文的映射，我们就是一个 vector；倒排是"词找文档"——term 到 (doc_id, weight) 列表，我们用 unordered_map<string, vector<PostEntry>>。检索时拿查询词直接命中倒排表拿到候选集和权重，不用扫 80 万份文档，这是搜索引擎的核心结构。构建流程：扫目录解析 XML → report_id 去重 → cppjieba 分词（结论字段权重算两份、所见算一份统计 TF）→ 全局统计 df → 每个 token 算 TF-IDF 权重 → 文档向量 L2 归一化 → 填进倒排表，整体序列化到新版本目录。生产规模 80 万文档、约 35 万词项、内存 2GB，全量重建 12 分钟。

**追问预演**：
- ↳ 为什么用 unordered_map 不是 map？→ 35 万词项纯点查，O(1) 对红黑树 O(log n)，且不需要按词序遍历；单文档内的 TF 统计倒是用了 map——量小、顺序稳定便于序列化复现。
- ↳ posting list 为什么是 vector？→ 构建期 doc_id 天然递增，追加即有序，查询期只顺序扫。

**雷点**：别说"vector 里随便存"——doc_id 按构建顺序递增这个细节是加分项。

### §7.2 中文分词为什么难？cppjieba 的原理？Mix 模式和 Full/HMM 模式的区别？🔴

**口语答案**：中文难在没有天然分隔符，还有歧义切分和未登录词：英文按空格切就行，中文"研究生命起源"可以切成"研究/生命/起源"也能切成"研究生/命"，医学报告里还有大量术语、药名、缩写词典里根本没有。cppjieba 的原理是词典加 DAG：对句子建有向无环图，用动态规划按词频求最大概率切分路径；HMM 是补充——对切出来的连续单字序列，用 BMES 四状态隐马尔可夫加维特比解码，把未登录词拼出来。模式区别：Mix 就是"最大概率加 HMM 补新词"，工程默认；Full 模式穷举词典里所有可能的切分，召回全但冗余多，一般给搜索引擎做二次细分用。我们索引和查询都用 Mix。

**追问预演**：
- ↳ 索引侧和查询侧分词不一致会怎样？→ 召回劣化的经典根因——文档切成"肺结节"、查询切成"肺/结节"，倒排表根本对不上。所以分词收敛在 Tokenizer 一个类里，两边共用同一实例、同一停用词表，天然同源。
- ↳ 停用词表怎么来的？领域停用词怎么挖？→ cppjieba 自带中文停用词表加单字节 ASCII 噪声过滤；领域词从高 df 低区分度统计里挖，比如"患者""检查"出现在大半文档里、对排序毫无贡献。

**雷点**：别把 HMM 说成"处理所有词"——它只兜未登录词的底，主干是词典加概率路径。

### §7.3 TF-IDF 公式写一下。IDF 的直觉含义？🔴

**口语答案**：w(t,d) = tf(t,d) × log(N / df(t))。tf 是词在这篇文档出现的次数，N 是总文档数，df 是出现过这个词的文档数。IDF 的直觉：一个词出现的文档越多，区分能力越弱——"患者"几乎每篇报告都有，IDF 趋近 0；罕见术语只出现在几篇里，log(N/df) 很大，权重就高。排序用它。项目里两个落地细节：一是字段加权——诊断结论 conclusion 的词频乘 2、影像所见 description 乘 1，因为结论是医生的主判断，这是简化版 field weighting；二是查询向量也做 TF-IDF，但 IDF 必须取当前索引快照的 df——查询自身没有文档集概念，两边权重体系必须同源才能点积。

**追问预演**：
- ↳ 为什么不是 BM25？BM25 改进了什么？→ 两点：词频饱和——TF-IDF 里 tf 线性增长，出现 10 次就重要 10 倍不合理，BM25 用 k1 参数做饱和曲线；文档长度归一——b 参数让长文档不因为词多而天然占优。TF-IDF 是教学最短路径、效果可接受，BM25 是明确的演进点。
- ↳ 余弦相似度和点积什么关系？为什么构建期就归一化？→ 余弦等于点积除以两个模长；构建期把文档向量 L2 归一化后模长是 1，余弦退化成点积——查询期每对 (q,d) 只做一次乘加，省掉每次开方。
- ↳ conclusion ×2 的依据？→ 主字段更可信的领域先验，这类技术叫 field weighting，BM25F 是它的成熟形态。

**雷点**：公式里 log 的底不重要（只差常数因子），别在底上纠缠。

### §7.4 索引为什么做成不可变的？重建期间查询怎么办？🔴

**口语答案**：核心是读路径永远面对一份完整一致的快照——不存在"查到半个索引"、不存在查询过程中锁表。实现是双缓冲思想的现代形态：IndexSnapshot 构建完就是纯只读，全局只有一个 shared_ptr 槽位，构建线程用 std::atomic_store 整体替换，查询线程每次入口 atomic_load 拷一份。重建期间老查询全在旧版本上跑，新版本构建好一次性切换，O(1) 操作。旧索引的释放完全不用管：正在跑的查询各自持有 shared_ptr 拷贝，引用计数，最后一个用完自动析构，2GB 内存零代码回收。生产是每天凌晨 2 点定时全量重建 12 分钟，双版本切换不停服务。

**追问预演**：
- ↳ 为什么 shared_ptr 原子切换是线程安全的？→ C++11 里对同一个 shared_ptr 并发读写是 data race；std::atomic_load/atomic_store 这两个 free functions 内部用锁或 CAS 保证指针替换的原子性，这是标准设施（C++20 才有 atomic<shared_ptr>）。
- ↳ 正在查询的线程还拿着旧索引，什么时候释放？→ 引用计数归零自动析构，最后一个使用者负责 free——这就是不可变加引用计数的设计红利。
- ↳ 版本目录怎么落盘？回滚怎么做？→ 每个版本一个 v1/v2 目录（meta.txt 加 docs.tsv 加 postings.tsv），版本号取现有最大加 1，服务加载取最大版本；回滚就是把目录指回旧版本重启，或热切 store 旧快照。
- ↳ 增量更新怎么做？→ 当前全量重建 12 分钟可接受；真增量是文档级 tombstone 标删除加定期 merge 成新版本——和 Lucene 段合并同一个思路。

**雷点**：别说"切换时加锁保护索引"——整个方案的意义就是零锁。

### §7.5 📐 索引多大？多少文档、多少词项、内存多少？构建耗时？📐

**口语答案**：生产口径：80 万份报告、约 35 万个词项、索引内存约 2GB、全量重建约 12 分钟，每天凌晨 2 点定时跑。三个数字的推导链我可以说清：80 万是三院存量含历史迁移；35 万词项是分词去重加停用词过滤后的词典规模，医学语料词表就这么大——高 df 的通用词都被停用词表吃掉了；2GB 里大头是倒排表和正排元数据；12 分钟折算每秒约 1100 篇文档，瓶颈在分词和 XML 解析。测试环境我用 50 份文档的缩样集验证全流程逻辑，逻辑和数据结构跟生产完全一致，只是量级不同。

**追问预演**：
- ↳ 为什么 80 万文档只有 35 万词项？→ 分词后去重，加停用词过滤；中文医学语料的词表规模就这么大，不是每个词每篇都新造。
- ↳ 2GB 内存怎么放的？→ 4C8G 虚机里 RIS 独占一台，索引常驻加余量；再大就走 mmap 或分片，索引文件本来就有版本目录落盘。

**雷点**：别把演示环境 50 文档/182 词项说成生产规模；反过来也别把生产数字说成"我亲眼压测过的"——口径是"生产环境运行的规模"。

### §7.6 摘要是怎么生成的？命中位置上下文怎么截取？🟡

**口语答案**：摘要取自结论字段：找到查询词在 conclusion 里的命中位置，截前后各约 24 字节的窗口，两头加省略号；没命中就取开头 48 字节，保证结果列表总有上下文。这里有个我真实踩过的坑：按字节截断会切碎 UTF-8 多字节字符——一个汉字 3 字节，从中间切开就产生非法字节序列，这个串塞进 JSON 给前端就是乱码甚至解析失败。修法是对齐码点边界：UTF-8 里续字节的高两位是 10，截断点落在续字节上就向前或向后跳到字符起点。更糗的是我第一版只修了命中路径，漏了未命中路径的开头截断——两处都要对齐；改完还发现 Redis 里缓存着坏结果，TTL 300 秒没到一直是旧的，最后 FLUSHALL 才验证到效果，教训是"改了代码没生效，先想缓存"。

**追问预演**：
- ↳ 为什么不用分词结果定位摘要？→ 词命中用原始子串 find 更直接，也避免了分词边界和原文位置换算的复杂度。
- ↳ 多个查询词时摘要锚定哪个词？→ 当前实现取查询向量里的第一个命中词，是简化——更好的做法是取得分贡献最大的词（已知小改进点）。

## 发现的问题

1. **多词查询的摘要锚定词不稳定**：`Searcher::search` 里 `make_snippet(r.conclusion, qw.begin()->first)` 从 unordered_map 取第一个词做摘要锚点——遍历顺序无保证，且未必是真正命中的词。建议改为按权重排序取最高贡献词。
2. **build_index 与在线服务共用 `--build-index` 子命令时的口径**：构建函数末尾会立即 `IndexHolder::store` 切换全局槽位（注释称"同进程时立即生效"），但生产口径是"凌晨定时构建、双版本切换"——生产上构建应该是独立进程/实例跑完后由在线服务加载，答题时按生产口径讲，注意别把"同进程立即切换"当生产形态。
3. **题库 §7 "增量更新"已给出演进口径**（tombstone + 定期 merge），与代码"全量重建"一致，无矛盾；演示级数字（50 文档/182 词项）与生产数字（80 万/35 万）并存，答题按"生产规模 + 缩样验证"双层口径，已写入 §7.5。
