# §2 PACS 简历 bullet 逐句拆解

## bullet 1：wfrest 接口 + SeriesWork 串联 + OSS 异步

### 🔴 为什么 OSS 写入不能放请求线程？放进去最坏发生什么？

**口语答案**：远端对象存储的写入耗时不可控——网络抖动、OSS 限流的时候一次上传就是秒级。放请求线程，导入接口的延迟就跟着 OSS 的状态抖，最坏把上游网关的连接和超时全拖垮，我们日均 15 万个对象的导入洪峰会直接撞在 OSS 的限流上。放消费端之后，同步链只剩落盘、解析、两个短事务，P99 稳在 300ms 以内；OSS 慢只体现为备份积压，有队列深度和消息表堆积监控兜底。生产真出过 OSS 限流把消费吞吐拖到约每秒 3 个任务的事，但导入接口完全无感。

**追问预演**：
- 💣 挑刺版："wfrest 本身全异步，放请求线程也阻塞不了啊？"——对，"阻塞请求线程"只是最直白的入门说法；真实动机是三条：解耦（备份失败不影响导入成功）、削峰（洪峰先进队列慢慢消费）、失败隔离（OSS 故障被隔离在消费端，不传染主链路）。就算框架能异步调，这个拆分决策也成立。
- 备份多久算异常？——积压超 2 万且持续 1 小时告警（深度加持续时间双条件），高峰正常积压 1 到 2 万、当日清零。
- 为什么不本地双写盘了事？——医院要异地容灾，OSS 是第二份数据，职责不同。

**雷点**：被"wfrest 全异步"一怼就改口"对对对我说错了"——挑刺版必须接得住，把动机从"阻塞"升级到"解耦+削峰+隔离"。

### 🔴 SeriesWork 是什么？你串了哪几步？某一步失败后面还执行吗？

**口语答案**：SeriesWork 是 workflow 里的任务串概念——把多个任务挂进同一个 series 顺序执行、共享上下文和生命周期，回调链不用层层嵌套。项目里我用它做 RIS 桥接：handler 的第三个参数拿到当前 HTTP 任务的 series，把 TLV 客户端任务 push 进去，HTTP 响应推迟到 TLV 回调里写——收 HTTP、发 TLV、收 TLV、回 HTTP 全程不占 handler 线程。导入这条链的落盘、哈希校验、元数据事务、备份事件创建，是在同一个请求处理函数里按序编排的 pipeline：任何一步失败立即短路返回、清理 staging 临时文件，后面的步骤不会执行。

**追问预演**：
- ↳ Task/Series 模型和"回调地狱"比好在哪？——series 保证顺序和生命周期统一管理，串联的回调天然有序，最后还能挂一个收尾回调做统一清理；纯嵌套回调要自己维护状态和错误分支。
- ↳ handler 代码跑在哪个线程上？阻塞它会怎样？——workflow 的 handler 线程池；阻塞它会占住 worker 槽位，并发一高吞吐就掉——所以导入链里的 DB 访问都是短事务，重活全部异步化。
- 导入链为什么不也用 series 异步串？——同步链本身毫秒级，同步写法简单、事务边界清晰；series 用在真正需要跨网络等待的桥接上，各得其所。

**雷点**：简历写"SeriesWork 串联导入四步"，代码实现是请求内同步 pipeline、SeriesWork 实际用在 RIS 桥接——按上面的口径讲（两处都真实存在），千万别只背简历原句，被要求白板写代码时会露馅（见文末"发现的问题"第 1 条）。

### 🟡 导入接口的请求/响应格式？multipart 和 octet-stream 都支持？怎么解析？

**口语答案**：POST /api/v1/images/import，请求头带 Bearer JWT。请求体两种都收：优先遍历 multipart 表单取第一个非空的文件域；没有文件域就退回 octet-stream 原始 body——这样网关可以走标准 multipart，脚本和测试用 curl 直接推原始字节，很方便。解析是 wfrest 帮我们做完的：multipart 的 body 切分和文件域提取框架完成，我们只拿数据和长度。响应统一 JSON：code、status（ARCHIVED/DUPLICATE/CONFLICT/FAILED）、instance_id、task_id、detail；状态码 201 新归档、200 幂等重复、409 冲突、400 解析失败、500 内部错误。

**追问预演**：
- 怎么防恶意大文件？——依赖网关侧的体量限制；服务侧哈希是流式的、解析遇像素即停，大文件主要耗 IO（可讲演进：请求体大小上限）。
- 一个检查几百张图怎么导？——网关按检查批量推、服务端逐对象处理，每个对象独立走幂等链路（口径：上游按 study 批量推）。
- JSON 是手拼的吗？——是，手写 json_escape 控制转义，不为此引 JSON 库。

### 🟡 500MB 文件导入过程中，内存里同时有它的几份拷贝？

**口语答案**：照实讲，两到三份：请求进来 wfrest 的 body 缓冲一份；multipart 解析出文件域可能再复制一份（取决于框架内部实现）；我这边落盘之后，解析那步又把整个文件读进一个 vector——虽然解析器遇像素即停、实际只扫前几 KB，但读取是整文件读的。哈希那步是 1MB 分块流式，只占常数内存。所以峰值是"框架缓冲加我的解析 buffer"，对 500MB 的 DR 文件确实不优雅，这是我知道的优化点：解析可以只读文件头部加按需 seek，DR 大文件场景值得做。

**追问预演**：
- 为什么当时整文件读？——先保证正确和简单；解析器边界检查在连续内存上最简单可靠，平均对象才 0.7MB，只有 DR 是大文件。
- 优化方案具体怎么做？——元数据都在像素数据 tag 之前，读头部若干 KB 覆盖全部所需 tag 即可，或 mmap 按需缺页。
- 会不会 OOM？——并发导入峰值请求 QPS 约 5，同时几个大文件在内存可控；真上量就该做流式解析。

**雷点**：拍胸脯说"全程流式零拷贝"——下一句就被问"那解析器的输入是哪来的"，诚实标出已知短板反而是加分项。

### 🟡 任务状态接口查什么？状态机有哪些状态、怎么转移？（✅§5：RECEIVED→PARSED→ARCHIVED/DUPLICATE/CONFLICT/FAILED）

**口语答案**：GET /api/v1/instances/{uid}，按 SOPInstanceUID 查两个状态机：归档侧 RECEIVED→PARSED→ARCHIVED，加三个终态 DUPLICATE、CONFLICT、FAILED；备份侧 NONE→PENDING→BACKED_UP/FAILED。转移规则：落盘解析完是 PARSED，归档事务二提交变 ARCHIVED；重复导入不新起一行、直接幂等返回；同 UID 异哈希标 CONFLICT 拒绝。状态放数据库不放内存——这是中断续传的前提：进程崩了重启，靠 status 字段判断哪些对象没走完。管理端还有 backup-status 接口看本地消息表流水，task_id、状态、重试次数。

**追问预演**：
- ↳ 状态放数据库还是内存？为什么？——数据库：崩溃后要能恢复决策、巡检 SQL 要能查堆积；内存状态机崩溃即失忆，续传无从谈起。
- RECEIVED 什么时候出现？——状态机的预留初始态；实现里落盘和解析在同一个请求内完成，直接落 PARSED，RECEIVED 是给"先收文件后解析"的异步模式留的（诚实口径，见文末发现的问题第 2 条）。
- 两个状态机为什么分开？——归档状态和备份状态生命周期不同：归档秒级走完，备份异步分钟级；耦合在一起查询和恢复都别扭。

## bullet 2：四层建模 + 唯一索引 + 状态机续传

### 🔴 为什么要四层建模不是一张大表？（✅§5：反例——患者改名更新风暴、数据冗余不一致）

**口语答案**：因为 DICOM 标准本身就是患者→检查→序列→实例四层层级，而且查询模式是分层的：医生按患者查历史检查，系统按实例定位文件，两个维度差着三个量级。反例就是一张大表：患者姓名、性别在每个实例行重复——一次 CT 检查几百张图就是几百行冗余，患者改名就是一场更新风暴，中途失败还留下新旧行不一致。范式化之后患者信息只有一份，各层 UID 建唯一键做幂等，一次检查 100 到 500MB 的几百个对象共享同一个 study 行。

**追问预演**：
- 查"某患者的所有影像"怎么办？——patient→study→series→instance 沿外键 JOIN，患者维度有索引，路径清晰。
- 层级 UID 谁保证唯一？——DICOM 标准全局唯一；我们不信任它，照样建唯一索引兜底裁决。
- 以后分库分表怎么办？——按 study 哈希分片，四层天然聚簇在一次检查内，拆分友好。

---

### 🔴 为什么 UID 不直接当主键？（✅§5：长主键→二级索引膨胀+随机插入页分裂）

**口语答案**：UID 是最长 64 字符的 VARCHAR。InnoDB 里二级索引的叶子节点存的是主键值，主键一长，每个二级索引都跟着膨胀；更糟的是 UID 不是有序的，直接当聚簇索引主键，插入位置随机，B+ 树会频繁页分裂、写放大。所以用自增 BIGINT 代理键做主键——顺序插入、JOIN 也便宜——UID 建唯一索引做业务幂等键，两边的好处都拿到。这是"代理键加业务唯一键"的双键设计，医疗这种写入方单一、UID 语义强的场景很常用。

**追问预演**：
- 为什么自增主键好？——聚簇索引顺序追加，不分裂、页利用率高（接 MySQL 专项）。
- 唯一索引和普通索引写起来差多少？——唯一索引多一次唯一性检查，可忽略；换来数据库层的原子裁决，值。
- BIGINT 会用完吗？——无符号 64 位，日增 15 万对象也够几万年。

### 🔴 幂等怎么保证的？并发导入同一个文件会发生什么？（✅§5/§7：唯一索引裁决 + FOR UPDATE 串行化）

**口语答案**：幂等键是 SOPInstanceUID，DICOM 保证全局唯一。两层防线：第一层，uk_sop_uid 唯一索引把"存不存在"的竞态收窄到数据库原子裁决——对比"先查后插"，两个并发都查不到、都插入，脏数据就进来了；第二层，导入事务一进来先 SELECT FOR UPDATE 锁住该 UID 的行，并发的同 UID 导入在锁上排队，后到者醒来时行已存在，进决策树按哈希分流：同哈希返回 200 幂等带既有 id，异哈希 409 拒绝。净效果：同一个文件导多少次，库里只有一行、OSS 只有一份。

**追问预演**：
- 只靠唯一索引行不行？——能防脏数据，但拿不到"已存在行的状态和 id"做决策树；FOR UPDATE 把判断和动作放进一个临界区。
- 并发首导同一新 UID 会怎样？——两个事务都要在同一个位置插入，会有一方被死锁回滚，重试后撞 DUPLICATE 幂等收敛（细节见 §3 FOR UPDATE 题）。
- 幂等键为什么不用内容哈希？——哈希做的是内容指纹（判重判冲突），身份键必须是 UID：同 UID 是"同一个对象"，哈希只能回答"内容是否一致"。

### 🔴 中断续传怎么实现的？进程在各个点崩溃后重启，分别发生什么？（✅§7：三个崩溃窗口及恢复路径）

**口语答案**：靠两个锚点：数据库里的 PARSED 状态和 staging 目录的临时文件。三个崩溃窗口逐个过：一，写 staging 中途崩——库里没记录，残留的 .part 文件无害，重导全新处理，孤儿文件定期清；二，事务一提交（实例 PARSED）之后、rename 之前崩——行在库、状态 PARSED，重导同 UID 同哈希走续传分支：刷新层级引用、补 rename、提交事务二收尾；三，rename 之后、事务二之前崩——文件已在最终路径，重导同样续传收尾。核心是进程无状态，一切可恢复的信息都在库和文件系统里。

**追问预演**：
- 谁触发"重导"？——上游网关对我们返回非 201 会重试；幂等设计保证重试无副作用。
- RECEIVED/PARSED 的对象会永远卡住吗？——巡检 SQL 能查出来；消息表堆积告警覆盖备份侧。
- 续传会重复插层级表吗？——不会，层级 upsert 幂等，靠唯一键加 LAST_INSERT_ID 技巧。

**雷点**：只会背"有续传"，画不出三个崩溃点各自的恢复路径——这题就是考你对事务边界的理解，边框画错了整条链都白讲。

### 🟡 患者身份为什么 (PatientID, Issuer) 复合唯一？Issuer 为什么不许 NULL？（✅§5：NULL 不参与唯一约束，已实证）

**口语答案**：同一个 PatientID 可能来自不同医院或不同系统——院内外、本院和区域平台各发一套号，Issuer 标记身份的发行方，(PatientID, Issuer) 合起来才是全局身份，只认 PatientID 会把两个患者合并。Issuer 不许 NULL 是 MySQL 的坑：唯一索引对 NULL 不去重——我们建临时表实测过，两条相同 PatientID、issuer 都是 NULL 的记录都插得进去；改成 NOT NULL DEFAULT ''，空串才参与唯一约束。这个坑一句话就能现场演示，印象很深。

**追问预演**：
- 为什么不是 NULL 而是''？——NULL 在 MySQL 唯一索引语义里"互不相等"，''是普通值参与比较。
- 其他 NULL 陷阱？——NULL 参与比较结果是 NULL 不是真假、count 不含 NULL 行、索引对 is null 的处理。
- 患者信息重复导入怎么合并？——患者层 upsert：撞唯一键就取既有行 id 并刷新姓名（改名场景），不产生第二行。

### 🟡 物理外键加不加？你们为什么加？（✅§5：完整性优先 vs 互联网高并发/分库分表场景不加）

**口语答案**：我们加了物理外键，这是场景取舍：写入方单一——只有归档服务写这套表、写入量可控、医疗数据完整性优先，外键从数据库层杜绝孤儿实例和悬挂引用，出了脏数据在医院是事故。互联网高并发场景常不加：外键有锁开销、拖慢写入，而且分库分表之后跨库外键直接失效，只能靠应用层维护一致性。我能把两边的理由都摆出来——加不加不是对错题，是业务优先级题，医疗这个场景我站完整性。

**追问预演**：
- 外键对导入性能有影响吗？——每次插入多一次父行存在性检查，我们的量级（日 15 万）完全无感。
- 分库分表了怎么办？——应用层维护：插入前查父行或依赖上游保证层级先建好。
- 为什么不用触发器做校验？——触发器隐式执行、排障困难，外键是声明式的、语义清晰。

### 🟡 sha256 为什么 CHAR(64)？DATETIME(3) 为什么？

**口语答案**：SHA-256 输出恒定 64 个十六进制字符，定长 CHAR(64) 比 VARCHAR 省一个长度前缀字节，语义也更准——存的就是定长指纹，不存在"有时 63 个字符"的世界。DATETIME(3) 是毫秒精度：备份链的延迟统计、消息表的 next_retry_at 到期判断、堆积巡检的"超时 5 秒"判断都建立在毫秒差上，秒级精度这些计算全糊掉；排障时对时间线，毫秒也常常是关键。

**追问预演**：
- 为什么存十六进制不存二进制？——32 字节二进制省一半空间，但十六进制可读、可直接进 SQL 日志比对；量级下空间不是瓶颈。
- 为什么不用 TIMESTAMP？——2038 问题加时区语义隐式转换，DATETIME 存什么是什么，内网统一时区更直。
- 时间戳谁生成的？——默认 CURRENT_TIMESTAMP(3) 加 ON UPDATE 自动维护。

## bullet 3：RAII + 流式 SHA-256 + 哈希判重/判冲突

### 🔴 为什么流式分块算哈希？整文件读进内存会怎样？

**口语答案**：哈希必须覆盖文件全部内容才有意义，而我们的对象里 DR 单张 30 到 50MB、CT 整检查 100 到 500MB，整文件读进内存算哈希，并发几个请求内存就爆了。流式分块只需要 1MB 常驻缓冲，内存占用和文件大小无关；EVP_DigestUpdate 逐块增量喂入，最终结果和一次性算完全一致。代价几乎为零——文件本来就要从盘上读一遍，哈希是搭在这次 IO 上的顺风车，只多了 CPU 上的压缩函数计算。

**追问预演**：
- CPU 开销大吗？——SHA-256 吞吐 GB/s 级，0.7MB 平均对象毫秒以内，不是瓶颈。
- 为什么不顺便把哈希算在落盘时？——可以合并那次读盘，是已知优化点；当前两次读有页缓存兜着。
- 哈希和文件一起怎么防篡改？——哈希入库后就是基线，重复导入比对哈希即可发现内容变化。

---

### 🔴 RAII 在这里具体管了什么资源？RAII 的本质讲一下（技能栏联动，§13 C++ 专项）

**口语答案**：两个实例：SHA-256 的 EVP_MD_CTX——封装成栈上的 Sha256 对象，构造时 new、析构自动 free，中间任何提前 return 都不漏；数据库连接的 MySQLGuard——构造从池里 acquire、析构自动归还，异常路径也不泄漏连接。RAII 的本质是把资源的生命周期绑定到栈对象的生命周期：C++ 没有 GC，但析构函数是确定性执行的——正常返回、提前返回、异常展开，栈对象都会被析构。把"释放"写进析构函数，就把最容易漏的那条路径交给语言机制兜底。

**追问预演**：
- Guard 为什么禁拷贝只留移动？——归还权必须唯一：拷贝会让两个 Guard 指向同一连接、双重归还加并发使用；移动转移归还权、旧对象置空——正好是 C++11 move 的实战用例。
- 文件句柄也 RAII 了吗？——诚实说：staging 的文件句柄当前是手动 fclose，各分支都覆盖了，严格 RAII 化（封装 FileGuard）是改进项（见文末发现的问题第 3 条）。
- 智能指针和 RAII 什么关系？——unique_ptr/shared_ptr 是 RAII 在堆资源上的标准化封装，RAII 是思想、智能指针是工具。

**雷点**：只会背"RAII 就是智能指针"——RAII 是构造/析构对称的思想，智能指针只是它的一个应用；这题挂在技能栏，答窄了 C++ 专项全垮。

### 🔴 同 UID 不同内容为什么拒绝？静默覆盖行不行？（医疗数据不可变性）

**口语答案**：因为医疗数据不可变。同一个 SOPInstanceUID 在语义上就是同一张影像，如果同 UID 不同内容还静默覆盖，可能出现"医生上周看的片和这周看的片不一样"却没有任何痕迹——这在医疗是事故级问题，影像是诊断依据。所以哈希不一致直接 409 拒绝：已归档的数据一个字节不动，未归档完的 PARSED 行标记 CONFLICT 便于排障，让人工去裁决是上游发错了还是真有新版本。通用一点说，这是"身份键和内容指纹分开校验"的设计：UID 定身份，哈希验内容，对不上宁可拒绝不可默默改。

**追问预演**：
- 真有合法的版本更新怎么办？——走人工：排障确认后由管理动作处理，不做自动覆盖。
- 409 的响应里给什么？——既有 instance_id 加冲突原因，调用方能定位是哪个对象。
- 冲突会污染已归档数据吗？——不会，DUPLICATE/CONFLICT 分支都不改既有归档行。

### 🟡 SHA-256 和 MD5/SHA-1 比，为什么选它？（碰撞/安全视角）

**口语答案**：MD5 和 SHA-1 都已经被实际的碰撞攻击——攻击者可以构造两个哈希相同的不同文件。我们的哈希承担两个职责：完整性基线和内容指纹（判重判冲突），一旦能被碰撞，攻击者可以让"篡改过的文件"和原文件哈希一致，判重逻辑直接被骗过——把冲突伪装成重复导入。SHA-256 目前没有实际碰撞，性能上 OpenSSL 原生支持、吞吐 GB/s 级，在我们场景没有可感知成本，是"零成本买安全底线"的选择。

**追问预演**：
- 为什么不上 SHA-3/512？——SHA-256 安全余量对本场景足够，更长摘要只是存储和比对成本增加。
- 哈希能防谁？——防传输损坏和无意变更是一定的；防恶意攻击者还要配合鉴权，别夸大。
- 判重为什么不用更快的 CRC？——CRC 是校验和不是密码学哈希，碰撞概率高到能自然发生，只能防意外不能防构造。

### 🟡 分块多大？为什么这个大小？

**口语答案**：1MB。权衡两头：分块太小，比如 4KB——500MB 文件要十二万多次循环加函数调用，开销全在调度上；分块太大，比如一次 100MB——就失去"内存与文件大小无关"的意义了。1MB 的效果：平均 0.7MB 的对象基本一两块读完；500MB 的 DR 文件也始终只占 1MB 常驻内存；而且 1MB 和操作系统的页缓存、磁盘预读的量级合拍，顺序读的吞吐能吃满。

**追问预演**：
- 试过别的块大小吗？——开发时对比过 64KB/1MB/4MB，量级差异不明显，1MB 是"够小保内存、够大保吞吐"的中庸值。
- fread 和 read 系统调用什么关系？——fread 是 stdio 带用户态缓冲，减少系统调用次数；直接 read 每块一次陷入内核。
- 哈希能边收网络流边算吗？——可以，multipart 拿到的是完整 body，落盘后算；真流式需要框架级分块回调，是演进项。

### 🟡 重复导入返回什么？冲突返回什么？（200 幂等返回 / 409）

**口语答案**：重复——同 UID 同哈希且已 ARCHIVED——返回 200，status 是 DUPLICATE，带既有 instance_id，staging 临时副本直接删掉：语义是"你要的结果已经在了，这次调用也算成功"。冲突——同 UID 异哈希——返回 409 加 CONFLICT，绝不覆盖。新对象 201 带 task_id。这组状态码是刻意对齐 HTTP 语义的：200 成功且无新资源产生，201 创建了新资源，409 与既有资源冲突——上游网关拿状态码就能决定要不要重试，不需要解析 body 猜。

**追问预演**：
- 为什么重复不用 201？——没有创建新资源，201 会误导网关的计数和去重逻辑。
- 409 之后上游该干嘛？——不重试，报警人工查；重试也还是 409。
- 幂等返回的 body 和首导一致吗？——instance_id 相同、task_id 为空（没有新备份任务），detail 说明是幂等命中。

# §3 PACS 导入链深挖（同步链 + 事务）

## 🔴 完整讲一遍一次导入的流程（从 HTTP 请求到返回 201，每一步做什么）。

**口语答案**（这题就是主线叙事，练到 60 秒内讲完）：
带 JWT 的 POST 进来。第一步网关内鉴权：解 Bearer token，srpc 调认证服务验签加 RBAC，动作是 images:import。第二步取数据：multipart 文件域优先，否则原始 body。第三步落 staging：UUID 文件名写进 storage 目录的 staging 子目录、fflush 保证落盘——这是中断续传的锚点。第四步解析：手写 DICOM 解析器提取四层元数据，tag 升序遇到像素数据就停，耗时和文件大小解耦。第五步算哈希：1MB 分块流式 SHA-256。第六步事务一：FOR UPDATE 锁该 UID 行、跑幂等决策树、三层层级 upsert、实例落 PARSED。第七步 rename：staging 挪到 studyUID/seriesUID/sopUID.dcm 最终路径，同目录所以原子。第八步事务二：实例改 ARCHIVED、备份状态置 PENDING、backup_event 插本地消息表——和状态变更同一事务，这是消息不丢的第一道防线。第九步返回 201 带 task_id，随后立刻走快路径发 MQ，发失败由 3 秒一轮的补偿扫描兜底。同步链 P99 300ms 以内。

**追问预演**：
- 哪几步可能失败、分别返回什么？——解析失败 400、冲突 409、重复 200、DB/IO 失败 500，每步失败都清 staging。
- 事务二失败怎么办？——回滚并清理已 rename 的孤儿文件，保持"库里看得见的状态和文件系统一致"。
- 消息什么时候发出去？——响应之后快路径立刻发；核心约束是"事件先落库再发消息"，顺序不能反。

**雷点**：这题讲乱=整场面试的地图没了。固定顺序口诀：鉴权→取数→落盘→解析→哈希→事务一→rename→事务二→201。

## 🔴 为什么两个事务而不是一个大事务？（✅§7：文件 rename 是 IO 不进事务）

**口语答案**：因为两个事务中间夹着一个文件 rename，而文件 IO 不能进数据库事务。如果一个大事务包揽：rename 期间该行的锁一直持有，文件系统操作时长不可控——存储一抖就是长事务、长锁，并发导入全被拖住；而且数据库回滚得了、文件系统回滚不了，两个世界没有共同的事务。拆开之后每个事务都是毫秒级短事务，中间的崩溃窗口由 PARSED 状态加 staging 文件兜底，重导续传收尾。一句话：把不可回滚的文件操作挤到两个可回滚的事务之间。

**追问预演**：
- ↳ 事务一提交后、rename 前崩溃怎么办？——行停在 PARSED、staging 有完整文件；重导同 UID 同哈希命中续传分支：刷新层级引用、补 rename、提交事务二。第二次导入自动把第一次收尾。
- ↳ 为什么数据库事务里不能做文件 IO？——三个理由：拉长锁持有时间；IO 失败无法随事务回滚；连接池连接被长时间占用，吞吐塌方。
- 万一 rename 成功但最终路径上已有文件呢？——同 UID 走不到这，不同 UID 路径必不同；路径由 UID 三级拼出，天然无碰撞。

## 🔴 `INSERT ... ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id), ...` 这条 SQL 为什么这么写？

**口语答案**：它一条语句完成"插入或取回已存在行的 id"。关键在 UPDATE 子句里的 id=LAST_INSERT_ID(id)：撞唯一键时，把已存在行的 id 赋给 LAST_INSERT_ID——这是 MySQL 文档认可的惯用法——于是 mysql_insert_id 在"新插入"和"撞键已存在"两种情况下都返回正确的行 id，层级表的患者、检查、序列三层 upsert 全靠它，不需要"先 SELECT 判断再 INSERT"。影响行数的语义：1 是新插入，2 是更新了已有行，0 是命中但值没变化——这个语义在排查时很有用。

**追问预演**：
- ↳ 为什么不用"先查后插"？竞态在哪？——两个并发都 SELECT 不到、都 INSERT，靠唯一索引撞 1062 才能裁决；ON DUPLICATE KEY 把两步合成一步原子完成，竞态窗口消失。
- ↳ 影响行数 1/2/0 分别代表什么？——1 新插入；2 撞键且发生了更新；0 撞键但更新值和原值相同（MySQL 认为没改动）。
- 💣↳ mysql_insert_id 在 COMMIT 后返回 0 的 bug——必主动讲，见下一题。

## 💣 你踩过的 mysql_insert_id 在 COMMIT 后返回 0 的 bug（主动讲出来是最好的加分项，✅§7 踩坑实录，必背）

**口语答案**：这个 bug 我主动讲，印象最深。现象是联调时一批实例卡在 PARSED、本地消息表插不进去，日志报外键错误 instance_fk=0。定位：事务一里 INSERT 实例之后，我先发了 COMMIT、再调 mysql_insert_id 取 id——而 insert_id 绑定的是"本连接最后一条语句"，COMMIT 之后它就返回 0，事务二拿 0 去插 backup_event，被外键拒绝，事务一回滚不了（已提交），实例停在 PARSED。修复就是把取 id 挪到 INSERT 之后、COMMIT 之前，一行顺序调整。两个收获：一是吃透了 MySQL C API 的会话语义——insert_id 是连接级、语句时序敏感的；二是状态机兜住了我自己的 bug：卡住的实例第二次导入走续传分支自动收尾，没有产生脏数据。当时在代码注释里把这个坑写成了警示。

**追问预演**：
- 为什么单测没拦住？——触发条件是"取 id 晚于 COMMIT"这个特定顺序，正常断言只看结果行存在与否；之后补了实例状态对账。
- 有没有通用防法？——封装 DAO：取 id 和 INSERT 绑死在一个函数里，调用方拿不到犯错的时机。
- 什么场景 insert_id 还会踩坑？——同连接混用、多条 INSERT 只记最后一条、REPLACE 语义不同——都是"连接级状态"这同一个根。

**雷点**：这题是"把踩坑讲成资产"的样板——讲成"MySQL 有 bug"或"我改了就好了"都浪费了；必须落到根因（连接级、语句时序）和收获（状态机兜底）。

## 🔴 SELECT ... FOR UPDATE 锁的是什么？锁的范围多大？

**口语答案**：锁的是 SELECT 命中的索引记录，走的是 uk_sop_uid 唯一索引。行存在时是精确的记录锁，只锁这一行；行不存在时——MySQL 默认 RR 隔离级别下——会加间隙锁，锁住这个 UID 本应插入的位置，范围是唯一索引上相邻两个值之间的间隙。所以"范围多大"要分情况：存在则一行，不存在则一个间隙。它在我们链路里的作用：把"查状态、比哈希、做决策"放进临界区，并发的同 UID 导入在锁上排队，不可能有两个事务同时判"不存在"。

**追问预演**：
- ↳ 两个事务同时导入同一 UID，时序逐帧？——行已存在：B 的 FOR UPDATE 等 A 的行锁，A 提交后 B 醒来看到 ARCHIVED 行，比哈希走 DUPLICATE/CONFLICT。行不存在（首导并发）：A、B 都拿到同一间隙的间隙锁（间隙锁彼此兼容），随后都要往这插——插入意向锁和对方的间隙锁冲突，可能死锁。
- ↳ 会不会死锁？怎么处理？——首导并发同新 UID 可能死锁；InnoDB 死锁检测自动回滚代价小的一方（报 1213），另一方正常插入成功；被回滚方重试后命中 DUPLICATE，幂等收敛。应用层把 DB_ERROR 返回上游重试即可。
- ↳ 怎么排查死锁？——SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK 段，两个事务持锁等锁的顺序都在里面；再对照业务日志对时序。

**雷点**：答"锁整张表"或"只锁一行"都错——必须区分行存在/不存在两种情况，这正是间隙锁考点的标准问法。

## 🟡 staging 临时文件放哪个目录？为什么不能放 /tmp？（✅§7：rename 跨文件系统 EXDEV 失败）

**口语答案**：放在 storage 目录下的 staging 子目录，和最终对象同一个文件系统。因为续传的最后一步是 rename(2)，而 rename 只在同文件系统内保证原子性——跨文件系统它会返回 EXDEV 直接失败。放 /tmp 是这个设计的经典错误：/tmp 通常是独立挂载，甚至是 tmpfs——rename 必挂；tmpfs 还占内存、重启丢失，和"落盘锚点"的初衷相反。另外 staging 文件名用 UUID，并发导入互不覆盖，也是崩溃后续传场景的锚点。

**追问预演**：
- rename 为什么原子？——同文件系统内只是目录项操作，内核持锁完成，观察者要么看到旧路径要么看到新路径，没有中间态。
- 跨文件系统怎么办？——copy 加 unlink 两步，但两步就不原子了，要用临时标记加恢复逻辑，复杂度陡增。
- staging 残留文件谁清？——失败路径当场 unlink；异常退出的孤儿 .part 靠低频清理任务。

## 🟡 事务隔离级别用的哪个？为什么？

**口语答案**：MySQL 默认的 RR，我们没有显式改。原因是这条链路的正确性不依赖隔离级别：并发控制靠 FOR UPDATE 当前读加唯一索引兜底，这两个机制在 RR 和 RC 下行为一致；查询侧都是按 UID 的点查，没有 RR 才能解决的对象（比如可重复读的一致性快照需求）。反倒是 RR 下"不存在的行加间隙锁"让锁范围变大——如果导入并发上量、死锁变多，把这条链路降 RC 是现成的优化手段，能缩小间隙锁范围。当前峰值请求 QPS 约 5，完全没这个必要。

**追问预演**：
- RR 和 RC 的核心区别？——RR 事务内多次读同一快照、当前读加间隙锁防幻读；RC 每条语句新快照、只锁记录。
- 为什么很多互联网公司用 RC？——间隙锁少、死锁少、写入并发更友好，代价是要自己处理幻读类逻辑。
- 你们有依赖 RR 的读吗？——巡检和列表查询都不是重复读场景，没有。

**雷点**：顺口说"我们特意选了 RR"——代码里根本没设置，是默认值；说"特意"会被追问为什么、和 RC 对比就露怯。诚实说"用默认 RR+理由"。

## 📐 导入接口耗时分布？瓶颈在哪一步？

**口语答案**：先给结论数字：同步链 P99 300ms 以内——落盘、解析、两事务入库，不含备份；解析和文件大小解耦，500MB 的 CT 文件元数据解析 5ms 以内。结构上拆：线性于文件大小的是两步 IO——落盘写一遍、哈希读一遍，DR 大文件的长尾就在这；常数级的是解析（遇像素即停）、两次短事务（每次几毫秒的网络往返加执行）、一次 rename。瓶颈判断要分流量形态：平均 0.7MB 的对象下瓶颈在数据库事务串行度和连接池；DR 这种大文件进来时瓶颈瞬间切到磁盘 IO。分步骤的精确耗时分布需要专项压测，这个在待补清单里，我不编数字。

**追问预演**：
- 怎么观测耗时的？——日志里每步带毫秒时间戳（DATETIME(3) 级别的日志习惯）；聚合 P99 依赖监控平台的接口耗时指标。
- 要把 P99 再砍一半，动哪里？——合并落盘和哈希那次读盘（页缓存里本来就有）、事务一和事务二的往返合并评估、连接池预热。
- 50 对象/秒的目标怎么达成？——上游批量请求摊薄单对象开销、多 handler 线程并发、DB 短事务——设计和实测留了余量（待补数字：专项压测报告）。

**雷点**：现场编一个"落盘 80ms、解析 5ms、事务 100ms"的分布——这些分布数字口径里没有，编了必被"怎么测的"问死；给结构性分析加"分布待补"是安全答法。

2. **RECEIVED 状态从未被写入**：`pacs_db_init.sql` 的 CHECK 约束和状态机文档都含 RECEIVED，但 `ArchiveDao.cpp` 的 INSERT 直接写 'PARSED'（落盘与解析在同一请求内完成）。答案已按"预留初始态"口径处理，面试若被问"什么时候是 RECEIVED"照此答，不要说"落盘后先落 RECEIVED 再解析"。
3. **"RAII 管理文件句柄"与代码有出入**：弹药库/架构文档称 SHA-256 步骤"RAII 管理文件句柄与 EVP_CTX"，但 `Sha256.cpp` 的文件句柄是手动 fopen/fclose（各分支均已正确关闭）；RAII 实际覆盖的是 EVP_MD_CTX（Sha256 类析构）与 MySQL 连接（MySQLGuard）。答案按代码口径，并把"文件句柄 RAII 化"作为主动承认的改进项讲。
4. **口径"上游网关按 study 批量推（10–50 对象/请求）"与代码不符**：导入接口一次只处理一个对象（multipart 单文件域或原始 body）。"请求 QPS 峰值 ~5"与"对象吞吐 50 个/秒"仅在批量或多并发前提下自洽。本文件答案表述为"网关按检查批量推、服务端逐对象处理"，用户校对口径时需确认服务端是否存在逐对象循环的外层逻辑，或修正口径数字。
5. **FOR UPDATE 并发语义的精度**：弹药库 §7 说"并发同 UID 导入在此排队"——该说法对"行已存在"成立；对"行不存在"（首次并发导入同一新 UID），RR 下两个事务都能获得同一间隙的间隙锁（间隙锁彼此兼容），随后插入意向锁互相冲突可能触发死锁，由 InnoDB 自动检测回滚一方。题库 §3 追问"会不会死锁"的答案已按此事实作答，与弹药库表述的简化版有出入。
6. mysql_insert_id bug 的修复（INSERT 后立即取 id）与代码注释、弹药库 §7 一致，无矛盾；弹药库描述"事务二拿 instance_id=0 插消息表被外键拒绝→实例卡 PARSED→第二次导入靠续传分支自愈"与代码行为吻合。
