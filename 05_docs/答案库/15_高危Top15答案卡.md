## 卡 3｜OSS 为什么异步 + "wfrest 不是全异步吗"挑刺版

**核心答案**：因为远端对象存储写入耗时不可控——网络抖动、限流是常态，放请求线程，导入接口会被拖到秒级。放异步消息链后，接口只做落盘、解析、入库，P99 300 毫秒内返回；OSS 上传由独立消费者慢慢做，靠本地消息表、confirm、手动 ACK、死信队列保证不丢不重。日增 15 万个备份任务全走这条链。

**三层追问预演**：
- L1 "wfrest 全异步，放请求线程也阻塞不了啊？"——认下"阻塞"只是最直白的入门说法，真实动机三个：解耦（OSS 的限流毛刺不传染给导入接口）、削峰（上午 9–11 点集中导入，高峰 1–2 万积压、1 小时内回落是设计内潮汐）、失败隔离加可靠性语义（重试、指数退避、死信在消费端是现成的）。且挂起等待的任务仍占内存和连接，同步链 300ms 的预算不该花在远端写入上。
- L2 那为什么不直接异步任务上传、非要过 MQ？——异步任务还在同一进程：扩缩容绑定、重启互相影响、没有削峰缓冲和重试死信语义；独立消费者进程加 MQ 四样全有，事故分流时真用过。
- L3 削峰的代价是什么？——备份从同步完成变最终一致：积压和延迟，当日清零，双条件告警盯着（>2 万且持续 1 小时）。

**雷点**：被挑刺后改口"其实也能放请求线程"——前功尽弃；正确姿势是认下表述直白、立刻给三层动机。

## 卡 4｜消息丢失窗口四连

**核心答案**：四个窗口四个机制，谁也不兼职。①事务二提交前崩溃——事件和归档状态在同一个本地事务里，一起回滚，消息根本不存在、无消息可丢，导入失败上游重试；②发布或 confirm 返回前崩溃——事件已落库、状态 PENDING，补偿扫描 3 秒一轮，超 5 秒补发；③broker 落盘前宕机——exchange、queue 都声明 durable，消息 delivery_mode=2，broker 重启消息还在；④消费处理中崩溃——手动 ACK 没发，broker 自动重投。最后的顺序刻意是"先落库后 ack"，反过来才真丢。

**三层追问预演**：
- L1 confirm 还没回来 broker 就挂了呢？——发布端按失败处理留 PENDING 等补发；broker 侧 durable 加 delivery_mode=2 保证重启后消息还在；极端情况多一条重复，消费端幂等吸收。
- L2 补偿扫描和正常发送会不会重复发？——会，明确接受：允许重复、保证不丢，窗口只能缩小不能归零——归零要把 MQ 操作包进数据库事务，不值得。
- L3 ack 发了才崩呢？——那是重复不是丢失（消息已消费成功），正好引到下一题的幂等收敛。

**雷点**：窗口数答三（漏事务前）或五（把"ack 后崩溃"算成丢）；说"有 confirm 就不丢"——confirm 只覆盖"broker 收到"那一段。

## 卡 5｜消息重复消费怎么收敛

**核心答案**：会重复，at-least-once 的必然代价，我们的态度是"允许重复、保证不丢、消费端收敛"，三道闸：第一道，消费前先查 backup_event 状态，CONFIRMED 或 DEAD 直接 ack 跳过——task_id 有唯一约束；第二道，真正执行的动作是 OSS PutObject，同 key 同内容覆盖，天然幂等；第三道，收尾的两个状态更新放同一个本地事务。净效果等效 exactly-once——同一任务消费多少次，云端和库里只有一个终态。

**三层追问预演**：
- L1 task_id 去重靠唯一索引还是先查后改？——快路径先查（省一次上传），裁决兜底靠唯一约束：task_id 在归档事务里只插一次、消息里带的也是它，一一对应。
- L2 "查状态→执行→改状态"之间还有竞态吗？——多实例时窗口存在——两边同时判"未完成"都去上传——但 OSS 覆盖幂等加状态 UPDATE 是幂等赋值，最坏多传一次，结果收敛一致。
- L3 为什么只说"等效"exactly-once？——真 exactly-once 要事务性 MQ 或协议级支持；正确表述是 at-least-once 投递加消费幂等，效果上等效——一字之差就是懂和背的区别。

**雷点**：吹"我们做到了 exactly-once"——分布式下没有协议支持做不到，这个表述本身就是扣分点。

## 卡 6｜粘包半包怎么处理（TLV 增量解码器）

**核心答案**：TCP 是字节流、没有消息边界，所以必须应用层协议自己定边界。我们的 TLV 帧：type 1 字节、flags 1 字节、len 4 字节网络字节序，载荷上限 1MB。解码器是增量的、每连接一个实例：onMessage 到数据先循环取完整帧——头部不齐先攒、体不齐继续攒、完整就处理，一次回调里有多个帧就循环取、半帧留缓冲。非法帧类型直接断连——这时长度字段不可信，无法重同步。

**三层追问预演**：
- L1 一次 onMessage 收到两个半帧怎么办？——循环取帧：第一帧完整就处理，剩下的不足一帧留在缓冲区等下次；客户端分三次 send 发半帧也同理拼起来。
- L2 非法帧为什么断连不跳过这个帧？——长度字段是定位下一帧的唯一依据，帧类型非法意味着长度不可信，跳多少字节都不对——同步已不可能，保命要紧。
- L3 客户端谎报长度 2GB 会怎样？——MAX 载荷 1MB 检查，超限 TOO_LONG 断连；否则按 2GB 预分配缓冲区就是内存攻击面。

**雷点**：说"TCP 粘包是 TCP 的 bug"——TCP 是流语义，本来就没有消息概念，边界是应用层的责任；len 为什么网络字节序答不出（跨平台统一字节序，小端宿主 memcpy 直读会错）。

## 卡 7｜手写线程安全 LRU

**核心答案**：两个容器组合：std::list 存 pair 维护访问序——队头最近使用、队尾最久未用；unordered_map 存 key 到链表迭代器，O(1) 定位。get 命中把节点 splice 到队头——只重连指针不拷贝数据，O(1)；put 满了淘汰队尾。两个细节：淘汰时先删 map 索引再 pop_back 节点——反了的话 key 取不到、迭代器悬垂；线程安全一把 mutex 护住所有操作，临界区是一次哈希查找加指针搬移，百纳秒级。项目里 L1 缓存就是它，512 条容量。

**三层追问预演**：
- L1 splice 为什么 O(1)？迭代器还有效吗？——splice 只重连前后指针，节点不销毁不拷贝；map 里存的迭代器继续有效——这正是选 list 的原因。
- L2 锁能不能细一点？读写锁行不行？——不行：get 也要 splice 改链表，"读"本质是写，读写锁无收益；要细粒度就分段锁——哈希分片、每片一个 list 加 map，高并发才值得。
- L3 get 和 put 各锁几次？——各一次，进门 lock_guard 到函数返回，绝不嵌套加锁；要是加淘汰回调（比如写回），锁内拷数据、锁外做回调。

**雷点**：用 erase 加 push_front 替代 splice（暴露不了解 list 特性）；淘汰顺序说反（先 pop_back 再删索引）当场翻车。

## 卡 8｜唯一索引怎么做幂等 + 并发导入时序（FOR UPDATE）

**核心答案**：幂等地基是 SOPInstanceUID 唯一索引：并发重复导入时第二个 INSERT 撞 1062，转"重查加哈希对比"分支——同 UID 同哈希按重复导入幂等返回，同 UID 异哈希标记冲突 409 拒绝，绝不静默覆盖。并发时序：决策树在 SELECT FOR UPDATE 之后——锁住该 UID 的行，并发同 UID 的导入在此排队，两个事务不可能同时判"不存在"。对比"先查后插"：两边都查不到就都插入，脏数据。

**三层追问预演**：
- L1 FOR UPDATE 锁的是什么？范围多大？——锁唯一索引命中的那一行，范围极小；不同 UID 互不影响，并发导入不同对象完全并行。
- L2 为什么两个事务不是一个大事务？——中间的文件 rename 是 IO，事务里做 IO 等于长事务加长锁；拆开后崩溃窗口由 PARSED 状态加 staging 文件兜底。
- L3 会不会死锁？——单 UID 只锁单行，并发同 UID 是排队不是交叉持锁；层级 upsert 按 patient→study→series 固定顺序访问，交叉成环概率极低；真发生 InnoDB 死锁检测自动回滚一个，SHOW ENGINE INNODB STATUS 看最近死锁日志。

**雷点**：把"先查后插加唯一索引兜底"说成本项目的方案——我们根本不走先查后插，唯一索引就是第一道裁决；哈希对比的目的说不清（区分"重复导入"和"UID 冲突"两种结局）。

## 卡 9｜索引不可变 + 版本切换为什么

**核心答案**：两个理由。一是读路径永远面对完整一致的快照——构建新版本不阻塞查询：80 万文档全量重建约 12 分钟，每天凌晨 2 点定时，期间服务照常跑，双版本切换不停服务。二是切换是 O(1) 的——新索引建好，shared_ptr 原子替换，零锁；正在查询的线程还拿着旧索引，引用计数归零自动析构。版本目录 v1、v2 落盘共存，回滚就是指回旧目录；缓存键里也带版本号，切换后天然读新结果。

**三层追问预演**：
- L1 重建期间查询怎么办？——读旧版本快照，新旧共存、原子切换——这就是"不可变"买来的东西。
- L2 旧索引什么时候释放？——引用计数：最后一个持有旧快照的查询结束，shared_ptr 计数归零自动析构；atomic_store/atomic_load 保证指针替换本身线程安全。
- L3 增量更新怎么做？——现在全量 12 分钟够用；真增量是文档级 tombstone 加定期 merge——Lucene 段合并同思路，段集合指针照样用这套原子切换。

**雷点**：说"切换时加写锁保护索引"——那就把不可变设计的最大卖点讲没了；80 万文档/35 万词项/12 分钟这组数字要能互相印证（词表小是因为分词去重加停用词过滤）。

## 卡 10｜为什么 RabbitMQ 不是 Kafka

**核心答案**：按需求画像选：量不大——日均 15 万条、峰值每秒几十条；每条都要可靠的投递确认；失败要有现成的死信和重试语义。RabbitMQ 的 confirm、DLQ、路由模型正好整套匹配，团队也熟。Kafka 的强项是百万级吞吐、回放、流处理，但在这条链上：per-message 的 confirm 没有原生对应——acks=all 是分区副本层面的；重试和死信要自己搭重试 topic；运维更重。中间件选型选的是语义匹配，不是流行度。

**三层追问预演**：
- L1 Kafka 怎么保证不丢？——三段各配齐：生产端 acks=all 加重试；broker 侧 replication.factor≥3 加 min.insync.replicas≥2；消费端关自动位移、处理完手动提交——三段缺一就有丢失窗口。
- L2 用 Kafka 重做这条链怎么设计？——本地消息表仍然要（生产端丢失窗口和用什么 MQ 无关）；confirm 换发送回调加 acks=all；按 instance_id 做 key 保序进分区；重试 topic 加死信 topic 自建，退避状态照旧在库里。
- L3 什么信号出现你会换 Kafka？——消息量上两个数量级、需要回放历史、或要接流式计算的时候。

**雷点**：踩"Kafka 会丢消息"——配置齐全的 Kafka 不丢，差异在语义模型和运维成本，不在可靠性高下。

## 卡 11｜JWT 原理 / 注销 / 和 session 对比

**核心答案**：JWT 三段：b64url 的 header、b64url 的 payload，加 HMAC-SHA256 签名——我们 HS256 手写实现，验签用 CRYPTO_memcmp 常数时间比较，防时序侧信道逐字节猜签名。和 session 比：无状态——签名可本地验、不用每次查 session 存储；我们当前是网关 srpc 调认证服务统一验签加 RBAC，内网一次约 1 毫秒，演进就是网关本地验签、只在权限变更时查服务。代价是注销难、payload 不可变。注销现在靠短 TTL 2 小时自然过期，演进是 Redis 黑名单记 jti 或 refresh token 双令牌。

**三层追问预演**：
- L1 无状态怎么注销？——三档：短 TTL 自然过期（现状）；Redis 黑名单记 jti，验签时多查一次；refresh token 双令牌——短访问令牌加长效刷新令牌。
- L2 secret 泄露怎么办？——轮换 secret，旧 token 全部失效；长期演进是 RS256——私钥签发、公钥验签，多服务场景不用共享秘密。
- L3 权限变更怎么立即生效？——RBAC 矩阵在认证服务端，网关每请求调 Verify 拿最新权限，改矩阵立即生效——这正是权限放服务端不放网关的原因；本地验签演进化要配短 TTL 权限缓存补这个洞。

**雷点**：说"JWT 防篡改所以也防重放"——签名不防重放，要防得靠 HTTPS 加时间戳/nonce；注销答"删掉 token"（服务端根本没存）。

## 卡 12｜TF-IDF 公式 + 为什么不是 BM25

**核心答案**：TF-IDF：词 t 在文档 d 的权重 = 词频 TF × log(总文档数 N / 含该词文档数 df)。IDF 的直觉：越是在大量文档都出现的词越没区分度——"患者"这种高频词权重被压下去，专有术语权重高。我们构建期就算好权重并做 L2 归一化——归一化后余弦相似度退化为点积，查询期省计算；conclusion 字段权重乘 2，是简化版的 field weighting。为什么不是 BM25：BM25 两处改进——词频饱和函数、文档长度归一——是明确演进点；我们选 TF-IDF 是教学最短路径且效果可接受。

**三层追问预演**：
- L1 IDF 为什么用 log？——文档数是乘性增长的，不取 log 的话 IDF 会被总文档数支配、失去"区分度"的相对意义；log 把它压成温和的衰减。
- L2 构建期为什么归一化？——归一化后余弦等于点积：查询向量一次归一化、文档向量构建期归一化，打分就是内积循环——省掉查询期每文档的模长计算。
- L3 查询向量怎么算？查询也做 TF-IDF 吗？——查询分词和索引用同一个 Tokenizer 封装——索引/查询分词不一致是召回劣化的经典根因；查询短，主要靠文档侧权重打分。

**雷点**：公式写不出或 TF、df 说混（TF 是词在该文档的频率，df 是含该词的文档数——两个量纲）；说"BM25 更好所以我们用了"（没用就是没用，讲清演进点比硬贴标签加分）。

## 卡 13｜epoll LT/ET + Reactor 主从模型

**核心答案**：Reactor 是 IO 事件驱动模型：主 loop 只管 accept，新连接轮询分给 4 个 sub loop，每个 loop 一个线程一个 epoll——one loop per thread，连接固定绑定一个 IO 线程，线程内无锁。epoll 对 select 的优势：fd 用红黑树注册一次、就绪事件进就绪链表由内核回调挂上，不用每次调用全量扫描——fd 多且活跃稀疏时优势最大。LT 和 ET：muduo 用 LT——只要缓冲区还有数据就持续通知，编程模型简单、关注写事件的行为一致；ET 只在边沿触发一次，必须循环读到 EAGAIN，否则剩下的数据再也不通知。

**三层追问预演**：
- L1 ET 为什么必须循环读到 EAGAIN？——ET 只通知一次"可读"，读一半剩下的是不会再来通知的——数据滞留；LT 没这个问题，这就是 muduo 选 LT 的理由。
- L2 为什么是 4 个 sub loop？——和核数挂钩：部署机是 4C，IO 密集型事件循环线程数约等于核数就够；再多上下文切换反亏，不够则单 loop 被慢操作拖累更多连接。
- L3 epoll 一定比 select 快吗？——不一定：fd 少且几乎全部活跃时，select 的线性扫描开销很小，epoll 维护红黑树和回调反而多一层成本——epoll 赢在"多而稀疏"的场景。

**雷点**：LT/ET 的语义说反；"4 线程"只说"配置文件里配的"——必须给核数挂钩的定量理由；说"epoll 永远更快"。
