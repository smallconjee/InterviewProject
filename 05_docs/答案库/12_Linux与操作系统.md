## 一、进程 / 线程 / IPC / 信号

### §14.1 进程和线程的区别？协程是什么？🔴

**口语答案**：教科书一句话：进程是资源分配的单位，线程是调度执行的单位。展开讲：进程有独立的虚拟地址空间、文件描述符表、信号处理表——隔离性好，通信要靠 IPC；同一进程内的线程共享地址空间和 fd，各自只有自己的栈、寄存器、errno——通信就是读写共享内存（所以要同步原语），切换成本也低：线程切换只需保存寄存器和换栈指针，进程切换还要换页表、TLB 大面积失效。隔离性 vs 通信成本，是这对概念的核心取舍。协程是**用户态**的轻量执行流：调度器在用户空间（库或编译器 runtime），切换就是保存恢复几个寄存器，不陷入内核、没有系统调用开销，成本纳秒级——比线程切换（微秒级）低一两个数量级；代价是协程不能利用多核（同一线程内串行），阻塞式系统调用会把整条线程卡住，所以要么配非阻塞 IO，要么库替你管。我项目的现成讲点：workflow 号称"协程式"编程——它不是真协程，是用任务串 SeriesWork 加回调把异步代码写成同步的样子（ThriftMessenger 那种"发完 TLV 等回复再写 HTTP 响应"的链路，代码看起来顺序，底层全是异步调度）；真按协程理解的话，RIS 用的 muduo one loop per thread 是另一条路线——固定 IO 线程加事件驱动。两条路线解决同一个问题：怎么在少量线程上跑大量并发等待。

**追问预演**：
- ↳ 线程崩溃为什么整个进程死？→ 默认信号（SIGSEGV）的处置是进程级的——一个线程踩坏内存，内核把信号递给进程，全体退出；这是进程隔离边界的体现。
- ↳ 上下文切换具体切什么？→ 线程：寄存器、栈指针、线程局部存储；进程：以上全部加 CR3 页表基址（TLB 失效是最大隐性成本，除非用 ASID）。

### §14.2 进程间通信方式有哪些？各适用什么场景？🔴

**口语答案**：按"单机内"数下来六种，各有站位：管道——匿名管道 pipe 限父子关系、流式字节流，FIFO 命名管道放开到任意进程；简单但容量小、字节流要自己定界。消息队列——内核维护的消息链表，按条收发有边界，但每条消息过两次内核拷贝，大小有限制。共享内存——两个进程的虚拟地址映射同一块物理内存，**最快**：一旦建好，读写就是普通内存访问，数据零拷贝、不进内核；正因为它只是裸内存，本身没有任何互斥，两个进程同时写就竞争——所以要配信号量或互斥原语做同步，"快"和"要配信号量"是同一枚硬币的两面。信号量——本质是计数同步原语，不是传数据的，专职协调（P 拿配额、V 还配额）。信号——异步事件通知（kill、SIGTERM），带一个编号不带数据（SIGUSR 带实时信号可捎带少量信息），适合"通知发生了"不适合传内容。socket——唯一跨机器的，本机还可以走 Unix domain socket（不走网络栈，更快）。我的项目是分布式视角的 IPC 大合集：PACS 网关和 RIS 之间走自定义 TCP 协议（TLV 帧过 socket）；导入服务和备份消费者之间走 RabbitMQ（跨进程的消息队列，带持久化和可靠投递，比 SysV 消息队列强一个量级）；两级缓存用 Redis（跨进程共享数据）。为什么不用共享内存：我们的进程是跨虚机部署的，共享内存出不了单机；单机内的高频共享（同进程多线程）用 mutex 加原子就够了。

**追问预演**：
- ↳ 共享内存怎么建？→ POSIX shm_open 加 mmap，或 SysV shmget；生命周期要手动清理（/dev/shm 里可见）。
- ↳ 快多少？→ 管道/消息队列一次通信两次拷贝（用户到内核、内核到用户）加系统调用；共享内存建好后的读写零拷贝零系统调用——高频小消息差出数量级，大数据低频差距被数据本身摊薄。

### §14.3 信号处理的坑？信号处理函数里能 printf/加锁吗？🔴（两个真实故事）

**口语答案**：核心概念是 async-signal-safe（异步信号安全）：信号 handler 会在**任意两条指令之间**打断主流程——如果打断时主流程正拿着 stdio 内部锁，handler 里再调 printf 就对同一把锁二次加锁，自死锁；malloc/free、C++ 的锁同理。安全白名单很短：write(2) 这种可重入系统调用。规范姿势：handler 只设置一个 volatile sig_atomic_t 标志，真正的处理（日志、清理、退出）回到主循环做。我两个真实踩坑正好各占一半。第一个是日志乱序：服务日志里 shutdown signal 这行出现在文件**最前面**——原因是信号 handler 用无缓冲的 write(2) 直接输出，而主流程的 INFO 日志还躺在 stdio 缓冲区里没刷——两条输出路径混用，时间序全乱；修法是 handler 只设标志位、由主循环统一打日志（另一条路是接受乱序，把缓冲策略统一）。第二个更狠：备份消费者 SIGTERM 收不掉变僵尸——消费 API 是无限阻塞等待，主循环根本走不到检查退出标志那一步，进程杀不死；最后的修法是 handler 里直接 _exit——这看起来违反"handler 里少做事"的教条，但 _exit 不跑 atexit、不碰 stdio 和锁，是白名单级操作，恰恰是安全的；敢这么粗暴的底气在下游：未 ACK 的消息 broker 会重投，消费端幂等吸收重复——**幂等设计反过来简化了关闭语义**，这是我最喜欢讲的一句。两个故事合起来：教条是"handler 只设标志"，但要理解背后的安全边界，才敢在关闭场景做出"_exit 反而正确"的工程判断。

**追问预演**：
- ↳ 为什么 write 安全 printf 不安全？→ write 是直通内核的系统调用、不依赖用户态锁和缓冲；printf 要拿 stdio 锁、访问共享缓冲区，都是可能被中断时持有的资源。
- ↳ SIGKILL 和 SIGTERM 区别？→ SIGKILL（9）不可捕获不可忽略、进程必死，连清理都不给机会；SIGTERM（15）可捕获做优雅退出——我们要优雅退出才踩了僵尸坑，SIGKILL 根本不给你踩的机会。

## 二、内存与 IO

### §14.4 mmap 是什么？什么时候比 read/write 快？🟡

**口语答案**：mmap 把文件（或匿名内存）映射进进程虚拟地址空间：建立的是"虚拟页到文件页缓存"的映射，第一次访问某页触发缺页，内核把文件页读进 page cache 直接映射给你——之后读写就是普通内存访问，没有系统调用、没有内核态到用户态的显式拷贝。对比 read/write：每次调用都陷入内核、数据从 page cache 拷到用户缓冲（read）或反向（write），高频小 IO 的开销全在切换和拷贝上。mmap 什么时候赢：**随机访问**大文件（按需缺页，不用预读整个文件）、**反复访问**（页常驻后零成本）、**多进程共享**同一份映射（映射同一文件即共享同一物理页，省一份内存）。什么时候不赢：顺序读大文件——read 加内核预读已经很高效，mmap 建映射、缺页的管理开销反而多余；小文件也不划算（映射的最小粒度是页，还要 munmap）。注意点：mmap 不是免检的——脏页靠内核回写或显式 msync，映射泄漏（忘了 munmap）就是虚拟地址空间泄漏。我项目里这是明确的演进项：RIS 索引加载现在是把版本目录整个读进内存构造 unordered_map（80 万文档约 2GB），进程冷启动和版本切换都要付这份构建成本；演进方向是索引直接序列化成 mmap 友好的布局（词典按序数组加定长倒排段），加载退化为一次 mmap——缺页按需、切换成本从"分钟级构建"降到"毫秒级映射"，冷启动扛得住重启风暴。

**追问预演**：
- ↳ mmap 和共享内存什么关系？→ 匿名 mmap 共享 MAP_SHARED 就是共享内存的实现之一；文件 mmap 额外有页缓存和回写语义。
- ↳ 缺页异常对延迟的影响？→ 首次访问每页一次缺页（软缺页，微秒级），对延迟敏感路径要 madvise 预热或 willneed——这也是 mmap 方案要评估的点。

### §14.5 零拷贝了解吗？sendfile/splice/writev 🟡

**口语答案**：先摆传统路径的账：把文件内容发到网络，read 加 write——数据要拷四次（磁盘到页缓存 DMA、页缓存到用户缓冲、用户缓冲到 socket 缓冲、socket 到网卡 DMA），系统调用两次、用户态内核态切换四次，其中第二三两次 CPU 拷贝和中间那块用户缓冲完全是"路过"。零拷贝家族就是把中间路过砍掉：sendfile——文件直接送 socket，数据不进用户空间，配 DMA gather（网卡自己按描述符取页缓存数据）连 CPU 拷贝都能归零，静态文件下发/消息中间件刷盘都用它；splice——借管道缓冲区在两个 fd 之间"搬页引用"，不拷数据，适合任意两个 fd 间流转；writev——严格说是"少拷贝"：多个分散缓冲**一次系统调用**发出（聚集写），省的是调用次数和"先拼成一个大缓冲"的那次拷贝，TLS 加密场景还有 sendfile 用不了的补充优势。我项目的直接用例：RIS 的 TLV 编码用两个 iovec——6 字节帧头一个、payload 一个，writev（workflow 内部走聚集写）一次发出，payload 从来不被 memcpy 拼进连续大缓冲；这对大响应（Top10 结果几 KB）是实打实的节约，也是"零拷贝思想在日常代码里的落地"——不一定是系统调用级零拷贝，但"数据在内存里多搬一次都是浪费"是同一个意识。

**追问预演**：
- ↳ 我们能用 sendfile 吗？→ 协议是 TLV 二进制不是裸文件，且有鉴权加密需求——sendfile 的适用面是"文件原样下发"；影像文件如果做静态分发网关，nginx 侧天然在用。
- ↳ 直接 IO（O_DIRECT）和零拷贝关系？→ 正交：O_DIRECT 绕过页缓存（数据库自己管缓存，如 InnoDB），零拷贝讲的是路径中拷贝次数——别混成一个概念。

### §14.6 用户态和内核态什么时候切换？成本在哪？🟡

**口语答案**：切换的三个入口：系统调用（主动）、中断（硬件打断，网卡包到了、时钟到了）、异常（缺页、除零）。成本拆三层：最直接的是模式切换本身——保存恢复寄存器、切栈、权限切换，现代 CPU 加上 Spectre/Meltdown 缓解后陷入返回贵了不少；第二层是间接污染——内核代码会踩脏 cache 和 TLB，切回用户态后原热点数据全凉了；第三层是系统调用语义带来的——如果每次调用还伴随 fd 集拷贝（select）或数据拷贝（read/write），那才是大头。所以优化的思路全是"减少次数、批量做"：stdio 缓冲攒一批再 write（我们日志"整行一次 fwrite"顺带吃到这个红利）、writev 聚集写、epoll 一次等待一批 fd（对比 select 每次把整个 fd 集拷进内核）、mmap 免掉读的系统调用。判断是不是瓶颈看数据：strace -c 统计调用次数和耗时分布，sys 占比高的进程就是"切换病"。

**追问预演**：
- ↳ 缺页也是切换，为什么 mmap 反而快？→ 它把"每次访问一次拷贝加调用"换成"每页一次缺页"，页粒度 4KB 摊薄后远小于逐次 read——批量化在页的维度发生。
- ↳ vDSO 是什么？→ 内核把 gettimeofday 这类只读操作映射进用户态执行，不陷入内核——"消灭系统调用"的极端手段，时钟读取零成本。

### §14.7 虚拟内存 / 页表 / 缺页中断的流程？🟡

**口语答案**：每个进程拿到的是一整段连续的虚拟地址空间，按页（一般 4KB）为单位映射到物理内存或文件或"暂不存在"。地址翻译由 MMU 完成： walks 多级页表（x86-64 常见四级：PGD、PUD、PMD、PTE），每级取虚拟地址的一段做索引，页表基址在 CR3；translation 先查 TLB——页表项的硬件缓存，命中就直接出物理地址，不命中才走页表。缺页中断的流程：TLB miss、查页表发现 PTE 无效（页不在内存或无权限），CPU 触发 page fault 陷入内核；内核查该地址所在的 VMA（进程的虚拟内存区域描述）——**不合法**（没映射的野指针地址）就给进程发 SIGSEGV，段错误就是这来的；**合法但未调入**就补上：匿名页分配物理页清零，文件映射页从文件读入 page cache，填好 PTE，返回用户态重新执行那条指令——所以缺页是"透明的按需加载"，不是错误。这个机制上还搭着两个重要玩法：写时复制 COW——fork 后父子共享物理页标只读，谁写谁缺页，内核拷一份再放行，这是 fork 快和 Redis bgsave 的基础；内存映射文件，就是上一题的 mmap。我项目关联：进程 RSS 的控制（索引 2GB 对 8G 虚机的预算管理）、mmap 演进方案，底层都是这套按需分页。

**追问预演**：
- ↳ 为什么多级页表省内存？→ 单级页表要为整个地址空间每页建表项（哪怕没用）；多级允许"没分配的区间连中间层都不建"，稀疏地址空间下指数级省。
- ↳ 大页/THP 是什么？→ 2MB 或 1GB 的页，TLB 一项覆盖更大范围，减少缺页和 TLB miss——对大内存索引类负载有感；代价是内部碎片和迁移开销。

### §14.8 rename(2) 为什么是原子的？🟡（staging 设计的地基）

**口语答案**：rename 做的事：在目标目录里创建一个新目录项指向**同一个 inode**，再删掉旧目录项——文件内容、权限、数据块一个都没动，动的只是"名字到 inode 的映射"这笔元数据。现代文件系统（ext4/xfs）对目录项修改走日志（journal）：改名作为单个事务提交，崩溃后要么两个可见性状态之一——旧名字在或新名字在，**不存在半个名字、也不存在指向半截数据的新名字**；对并发观察者来说这就是原子瞬间。两个边界：一是跨文件系统 rename 直接报 EXDEV 失败——不同文件系统 inode 编号体系独立，没法只改目录项；二是它原子的是"名字切换"，不保证新内容已经 fsync 落盘——要崩溃安全还得对文件本身 fsync 后再 rename。我项目把它当归档链的地基用：DICOM 对象先写进**同目录**下的 staging 临时文件（慢操作，写几百 MB 都行，崩了就崩了，重启扫描清掉半截文件），全部写完、哈希算完，最后一步 rename 成最终路径——对外可见的那一刻就是"完整、已校验"的对象；staging 必须和最终对象同文件系统（放 /tmp 是经典错误，tmp 很可能独立挂载，rename 直接 EXDEV）。数据库双事务的"事务一提交后、rename 前崩溃"窗口也靠这套语义兜底：重启后要么 staging 还在（重新 rename），要么对象已就位（状态机续传）。

**追问预演**：
- ↳ 和"写临时文件再 cp 覆盖"什么区别？→ cp 覆盖是"先截断目标再逐块写"——中间任何时刻读者都看到半截文件；rename 是目录项切换，读者要么旧要么新。
- ↳ 这个模式还有什么名字？→ "原子写换"模式：配置热更新、索引双版本目录切换、AOF 重写改名，全是同一招——写新、校验、原子换名。

## 三、工具与排障（简历点名 GDB/Wireshark）

### §14.9 gdb 怎么调多线程？怎么看死锁？core dump 怎么分析？🟡

**口语答案**：多线程三板斧：info threads 列出所有线程（带当前停点），thread n 切到目标，thread apply all bt 一次打全所有线程栈——这是排障第一招，死锁现场全靠它。看死锁的判读法：thread apply all bt 的输出里找两个以上栈顶停在 __lll_lock_wait / __pthread 的线程，再用 p *(pthread_mutex_t*)&mutex 打印锁对象，看 __data.__owner（持有者的线程 LWP 号）——A 等的锁 owner 是 B、B 等的锁 owner 是 A，交叉互等，实锤。配合 set scheduler-locking on 可以锁定单线程单步，别的线程不抢跑（记得调试完关掉）。core dump 是崩溃瞬间的进程快照：先保证产物——ulimit -c unlimited（容器里要显式配）、内核 core_pattern 指定落盘路径和命名（接 systemd-coredump 或直接文件），二进制要带 -g 符号且别 strip；分析流程：gdb ./bin core 进去，bt 看崩溃栈、frame n 进帧、info locals 看变量、info registers 加 x 看内存——对照源码行号定位。我的实践环境：开发容器开了 SYS_PTRACE，VS Code 的 launch.json 配 gdb 调试两个服务；离线快速抓现场用 pstack（就是 attach 的 thread apply all bt）不打断服务先拍照。真实调过的例子是 muduo 在 ARM64 容器编不过那个 static_assert——虽然那是编译期问题，但"读报错、查 ABI 差异、最小修复"的路径和运行期排障是同一套功夫。

**追问预演**：
- ↳ 线上不能 attach（秒级卡顿）怎么办？→ pstack/gcore 抓快照立即detach，回线下分析；再不行靠日志时间线。gcore 就是"手动产 core"。
- ↳ release 版没符号怎么调？→ 从构建产物还原：保留带符号的版本对照（addr2line 或 symbol server 思路）；所以 CI 产物要存符号——工程习惯问题。

### §14.10 Wireshark 抓包抓过什么？🟡（备一个小故事）

**口语答案**：抓包是我排网络问题的第一现场，讲一个和项目直接相关的：调 RIS 的 TLV 粘包/半包逻辑时，我写了个测试客户端把一帧拆成三段 send 模拟半包，同时在服务端机器 tcpdump 抓 9090 端口、导出 pcap 用 Wireshark 看——过滤器 tcp.port == 9090，Follow TCP Stream 把整条字节流拉出来对着帧格式 [type][flags][len] 一个字节一个字节对：三段报文各自到达的时间、每次到达服务端解码器返回 PARTIAL 的日志、第三段到齐才完整解出一帧——协议层的行为和 tcp 层的交付完全对上，解码器的状态机就是这么验证的。这套观察顺带看到的基础现象也能讲：连接建立的三次握手 SYN/SYN+ACK/ACK、断开的 FIN 四次交互、偶发的 RST（比如服务端 TOO_LONG 主动断连，抓包里就是一个 RST 而不是 FIN——和我们主动 shutdown 的实现互相印证）。Wireshark 的日常技巧就三条：捕获过滤器（tcpdump 语法，抓的时候过滤）和显示过滤器（wireshark 语法，看的时候过滤）分清；Follow Stream 看单条连接的完整故事；IO Graphs 看时间轴上的流量突变定位卡顿时刻。

**追问预演**：
- ↳ 抓包看到大量重传说明什么？→ 丢包或拥塞——内网一般是 buffer 溢出或网卡速率不匹配；结合 ss -i 看重传统计分清"谁的问题"。
- ↳ 内网明文传输有什么风险？→ 内网不等于可信网（医疗内网有大量第三方设备）；我们的 TLV 是明文，安全演进是 TLS 加固或至少把认证令牌放加密通道——诚实讲现状加演进。

### §14.11 CPU 100% / 内存泄漏，线上怎么一步步排查？🟡

**口语答案**：CPU 100% 的路径，每步一个工具：top 找到吃 CPU 的**进程**；top -Hp <pid> 切到线程视图找到吃 CPU 的**线程**，记下线程号转十六进制；两个方向定性——strace -p 或 -c 看它是不是在系统调用里打转（空转 EAGAIN、锁自旋在 futex），perf top / perf record -g 采样看用户态热点函数（火焰图更直观）；对不上再 jstack/gdb 对线程号看栈。C++ 服务的高频病因清单：正则回溯爆炸、日志同步刷盘打满、锁竞争自旋、死循环 bug（我们解码器收到非法帧直接断连就是防"坏输入打进死循环"的例子）。内存泄漏的路径：先确认"是不是泄漏"——top/ps 看 RSS 趋势，对比 /proc/<pid>/status 的 VmRSS 和 smaps（看是堆涨还是 mmap 涨、哪个段在涨）；增长模式定位嫌疑对象（连接涨=句柄泄漏可 ls /proc/<pid>/fd 数一下、缓存涨=容器无界、索引切换后旧版本没释放=shared_ptr 泄漏）；测试环境用 valgrind 或 ASan 跑复现路径拿 definitive lost 的分配栈；线上止血是重启加保留 core/日志现场。预防重于排查：关键结构加容量上限（LruCache 512 条就是上限思维）、版本切换的引用计数靠 shared_ptr 自动回收、长事务和长连接都有超时——我项目里 acquire 3 秒超时、Redis 2 秒超时、帧长 1MB 上限，全是"病发时止损"的预埋。

**追问预演**：
- ↳ perf 和 strace 怎么选？→ strace 看系统调用（判断"卡在哪类操作"），perf 看热点（判断"哪段代码在烧 CPU"）——前者定性场景，后者定位代码。
- ↳ 内存涨但 valgrind 查不出泄漏？→ 多半是"逻辑泄漏"（容器只增不减、碎片化、配置就是吃这么多）——leaky 和 wasteful 要分开定性。

### §14.12 load average 是什么？和 CPU 使用率的区别？🟡

**口语答案**：load average 是最近 1、5、15 分钟内，**可运行加不可中断睡眠**的平均任务数——Linux 特有的把 D 状态（通常是等磁盘 IO）也算进去了。它回答"排队的人多不多"，CPU 使用率回答"服务员忙不忙"——两个指标交叉出三种经典读法：load 高、CPU 也高——真算力瓶颈，加核或优化计算；load 高、CPU 低——大概率 IO 瓶颈，大量任务卡在 D 状态等盘，去看 iostat 和磁盘队列；load 低、CPU 高——少数线程空转（自旋锁）或单核打满（单线程瓶颈），负载还没排起队。经验刻度：load 接近核数（我们虚机 4C）算满载，持续超过核数就是排队。和我们生产 4C8G 虚机对应：load 持续 4 以上就该查了。再往上一层是我的业务视角：这套"通用负载指标"之外，我们自建了两个业务级"load"——消息表堆积数和队列深度，每日巡检、积压超 2 万且持续 1 小时告警——机器指标正常但业务在堆积的故障（比如那次 OSS 限流、消费吞吐掉到 3 任务/秒），load average 是看不出来的，监控必须打到业务语义这一层。

**追问预演**：
- ↳ D 状态进程为什么算进 load？→ Linux 的立场：它们在等资源也算"待办负载"——IO 慢的时候系统确实过载，只是瓶颈不在 CPU；这也提醒 load 高先分诊再用药。
- ↳ 什么工具组合看全貌？→ top/load 看全局、vmstat 看 r 列和上下文切换、iostat 看盘、pidstat 按进程拆——四件套齐了瓶颈归属基本清楚。
