## 一、muduo / Reactor / epoll

### §8.1 Reactor 模式讲一下？one loop per thread 是什么意思？🔴

**口语答案**：Reactor 是事件分发模型：线程不阻塞在某一个连接的 read 上，而是把所有连接的 fd 都注册给 epoll，事件来了内核通知谁就绪，回调处理谁——"等 IO"这件事统一外包给了多路复用器。one loop per thread 是 muduo 的线程模型：一个线程配一个 EventLoop、也就是一个 epoll 实例，一条连接从建立到关闭固定归属一个 loop，同一 loop 上的回调天然串行，所以连接内部操作不用加锁。我们是主从 Reactor：主 loop 只跑 Acceptor 负责 accept 新连接，setThreadNum(4) 起的 4 个 sub loop 负责已建连接的读写和业务回调；新连接由 EventLoopThreadPool 轮询分配到 sub loop，负载摊平。这个模型的好处就是无锁化和连接均衡。

**追问预演**：
- ↳ 为什么主 loop 不顺便处理 IO？→ accept 和 IO 分离后，慢的回调只拖住自己 loop 上的连接，新连接接入永远有人应答。
- ↳ 单 Reactor 多线程和主从 Reactor 的区别？→ 前者一个 epoll 加worker 线程池，锁竞争在共享就绪队列；主从把连接分片到各 loop，锁竞争消失——muduo 选了后者。

### §8.2 💣 为什么线程数是 4？怎么定的？🔴💣

**口语答案**：这个数可以从三个量推出来：部署规格、负载模型、单查询耗时。第一，生产是 4C8G 虚机，IO 线程兼做检索属于计算加 IO 混合型，线程数先对齐核数量级，开多了是上下文切换白花钱；第二，峰值 20 QPS、单查询 P99 80ms，同时在飞的请求约 20 × 0.08 = 1.6 个，单线程串行处理能力约 12 QPS，4 线程理论上限 50 QPS，对峰值留了 2.5 倍余量；第三，~200 条长连接摊到 4 个 loop，每 loop 50 条，对 epoll 是零压力。三个量交叉验证出来 4 够用且不浪费。诚实讲一个改进点：setThreadNum 目前是硬编码，应该进配置文件随部署规格调。

**追问预演**：
- ↳ 流量涨 10 倍你先动哪里？→ 先把检索挪进业务线程池（IO 线程回归纯编解码，见 §8.13），IO 线程数反而可以降；然后 RIS 水平扩实例共享 L2 缓存。
- ↳ 线程数等于核数一定对吗？→ 纯计算型是的；IO 密集型可以按核数 ×（1 + 等待/计算）放大，但受部署预算约束，先量后调。

**雷点**：千万别说"配置里就这么写的"——这题考的就是定量推导。

### §8.3 epoll 和 select/poll 的区别？🔴

**口语答案**：三者都是 IO 多路复用，差距在 fd 数量和扫描成本。select 用固定 fd_set 位图，每次调用把整个集合拷进内核、返回后再线性扫一遍找就绪的，还有 FD_SETSIZE 1024 的硬上限；poll 换成数组摆脱了 1024，但每次全量拷贝加 O(n) 扫描没变；epoll 把注册和等待拆开——epoll_ctl 增删改一次注册进内核红黑树，fd 就绪时由内核回调把它挂到就绪链表，epoll_wait 只拷贝就绪的那部分，成本是 O(活跃 fd) 而不是 O(总 fd)。我们场景是 200 条长连接、低比例活跃，正是 epoll 的主场。但 epoll 不是永远快：fd 少且几乎全部活跃时，select 一把梭也扫得动，epoll 反而多一层内核调用，差距主要在"连接多、活跃占比低"时拉开。

**追问预演**：
- ↳ LT 和 ET 的区别？muduo 用哪个？→ LT 只要缓冲区还有数据每次 wait 都通知；ET 只在状态从无到有翻转时通知一次。muduo 用 LT：编程模型简单、不用怕漏读，写事件语义也一致。
- ↳ ET 为什么必须循环读到 EAGAIN？→ ET 只通知一次，读一半剩下的留在内核缓冲区就再也没有通知了，数据活活饿死——必须一次 drain 干净，读到返回 EAGAIN 为止。
- ↳ epoll 底层怎么实现？→ 三个部件：红黑树管理 fd（ctl 增删改）、就绪链表（事件回调把 fd 挂上去）、wait 只在链表上取；回调挂链的活是驱动中断触发的。

### §8.4 muduo 为什么要设计应用层 Buffer？🔴

**口语答案**：因为内核只给你字节流，应用需要"消息"和"速率差"的缓冲。读方向：一次 read 不保证是完整帧，得攒到够；写方向：对端收得慢时 socket 发送缓冲会满，写不完的数据得在用户态暂存。muduo Buffer 的结构是一个 vector 加 readIndex、writeIndex 两个游标，头部还预留了 prependable 空间——以后往数据前面插长度头不用搬移整个缓冲。读用 readv 配 64KB 栈上 extrabuf 尽量一次读净，LT 模式下既减少系统调用又不至于无限扩容；写是先尝试直接 write，写不完挪 outputBuffer 并注册 EPOLLOUT，写完立刻取消关注。对端一直不收，outputBuffer 就涨内存，muduo 有 highWaterMark 回调可以做告警或主动断连自我保护。我们这边 Buffer 和 TLV 解码器的衔接是：onMessage 里 retrieveAllAsString 整段喂给解码器，半帧留在解码器自己的缓冲里等下一波。

**追问预演**：
- ↳ 为什么用 readv 加栈上缓冲？→ 一次系统调用把内核数据尽量搬空，避免"读了一点、下次再触发"的往返开销。
- ↳ 为什么头部要预留空间？→ prependable——协议加长度前缀这类"后算出来要放前面"的字段可以直接在头部插，不用整体 memmove。

### §8.5 muduo 的 send 从别的线程调用安全吗？🟡

**口语答案**：安全，这是 muduo 设计好的：TcpConnection::send 进来先判断当前线程是不是这条连接所属的 IO 线程，是就直接写；不是就 runInLoop 把写操作投递回所属 loop 的队列，由它在自己的线程里执行——所有对这条连接的操作最终都串行在同一个 loop 上，无锁但线程安全。这个性质也是我们后面演进方案的底气：把检索挪到业务线程池后，worker 算完结果直接 conn->send 回写，不需要自己加锁，框架自动转交回 IO 线程。

**追问预演**：
- ↳ runInLoop 和 queueInLoop 区别？→ runInLoop 在调用线程就是本 loop 线程时立即执行，否则投递；queueInLoop 无条件投递（经 eventfd/wakeup 唤醒目标 loop）。
- ↳ 为什么不直接给 TcpConnection 加锁？→ 一个连接的 fd 操作加锁粒度太粗且到处是锁；把操作"挪回同一个线程"是无锁化的标准手法。

### §8.6 TcpConnection 的生命周期怎么管理的？🟡

**口语答案**：shared_ptr 管理，TcpConnection 继承 enable_shared_from_this。TcpServer 有一个 connections_ 的 map 持有所有连接的 shared_ptr；连接关闭时不直接 delete，而是从 map erase、再通过 queueInLoop 把最后的清理动作排回 IO 线程，保证正在执行的回调期间对象一定活着，最后一个 shared_ptr 析构时连接对象才真正释放——不会出现回调跑到一半对象没了的悬垂。我们自己的连接级状态也是配合这个模型设计的：TLV 解码器按连接名挂在 map 里，连接建立创建、断开 erase，半帧缓冲随连接一起消失。一个可以说的改进点：muduo 其实提供 conn->setContext 挂连接级数据，就不用我们自己维护 map 加锁了。

**追问预演**：
- ↳ 为什么用 shared_ptr 不用裸指针？→ 关闭时序不确定（对端断、本端关、定时器到期），引用计数把"谁最后用完谁释放"自动化。
- ↳ enable_shared_from_this 干什么的？→ 让对象在自己的成员函数里安全拿到自己的 shared_ptr（share_from_this），避免"栈上或裸指针管理的对象被两个 shared_ptr 各自计数"。

## 二、TLV 协议 / 粘包半包

### §8.7 "TCP 是字节流没有消息边界"——这句话对你的设计意味着什么？🔴

**口语答案**：意味着"消息"是应用层概念，内核不承诺任何边界：客户端两次 write，服务端可能一次 read 全收到——粘包；一次 write 的数据可能分两三次到达——半包，中间还可能被 MTU 分片、被 Nagle 合并。所以应用必须自己定义帧边界、并且用增量方式解析——这就是我们 TLV 协议存在的原因：定长 6 字节头带 4 字节长度字段，解析逻辑是不动状态的增量状态机，数据不够就等，够了就取帧。反过来说，任何"一次 recv 就当一条完整消息处理"的代码，在测试环境碰巧能跑，上量必炸——这是网络编程的第一课。

**追问预演**：
- ↳ 粘包是 TCP 的 bug 吗？→ 不是，TCP 本来就是流协议，"包"是应用层的想象；要消息语义就上应用层协议。
- ↳ UDP 有这个问题吗？→ 没有，UDP 是数据报语义，有边界，但要自己处理丢包乱序。

### §8.8 粘包/半包怎么处理的？🔴

**口语答案**：长度前缀加增量解码器。解码器内部一个缓冲区，onMessage 把收到的字节 feed 进去，然后循环 decode：先看攒没攒够 6 字节帧头，不够返回 PARTIAL 等下次；够了读出 type 和长度，先校验类型合法、长度不超 1MB，再看体到没到齐，不到齐继续 PARTIAL；到齐就把这一帧取走、从缓冲 erase 掉消费，剩余字节留给下一帧，外层 for 循环直到 PARTIAL 或出错。所以一次 onMessage 收到两个半帧，就是循环解出两帧剩半个尾巴；客户端把一帧拆成三段 send，解码器就攒三次数据拼出一帧——我们有三段拼帧的专项测试验证过。这个设计的要点是解码器必须每连接一个实例：缓冲里的半帧是连接级状态，全局共享一个解码器，A 连接的半帧会和 B 连接的数据拼在一起，直接串流。

**追问预演**：
- ↳ 解码器放全局成员会怎样？→ 不同连接的字节流混进同一个缓冲，帧错位、结果串台——所以按连接名挂 map，断开时 erase。
- ↳ erase 消费为什么不用两个游标？→ std::string 的实现简单，帧头一次性 erase；性能敏感可以换成 readIndex 游标避免搬移，量级不大先不优化。

**雷点**：别说"muduo 帮我处理了粘包"——muduo 只给 Buffer，帧边界是应用的事。

### §8.9 帧格式 [type:1B][flags:1B][len:4B] 为什么这么设计？🔴

**口语答案**：这是"定长头加变长体"的长度前缀法。type 1 字节，目前五个取值（搜索请求/响应、建议请求/响应、错误），够用且留了扩展空间；flags 1 字节保留置 0，是给演进准备的——版本协商、压缩、加密都可以占一位，向后兼容；len 用 4 字节网络字节序，2 字节 64KB 上限对长查询太紧，4 字节理论 4GB 又过大，所以配了 1MB 的主动上限做内存保护：客户端谎报 2GB 长度，解码器在分配任何东西之前就撞上 MAX_FRAME_PAYLOAD 检查，返回 TOO_LONG 错误帧并断连——先校验后分配，不真去攒 2GB。网络字节序是大端，这是网络协议的统一约定，跨平台唯一正确选择；x86、ARM 都是小端机，长度字段直接 memcpy 整读会把字节序读反，必须逐字节拼或用 ntohl。

**追问预演**：
- ↳ htonl/ntohl 做了什么？怎么判断机器字节序？→ host 与 network 字节序互转，小端机上做字节翻转；判断用联合体取 int 首字节，或编译期 __BYTE_ORDER__ 宏。
- ↳ 为什么校验顺序是先 type 后长度？→ type 非法不需要知道长度就能裁决断连；长度检查只在 type 合法后才有意义（见 §8.10）。
- ↳ 1MB 怎么定的？→ 查询串和 Top10 结果 JSON 都远小于它，留一个数量级余量；再大就该换分片或压缩了。

### §8.10 非法帧类型为什么断连而不是跳过这个帧？🔴

**口语答案**：因为流同步已经丢了。长度前缀协议里，定位下一帧起点完全依赖当前帧的长度字段；type 非法意味着这个帧根本不遵守我们的协议，它的长度字段不可信——你不知道该跳多少字节才能对齐下一帧。跳过等于拿垃圾当边界去猜，后面每一帧都会连环错。有分隔符的协议不一样，比如 HTTP 可以扫 \r\n\r\n 重新同步；长度前缀协议失去同步后唯一安全的做法就是回错误帧、断连，让客户端重连重来。超长帧同理。这个决策的本质是：流式协议的错误处理，宁可牺牲这条连接，不能赌整条流。

**追问预演**：
- ↳ 会不会误伤正常客户端？→ type 白名单是协议契约，正常实现不会发白名单外的值；误伤的只可能是 bug 实现或恶意流量，都应该断。
- ↳ 断连前为什么还回一个 ERROR 帧？→ 给客户端一个明确的死因，比静默断开好排查——错误处理也要可观测。

### §8.11 为什么不用 HTTP / JSON 行 / protobuf 长度前缀帧？🟡

**口语答案**：场景是内网常驻服务、长连接、高频短请求。HTTP 头动辄几百字节，我们帧头 6 字节，检索请求 payload 就十几个字节，协议开销占比完全不可接受，还要处理 keep-alive、chunked 这些复杂度；JSON 行按换行分帧，payload 里带换行就要转义、二进制不安全、解析还得逐字节扫分隔符；protobuf 长度前缀帧其实和 TLV 同构（也是定长头加变长体），但我们的查询就是一段 UTF-8 文本，强类型 schema 收益低，TLV 肉眼可调试——tcpdump 抓包直接看得出 type，排查成本低。如果接口复杂到多字段结构化，protobuf 那套是明确的演进方向。

**追问预演**：
- ↳ HTTP/2 或 WebSocket 行不行？→ 行但重：内网自研服务不需要一套通用协议的兼容包袱，自定义 TLV 200 行代码全掌控。
- ↳ 自定义协议的代价？→ 没有现成生态（抓包插件、压测工具），好在浏览器侧有 PACS 网关做协议桥接，不直面外部客户端。

### §8.12 协议怎么演进加字段？🟡

**口语答案**：三条路，按成本排序。第一是 flags 位：1 字节 8 个位全是保留的，bit0 做版本协商、bit1 压缩标记、bit2 加密标记，老端看到不认识的位按 0 处理，行为向后兼容；第二是 type 枚举扩容：256 个取值才用了 5 个，新功能加新 type 就行，比如以后加 PING/PONG 心跳帧、订阅推送帧；第三才是版本号字段——那要动帧头布局，需要握手协商，当前量级不值得。原则就一条：演进能力在协议设计期就留好（flags 不是白占字节的），事后改帧结构是最贵的方案。

**追问预演**：
- ↳ 删除一个 type 行不行？→ 谨慎——老客户端还在发；正确姿势是先双端兼容观察流量归零，再删。
- ↳ 帧头要不要加校验和？→ 内网可靠性高，TCP 自带校验；真要防应用层错误，先加 CRC 到 flags 位约定的扩展里。

## 三、代码级深挖（看代码的面试官会问到这层）

### §8.13 💣⚠️ 检索、Redis、MySQL 都跑在 IO 线程的 onMessage 里——一个慢查询会不会拖住整个 loop？怎么改？🔴💣

**口语答案**：会，这是我知道的这版实现最大的技术债，我不回避，分"现状为什么能接受"和"怎么改"讲。现状：do_search 内联在 onMessage 里，L1、L2、倒排检索、has_image 的 MySQL 关联查询全部在 IO 线程同步执行。当时可接受的边界是量级：峰值 20 QPS 的长连接低频查询，单查询 P99 80ms、L1 命中 5ms，每个 loop 同时在飞的查询不到 1 个——偶发慢查询影响的只是同一个 loop 上其他连接的排队延迟，而 200 条连接摊到 4 个 loop，每 loop 才 50 条。真正的风险在依赖的外部调用超时：Redis 设了 2 秒超时，MySQL 连接超时 2 秒——最坏组合下，Redis 挂一次拖 2 秒，MySQL 挂时每条命中结果都触发一次 2 秒的重连尝试、10 条命中就是 20 秒，这个量级拖住 loop 就是事故。所以演进方案很明确：第一步，onMessage 解出完整帧后把连接指针加查询词打包，投递到固定 worker 的业务线程池，worker 算完直接 conn->send 回写——send 是线程安全的，runInLoop 自动转回 IO 线程，IO 线程回归纯编解码；过渡期最简版是 runInLoop 投递到一个独立的计算 loop。配套还要做超时预算收敛：外部依赖超时压到几百毫秒，has_image 从逐条查询改批量 IN 查询。量级一上来这是第一个要动的地方。

**追问预演**：
- ↳ Redis 2s 超时，最坏这个 loop 卡多久？→ 单次约 2 秒，期间该 loop 上所有连接的读写都排队；叠加 MySQL 场景最坏 20 秒量级——所以要么改线程池、要么砍超时预算，两个都做。
- ↳ 投递到线程池，连接断开怎么办？→ conn 是 shared_ptr，worker 持有期间对象活着；send 到已断连接返回 -1 被框架忽略，无泄漏。
- ↳ 为什么不直接加 IO 线程数？→ 治标不治本：慢在同步等外部依赖，不在 CPU；线程加到 8 个只是把 20 秒摊薄成 10 秒，结构性问题要结构性解。

**雷点**：别硬拗"毫秒级所以没问题"——面试官问这题就是想听你算最坏情况并给出演进方案。

### §8.14 💣⚠️ RedisCache 被多个 IO 线程并发调用，hiredis 上下文线程安全吗？🔴💣

**口语答案**：hiredis 的同步上下文 redisContext 不是线程安全的，而我们的 RedisCache 被 4 个 IO 线程并发调用——每条连接的 onMessage 到 do_search 都会走到 redis get/setex。这个问题我们真实处理过：早期版本注释里声称线程安全但实现里没有锁，review 时发现，修法是给 get 和 setex 整体加 mutex，锁住包含网络往返的临界区。为什么"锁住整个网络调用"可以接受：临界区是一次内网 Redis 往返，约 1 毫秒量级；峰值 20 QPS、其中缓存写入只发生在 miss 时，锁的占用率是个位数百分比，串行化根本不是瓶颈——用粗粒度换简单正确，量级摆在这。演进路径也清晰：每 IO 线程一条独立连接彻底消除共享，或者一个小连接池，再往后是 hiredis 异步 API。顺带一个对比：同项目里 LruCache 也有一把 mutex，但它的临界区是纯内存操作、百纳秒级——两个组件的锁策略差异本身就是锁粒度与临界区性质的讲点。

**追问预演**：
- ↳ 为什么不直接每线程一个连接？→ 现在量级锁开销可忽略，先保持简单；连接数和重连管理是新增复杂度，等量级需要再上。
- ↳ Redis 挂了会怎样？→ 连接失败静默降级直查索引，只 WARN 一次防刷屏——缓存是加速器不是依赖。

**雷点**：别说"加了锁肯定有性能问题"——要拿占用率数字说话（20 QPS × 1ms ≈ 2% 占用）。

### §8.14b StudyLink 为什么单连接加互斥锁？锁会不会成为瓶颈？🟡💣

**口语答案**：StudyLink 是查 pacs_db 判断报告有没有关联影像的功能，用的是单条 MySQL 连接加一把互斥锁。原因就是频率：它只在缓存 miss 且结果带 UID 时逐条发生，峰值 20 QPS 乘 30% miss 乘每结果 10 条，约每秒 60 次，内网单查 1 毫秒左右，单连接串行占用率 6% 上下——上连接池的收益是个位数百分比，却要付出保活、借还、池管理的复杂度，不值当。锁会不会瓶颈：算占用就行，60 × 1ms = 6%，离饱和远。真正的问题不在锁，在于它也在 IO 线程路径上（承上一题）；演进是两个动作：换读连接池，以及把逐条 exists 改成一次 IN 批量查 10 个 UID——后者收益比前者还大。

**追问预演**：
- ↳ 连接断了怎么恢复？→ ensure 懒重连：下次调用发现连接为空就重建，失败降级 has_image=false，不阻塞检索。
- ↳ 60 次/秒的推导链再顺一遍？→ 峰值 20 QPS × 缓存 miss 率 30% × 每次结果 10 条命中 = 60 次关联查询/秒。

### §8.15 连接断开时解码器怎么清理的？🟡

**口语答案**：解码器按连接名挂在一个 map 里，onConnection 的断开分支在锁内 erase——shared_ptr 引用计数归零，解码器对象连同缓冲里残留的半帧一起析构，无泄漏。两个实现细节：一是 map 的 mutex 只保护 map 结构本身，因为 4 个 IO 线程都会增删查；onMessage 里是先在锁内把 shared_ptr 拷出来再 feed 解码，不在持锁状态下做重活。二是 muduo 本身保证同一条连接的回调固定在同一条 IO 线程，所以解码器对象内部不需要再加锁——连接级状态跟着连接走、线程归属跟着 loop 走，两个确定性叠加，清理就是一次 erase 的事。

**追问预演**：
- ↳ 为什么不挂在 TcpConnection 的 context 上？→ 可以，conn->setContext 是 muduo 的原生做法，还能省掉 map 和锁——这是我知道的改进点，当前独立 map 是最初实现。
- ↳ map 的 key 为什么用连接名？→ muduo 连接名唯一（ip:port:序号），天然可用作键。

### §8.16 JSON 是手拼的，为什么不用库？转义漏了会怎样？🟡

**口语答案**：因为响应字段少、全部是我们自己生成的字符串和数字，json_escape 十来行就把双引号、反斜杠、换行转了、控制字符替换成空格，引 rapidjson 或 nlohmann 的收益撑不起新增依赖。漏了转义的后果：值里带双引号会把字段截断，更糟的是攻击者可以注入额外的 JSON 字段，客户端解析错乱甚至二次注入 XSS——所以转义函数是安全边界，不是格式美化。这块我还有个相邻的实战教训：UTF-8 按字节截断会产生非法字符序列，JSON 到前端直接解析失败——摘要截断必须对齐码点边界。诚实说，字段再多、结构再嵌套，就该换 rapidjson 了，手拼的正确性靠纪律维持，库的正确性靠测试维持。

**追问预演**：
- ↳ 中文字符要转 \u 吗？→ 不用，JSON 允许原生 UTF-8，合法多字节序列直接透传。
- ↳ 浮点数怎么拼的？→ score 用 %.4f 定长格式化，既控制长度又稳定可测。

## 四、TCP 基础延伸

### §8.17 三次握手/四次挥手为什么是三次四次？TIME_WAIT 什么含义？出现在哪端？🟡

**口语答案**：握手三次是要让双方各自确认"我能发、对方能收"并同步初始序列号：第一次客户端证明发得出，第二次服务端证明收得到且发得出，第三次客户端证明自己收得到——两次不够，服务端无法确认客户端能收到它的包，而且网络里迟到的旧 SYN 会建出假连接。挥手四次是因为 TCP 全双工：每个方向独立关闭，我收到 FIN 只代表你不发了，我可能还有数据要发，所以 ACK 你的 FIN 和我自己的 FIN 是两件事，中间可以隔着数据。TIME_WAIT 出现在主动关闭的一方，停留 2 个 MSL：一是等最后的 ACK 万一丢了能重传，二是让这个连接的旧报文在网络里自然死亡，避免污染之后复用同四元组的新连接。我们是服务端、被动关闭为主，TIME_WAIT 一般在客户端侧；之前排查过一次端口占用，怀疑 TIME_WAIT 残留加 SO_REUSEADDR 行为，60 秒自愈，就是拿 ss -tlnp 看的。

**追问预演**：
- ↳ 为什么挥手不能三次？→ 也可以三段：被动关闭方没有数据要发时，ACK 和自己的 FIN 可以合并在一个段里发——能合并是恰好无数据的优化，不是协议保证；四次是通用形态。
- ↳ 大量 TIME_WAIT 的危害？→ 客户端侧端口耗尽、连接表内存；服务端被 TIME_WAIT 围着一般是代码在疯狂主动断连，先查行为再调参数。

### §8.18 大量 TIME_WAIT/CLOSE_WAIT 怎么排查？🟡

**口语答案**：第一步永远是先看分布再动手：ss -tan 配 awk 统计各状态数量（netstat 也行），看多的是哪个状态，两个状态的病根完全不同。TIME_WAIT 多在主动关闭方，说明本端在高频建短连接主动断——典型是压测客户端或重连风暴；治本是长连接加连接池，治标是客户端侧开 tcp_tw_reuse。CLOSE_WAIT 多是另一种病：对端已经发了 FIN，本端代码一直没有调 close——基本是自己的 bug，连接对象泄漏、忘了处理对端关闭；CLOSE_WAIT 堆积优先查代码而不是调内核参数，内核没有参数能替你 close。我们项目里有现成素材：一次 PACS 服务 8080 端口 bind 失败，排查就是 ss -tlnp 看监听、TIME_WAIT 残留加 SO_REUSEADDR 的行为，等了 60 秒自愈——排查思路比结论值钱。

**追问预演**：
- ↳ SO_REUSEADDR 解决什么？→ 允许绑定处于 TIME_WAIT 的本地地址，服务重启不用等 2 MSL——监听 socket 的标配。
- ↳ ss 比 netstat 好在哪？→ ss 直连内核 sock_diag，大连接数下快得多，netstat 要遍历 /proc。

### §8.19 TCP keepalive 和应用层心跳的区别？假死连接怎么处理？🟡

**口语答案**：内核 keepalive 默认两小时才发第一个探测，而且它只证明 TCP 栈活着——对端进程死锁、中间网静默丢包，它在超长周期后才能发现；参数还是全局或逐 socket 粗粒度调的。应用层心跳周期自己定，几秒到几分钟，能带业务语义——版本号、负载信息，超时后还能触发业务动作：告警、摘流量、踢连接。我们的场景诚实说没做心跳：内网工作站长连接，假死概率低、断了重连成本低，这是量级决定的有意识取舍。真要做就在 TLV 协议里加 PING/PONG 帧类型——type 枚举空间足够，几分钟一轮，连续超时就 conn->forceClose，把资源收回来。假死连接不处理的代价是连接表和每连接解码器慢慢泄漏占内存。

**追问预演**：
- ↳ 怎么定心跳周期？→ 大于正常 RTT 一个数量级、小于业务能容忍的故障发现时间，内网一般 30 秒到几分钟。
- ↳ 心跳谁发起？→ 客户端发服务端应答，双向探活只测一条路径；服务端也可定时主动探。

### §8.20 Nagle 算法和 TCP_NODELAY？🟡

**口语答案**：Nagle 是省带宽的小包合并算法：有未确认的小数据在途时，新来的小包先攒着等 ACK，攒够或确认回来再发——代价是交互式延迟。它和 delayed ACK 组合还有个经典坑：一边等攒包一边等确认，互等出几十毫秒的额外延迟。我们的 TLV 是请求-响应模式，请求响应各一次写完，属于延迟敏感的交互流量，应该关掉 Nagle——muduo 提供 conn->setTcpNoDelay(true)，一行的事。诚实讲当前代码没有显式打开，因为整帧一次 send、单次写的场景 Nagle 影响有限；这是我知道的改进点，连接建立回调里加上就行。

**追问预演**：
- ↳ 什么时候该留着 Nagle？→ 吞吐优先、批量传输、一次写很多段的场景，小包合并省协议头开销。
- ↳ TCP_NODELAY 和 TCP_QUICKACK 的关系？→ 前者关发送侧攒包，后者让接收侧立即 ACK 不延迟，两个方向对症下药。

### §8.21 内网明文传输安全吗？怎么加 TLS？🟡

**口语答案**：风险是真的：检索结果里有患者姓名、诊断结论——明文在内网跑，同网段任何能抓包的人都能看到，这在医疗合规上是硬伤，患者隐私是法定义务。加法分两档：最小改动是前置网关做 TLS 终止——医院内网本来就有 nginx 或网关层，TLS 在那里终结，网关到 RIS 这一段维持明文 TLV 走内网回环，改动只在网关配置；端到端加密就要在 muduo 侧接 OpenSSL——muduo 本身不带 TLS，要自己做非阻塞下的 SSL_read/SSL_write 封装、处理 want_read/want_write 状态机，这个复杂度不小。诚实的口径：当前是内网明文，靠网络隔离兜底，TLS 列在演进清单上，首选网关终结方案。

**追问预演**：
- ↳ 为什么不直接给 TLV 加个异或/自定义加密？→ 自造加密是反模式，要么不加要么上标准 TLS，半吊子加密给出虚假安全感。
- ↳ PACS 那条 HTTP 链路怎么办？→ 同样的问题，同样网关终结；生产内网有边界防火墙，演进上 TLS 优先级取决于医院合规要求。
