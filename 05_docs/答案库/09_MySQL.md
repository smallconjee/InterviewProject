## 一、事务与日志

### §10.1 事务的 ACID 分别靠什么保证？🔴

**口语答案**：四个特性各有机制，不能笼统说"InnoDB 保证"。原子性靠 undo log——事务修改前先记反向操作，回滚时逆序重放，要么全做要么全不做；持久性靠 redo log——顺序写 WAL，事务提交即落 redo，崩溃后重放恢复已提交的修改，不用每次刷数据页；隔离性靠锁加 MVCC——写写冲突用行锁、间隙锁串行化，读写并发用 MVCC 快照让读不阻塞写；一致性是目的，由前三个特性加数据库约束（主键、唯一索引、外键、CHECK）共同达成。项目里我的导入链是两个显式事务：事务一做四层建模的 upsert 加 instance 状态推进，事务二把 ARCHIVED 状态和本地消息表写入同一个事务——"状态变更和待发事件原子提交"就是靠 A 和 D 撑住的，中间靠 PARSED 状态加 staging 文件兜崩溃窗口。

**追问预演**：
- ↳ 为什么有了 redo 还要 undo？→ redo 记"做了什么"用于重做崩溃前已提交的，undo 记"怎么改回去"用于回滚未提交的，方向相反缺一不可；MVCC 的版本链也挂在 undo 上。
- ↳ WAL 是什么思想？→ 先写日志再写数据，把随机写数据页转化成顺序写日志，提交代价从"刷多页"降为"刷一次日志"，数据库和消息中间件（我项目里 RabbitMQ 的持久化）都是这个思路。

### §10.2 四种隔离级别？MySQL 默认哪个？RR 怎么应对幻读？🔴

**口语答案**：四种从低到高：读未提交（会脏读）、读已提交 RC（解决脏读，但一个事务内两次读可能不同——不可重复读）、可重复读 RR（解决不可重复读，InnoDB 默认）、串行化（全串行，性能最差）。幻读指同一范围查询两次返回的行数不同——别的事务插进了新行。RR 对付幻读是两条路：快照读（普通 SELECT）靠 MVCC，事务第一次查询时生成 Read View，之后一直用它，别的事务后插的行对它不可见；当前读（SELECT ... FOR UPDATE、INSERT、UPDATE）靠间隙锁 next-key lock，把索引记录加记录锁的同时锁住记录间的间隙，别的事务插不进来。我项目里并发导入同一个 SOPInstanceUID 就是这个用例：决策前 SELECT ... FOR UPDATE 锁住该 UID 行，第二个导入事务在这里排队，不可能两个事务同时判"不存在"再各自插入——幻读场景被当前读的锁挡住了。

**追问预演**：
- ↳ RC 和 RR 在 MVCC 上的实现差异？→ 就差在 Read View 的生成时机：RC 每次查询都生成新的（所以能看到别人已提交的新行），RR 只在第一次查询生成并复用到事务结束。
- ↳ 间隙锁的代价？→ 锁范围变大，等值命中唯一索引时退化为纯记录锁，但普通索引和范围条件会锁区间，低并发下容易锁等待——我们导入链只对唯一索引行加锁，范围最小。
- ↳ 你们项目用哪个级别？→ 默认 RR，没有改；导入链的幂等决策靠 FOR UPDATE 当前读，不依赖隔离级别兜底。

**雷点**：别说"RR 完全解决了幻读"——快照读挡一部分、当前读靠 next-key lock 挡一部分，先开快照读再当前读的混用场景仍可能读到幻影行。

### §10.3 MVCC 原理？Read View？版本链怎么形成的？🔴

**口语答案**：MVCC 是"读不加锁、读写不互斥"的机制，核心三件套。第一，InnoDB 每行有两个隐藏列：DB_TRX_ID 记最后修改它的事务 id，DB_ROLL_PTR 指向 undo log 里的旧版本。第二，每次修改都把旧版本留在 undo 里，通过回滚指针串起来，就是版本链——链头最新、越往后越旧。第三，读的时候拿一个 Read View，里面有创建那一刻的活跃事务集合 m_ids、最小活跃 id、下一个将分配的 id 和自己的 creator_trx_id；沿着版本链从新到旧找，某个版本的 trx_id 如果是自己改的可见，如果是已经提交且早于最小活跃 id 的可见，如果还在活跃集合里或晚于 max 就不可见、顺链回溯。效果：每个事务按"开启时的一致性视图"读数据，后提交的修改对它不存在。RC 和 RR 的区别只在 Read View 的生成时机——RC 每次查询重建，RR 复用第一次的。

**追问预演**：
- ↳ undo log 什么时候清理？→ 活跃事务都可能回访旧版本，purge 线程要等所有早于该版本的事务结束才清理——长事务会阻止 purge，undo 膨胀，所以长事务是大忌。
- ↳ 这个思想在哪还见过？→ 和我项目里"索引版本切换 + shared_ptr 原子替换"是同构的：读者拿快照、写者建新版本、旧版本等最后一个读者放手——不可变加版本化是并发读的通用解。

### §10.4 redo log 和 binlog 的区别？为什么有两阶段提交？🟡

**口语答案**：redo 是 InnoDB 引擎层的物理日志，记"某页某处改成了什么"，循环写、固定大小，作用是崩溃恢复和 WAL；binlog 是 server 层的逻辑日志，记语句或行变更（STATEMENT/ROW/MIXED 格式），追加写，作用是复制和归档恢复，从库靠重放 binlog 追主库。两份日志描述同一个事务，就必须保证一致，否则主从数据分叉——这就是两阶段提交：事务先写 redo 并标为 prepare，再写 binlog，最后把 redo 标记为 commit。崩溃恢复时按规则裁决：redo 到了 prepare 但 binlog 完整就提交（事务算成功），binlog 不完整就回滚。反例推一下就懂：先写 binlog 后写 redo，binlog 落了、redo 没落，崩溃后主库回滚了这笔写，但从库已经重放——主少从多，永久不一致。

**追问预演**：
- ↳ binlog 三种格式怎么选？→ ROW 最安全（语句含 now()/limit 等不确定性时 STATEMENT 会主从不一致），代价是量大；MySQL 8.0 默认 ROW。
- ↳ 组提交是什么？→ 多个事务的刷盘合并成一次 fsync 摊薄 IO，是高并发下提交吞吐的关键优化。

## 二、索引与 B+ 树

### §10.5 B+ 树为什么适合做索引？和 B 树/红黑树/哈希索引比？🔴

**口语答案**：一句话：B+ 树是为磁盘设计的矮胖多路树。InnoDB 页 16KB，非叶子节点只存键和子指针不存数据，单页能放几百个键，扇出极大——千万行数据树高也就三四层，一次点查三四次页 IO；叶子节点存全部数据并且用双向链表串起来，范围查询定位起点后顺着链表顺序扫，不用回树根。对比：B 树每个节点都存数据，扇出小树更高；红黑树是二叉树，百万行就要二十层，一层一次内存/磁盘访问，适合纯内存不适合磁盘；哈希索引等值 O(1) 但完全不支持范围和排序。我建表时把这套直接用上了：每层自增 BIGINT 做聚簇主键保证顺序插入，DICOM 的 UID 放 VARCHAR(64) 唯一键做二级索引——层级行数最多的 instance 表靠这个结构撑日增 15 万的对象量，点查路径就是"按 uk_sop_uid 走二级索引到主键再到聚簇页"。

**追问预演**：
- ↳ 为什么 16KB 页能决定树高？→ 树高 = log_扇出(行数)，扇出 ≈ 页大小除以（键+指针）大小；主键越短扇出越大、树越矮——这也是我用自增 BIGINT 不用 64 字节字符串主键的原因之一。
- ↳ 一次主键点查到底几次 IO？→ 根页和上层页常驻 buffer pool 命中内存，通常只有叶子那一次真实磁盘 IO；buffer pool 是 InnoDB 性能的第一道防线。

### §10.6 聚簇索引和二级索引？什么是回表？覆盖索引？🟡

**口语答案**：InnoDB 数据本身就组织在主键 B+ 树的叶子上，这棵树叫聚簇索引——主键即数据。二级索引是另建的 B+ 树，叶子只存"索引列 + 主键值"。所以走二级索引查到主键后还要回聚簇树取整行，这个动作叫回表，等于两棵树各查一次。覆盖索引是让查询需要的列全在二级索引里，免掉回表——比如只 SELECT uid, id 且索引就在 uid 上，EXPLAIN 的 Extra 会显示 Using index。我项目里的高频查询都尽量带主键或走唯一索引点查；消息表巡检 SQL 查堆积数只用 status 列，给 status 建索引后就是覆盖扫描，几十万行的表毫秒级出结果。

**追问预演**：
- ↳ 为什么要减少回表？→ 回表是随机 IO，二级索引筛出的每一行都可能跳一次不同的聚簇页；大批量回表有时不如直接全表扫，优化器会自己权衡。
- ↳ 最左前缀怎么回事？→ 复合索引 (a,b,c) 按 a 排序、a 相同再按 b——查询条件必须从 a 开始连续命中才能用这棵树；我们患者表 (patient_id, issuer) 复合唯一，查询必须带 patient_id 才走索引。

### §10.7 唯一索引和普通索引在查询/写入上的差异？🔴

**口语答案**：查询上差别很小：唯一索引查到第一条就停，普通索引要继续找下一条直到不匹配——因为唯一性保证了后面没有。真正差异在写入：普通索引可以用 change buffer，目标页不在 buffer pool 时把写操作先缓存起来，避免立刻读页，后台合并；唯一索引必须当场读页判重，不能用 change buffer，写放大更大。所以"业务上不需要唯一约束就别建唯一索引"是通用建议——但我的场景正好相反，是主动要唯一索引的那类：SOPInstanceUID 的 uk_sop_uid 是幂等的地基，并发重复导入时第二个 INSERT 撞 1062 唯一冲突，代码捕获后转"重查加哈希对比"分支，按 DUPLICATE 幂等返回或 CONFLICT 拒绝。对比"先查后插"：两个线程同时查不到、都去插，脏数据就进来了；唯一索引把竞态收窄成数据库层的原子裁决，代价就是那点写放大，完全值得。这里还有个我实证过的坑：MySQL 唯一索引对 NULL 不去重，两条 issuer=NULL 都插得进去，所以患者复合唯一键里 issuer 用 NOT NULL DEFAULT ''，空串才参与唯一约束。

**追问预演**：
- ↳ change buffer 什么时候失效？→ 唯一索引、以及写后马上要读同一页的场景（合并时还是得读页）；MySQL 8.0 里它是只对非唯一二级索引生效的机制。
- ↳ 撞 1062 之后你们的处理分支？→ 重查该 UID 的既有行，比 sha256：相同转 DUPLICATE 返回 200 幂等，不同转 CONFLICT 返回 409 拒绝——医疗数据不可变，绝不静默覆盖。
- ↳ 唯一索引和"先查后插加分布式锁"怎么选？→ 数据库唯一约束最简单可靠、零额外组件；锁方案只在跨库跨实例约束不了时才需要。

**雷点**：别把 NULL 不去重说成"NULL 不进索引"——NULL 是进索引的，只是唯一性判断跳过 NULL。

### §10.8 为什么自增主键好？页分裂是什么？🟡

**口语答案**：InnoDB 聚簇索引按主键有序组织，自增主键永远追加到最后一页，页写满就开新页，顺序写入；随机主键（UUID、哈希值）插入位置随机，目标页可能不在内存，还得频繁把半满的页一分为二——这就是页分裂：页满了插中间位置，InnoDB 把一半数据挪到新页，还要维护链表指针，写放大、页利用率低（半满）、树局部变高。另外二级索引叶子都存主键值，主键越长所有二级索引越膨胀，64 字符的 UID 主键会让每条二级索引记录都背上它。所以我的四层模型统一用自增 BIGINT 代理键做主键，UID 退到唯一键——JOIN 走短整型，幂等走唯一约束，两个好处都拿到。

**追问预演**：
- ↳ 自增主键有什么缺点？→ 持续写入有热点页争用（最后一个页的 latch），超高并发下有人用随机前缀打散；分库分表场景自增 id 会冲突，要号段或雪花。
- ↳ 页分裂能观察吗？→ Buffer pool 读写压力、innodb_metrics 里的页分裂计数；建表时预留页填充率的主键设计（如时间高位加随机低位）是另一种取舍。

### §10.9 什么写法会让索引失效？🟡

**口语答案**：背一组高频的：对索引列做函数或运算（DATE(create_time)、id+1）；隐式类型转换——字符串列传数字（MySQL 会把列转成数字，索引侧函数化失效），反过来数字列传字符串还能走；LIKE 左模糊 '%xx'；OR 连接了非索引列；复合索引不满足最左前缀；NOT IN、!= 视优化器成本可能放弃索引。排查方法就是 EXPLAIN 看 type 是不是 ALL 全表扫。我项目里实际注意的两条：关联查询 study_instance_uid 是 VARCHAR，参数一律按字符串绑定不拼数字，避免隐式转换；消息表巡检按 status 等值过滤，status 建了索引且不带函数。

**追问预演**：
- ↳ 为什么函数运算会失效？→ B+ 树按原始列值有序，f(col) 的序和 col 的序没有保序关系，树没法用；除非建函数索引（8.0 支持）。
- ↳ 隐式转换的方向性问题？→ MySQL 的规则是把字符串转数字，所以"字符串列 = 数字"时列被函数化失效；"数字列 = 字符串"时是参数被转换，索引还在。

## 三、连接池（我负责的模块，厚答区）

### §10.10 连接池为什么需要？大小怎么定？🔴

**口语答案**：一次 MySQL 建连要 TCP 三次握手、认证、会话初始化，毫秒级；如果每个请求都新建，接口耗时的零头全是建连，MySQL 侧还有 max_connections 默认 151 的预算——多实例共享很快打爆。池把建连成本摊销到进程生命周期：启动时预热建满、请求只做借出归还。我的实现是固定大小同步池：mutex 加 condition_variable 保护一个 deque 空闲队列，acquire 带谓词的 wait_for 等待，RAII Guard 析构自动归还。大小不是越大越好——连接太多 MySQL 侧上下文切换和锁竞争反而劣化；经验公式：CPU 密集约等于核数，IO 密集等于核数乘（1 加等待时间比计算时间），我们 4C 机器、SQL 是毫秒级的短查询，默认配 4 条，可配置；同时要按 max_connections 预算给所有实例分账。

**追问预演**：
- ↳ 归还时连接是不是要重置？→ 我们每条连接是纯会话无状态、字符集建连时定死 utf8mb4，无需 reset；如果用过临时表、会话变量，归还前要清理，否则串话。
- ↳ 池满了请求怎么办？→ acquire 3 秒超时返回空 Guard 加 ERROR 日志，快速失败——挂死比报错难排查得多；上层把这个当依赖故障处理。
- ↳ 为什么用同步池不用异步客户端？→ 见 §10.13 单独展开。

### §10.11 断连怎么自愈？为什么刻意不开 AUTO_RECONNECT？🔴

**口语答案**：MySQL 服务端有 wait_timeout，空闲 8 小时断连，还有网络抖动、DB 重启——连接失效是常态，池必须自愈。我的策略是"借出前校验 + 显式重连"：acquire 从队列取出连接后先 mysql_ping，失败打 WARN，然后在同一句柄上重新 mysql_real_connect，再失败就销毁句柄补建一条新连接维持池大小。刻意不开 MYSQL_OPT_RECONNECT，两个理由：一是自动重连会在你不知情时静默换连接，事务执行到一半连接断了、重连后接着发后面的语句，事务上下文已经没了——后半段语句可能裸奔自动提交，数据错乱；二是会话变量、字符集这些会话状态重连后全丢。显式策略把重连时机钉死在"借出前、无事务在途"。这个逻辑真演练过：测试环境 docker restart MySQL，服务日志出现 Lost connection 的 WARN、自动重连、接口恢复，全程无人工干预。

**追问预演**：
- ↳ 8.0 之后 AUTO_RECONNECT 的状态？→ 8.0.34 起该选项已废弃还刷告警，官方方向就是让你自己管——我们的显式方案正好是推荐姿势。
- ↳ ping 每次借出都做，开销？→ mysql_ping 空闲连接上是微秒级的本地往返；池大、借出频繁时可以换"后台线程定期保活"，小池不值得加线程。
- ↳ 所有连接失效且重建也失败会怎样？→ 诚实讲是已知限制：acquire 返回空 Guard，且这条连接从池里永久流失，池会耗干；演进点是后台保活加低水位补建，当前规模不引入。

### §10.12 ping/重连为什么要在锁外做？acquire 超时上层拿到什么？🟡

**口语答案**：锁只保护空闲队列的出入队，ping 和重连刻意放在 unlock 之后做。原因：数据库抖动时 real_connect 可能阻塞到 connect_timeout 的 5 秒，如果持锁执行，一个线程重连就拖住所有等连接的线程——本来一条连接坏了，演变成全池卡死。锁外执行最坏只影响"借到这条坏连接的那一个请求"。这是"锁内不做任何可能慢的事"原则的标准应用。acquire 超时上层拿到的是空 Guard：构造时 conn 为 NULL，operator bool 返回 false，上层 if 判空走依赖故障分支返回错误响应——绝不能拿到空指针还往下用。配套还有个顺序细节：归还时先在锁内把连接 push 回队列、出了锁域再 notify_one，保证被唤醒的线程一定能拿到连接；条件变量没有记忆，反过来先 notify 后入队，等待者醒来重查谓词会失败又睡回去。

**追问预演**：
- ↳ notify_one 和 notify_all 怎么选？→ 每次只归还一条连接，唤醒一个等待者刚好；notify_all 会惊群，一堆线程醒来抢一条连接。
- ↳ wait_for 的谓词在防什么？→ 虚假唤醒和超时唤醒——醒来必须重查"队列非空"，这是条件变量的铁律（C++ 专项里展开讲）。

### §10.13 为什么不用 workflow 自带的异步 MySQL 客户端？🔴

**口语答案**：这题我当"取舍题"答而不是"对错题"。workflow 的 WFMySQLTask 是全异步客户端，彻底不阻塞 worker 线程，理论上更配它的调度模型——但代价是结果集解析全是回调式，多条 SQL 的事务链路写成回调嵌套，代码复杂度和可调试性都差；我的场景是导入链两个短事务、SQL 毫秒级，同步池加"handler 本身在异步 series 里推进"已经够用，P99 300ms 的预算里 DB 占比很小。另外自写同步池是脱离 workflow 可移植的通用组件，换网络框架直接搬走。演进路径也想清楚了：导入 QPS 真涨上去，先池化扩容和消息削峰，再不行把 DB 访问换异步客户端、或者 DB 前置请求队列。能讲清"现在为什么够、以后怎么换"比无脑上异步重要。

**追问预演**：
- ↳ 同步池会不会阻塞 workflow 的线程？→ 会占用一个 handler 线程等 SQL，毫秒级；workflow 线程数配得略大于核数，当前量级（峰值 15 QPS）下不构成瓶颈。
- ↳ 两个事务之间还有文件 rename，怎么保证不被池的重连打断？→ Guard 借出后连接全程被本请求独占，ping 只发生在借出前——事务中途绝不换连接，这正是拒绝 AUTO_RECONNECT 的原因。

### §10.14 RAII Guard 为什么只移动不拷贝？🔴

**口语答案**：Guard 的生命周期语义是"一个 Guard 独占一条借出连接的归还权"。如果允许拷贝，两个 Guard 指向同一连接，各自析构都调 release，同一连接被归还两次——空闲队列里出现两条指向同一句柄的记录，之后两个线程同时借出它并发写，会话直接错乱；这是数据正确性问题不是风格问题。所以拷贝构造和拷贝赋值 =delete，移动构造把 pool_ 和 conn_ 指针接管过来、源对象两个指针置 NULL，析构和 reset 都先判空——移动之后源对象退化成"空 Guard"，析构无动作，归还权始终唯一。acquire 按值返回正是靠移动语义完成的，零拷贝零连接复制。顺带一提这是 C++11 move 的纯收益：C++98 里要么返回裸指针手动管，要么付出一次连接包装的拷贝。

**追问预演**：
- ↳ 移动赋值怎么写？→ 先判自赋值，再 reset() 归还当前连接，然后接管源指针、源置空——move-and-swap 也能做，这里手工版更直观。
- ↳ 和 unique_ptr 什么关系？→ 同一个设计模式：unique_ptr 也是 delete 拷贝、只留移动，Guard 相当于给"连接归还"这个动作写了个专用 unique_ptr。

## 四、杂项与运维

### §10.15 utf8 和 utf8mb4 的区别？🟡

**口语答案**：MySQL 的 utf8 是历史遗留的残缺实现，最多 3 字节（utf8mb3），而 UTF-8 完整标准到 4 字节——emoji 和部分生僻汉字（姓名场景真会撞上）存进去直接报错或截断。utf8mb4 才是完整的 UTF-8。我的处理是全链路统一 utf8mb4：连接池建连时 mysql_set_character_set("utf8mb4")，表和列也是 utf8mb4——如果连接字符集和表不一致，写入时会发生转码，中文可能变问号。8.0 默认字符集已经是 utf8mb4，但显式设置连接字符集这个动作仍然要留，因为默认值会随版本和配置漂移，显式声明才是契约。

**追问预演**：
- ↳ 连接字符集和表字符集不一致会怎样？→ 驱动和服务端按 handshake 协商转码，配置错了轻则乱码重则插入失败；连接层显式 set 是唯一可靠做法。
- ↳ utf8mb4 对索引长度有影响吗？→ 有，VARCHAR 索引最长按字节数算，255 字符 ×4 字节超了 767 字节的老限制（需 DYNAMIC 行格式）；8.0 默认没问题。

### §10.16 mysql_store_result 和 use_result 的区别？不取结果会怎样？🟡

**口语答案**：mysql_query 只是把 SQL 发出去，结果集还在服务端。store_result 一次性把全部行拉到客户端缓冲，之后 mysql_num_rows、多次遍历都随便用，代价是结果集大时吃客户端内存；use_result 是流式，逐行 fetch、不整缓冲，内存省，但只能顺序读一遍、读完才能发下一条查询。默认大家都该用 store。不取结果的坑我项目里真踩过预防过：SELECT 之后不调 store/use 把结果取净，连接处于"未读净"状态，下一条查询直接报 Commands out of sync——哪怕你只要连通性测试。所以我们的 /db/ping 接口即使只看执行成功也把结果集取空再还连接，归还前连接必须是干净的。

**追问预演**：
- ↳ 为什么会有这个限制？→ MySQL 协议里一条查询的响应必须完整读完才能发下一条，这是协议的顺序性，不是 bug；use_result 更是把这条纪律逼到极致。
- ↳ 大结果集怎么处理？→ 分页 LIMIT、按流式 use_result 逐行消费、或导出走游标；千万别 store 一个百万行结果集。

### §10.17 慢查询怎么排查？EXPLAIN 重点看哪几列？🟡

**口语答案**：先打开慢查询日志，long_query_time 生产一般调到 1 秒甚至更低，我们内网还会配合消息表巡检 SQL 那种"扫全表但不慢到阈值"的查询，用 pt-query-digest 聚合慢日志找 TOP。拿到具体 SQL 后 EXPLAIN，重点四列：type——访问类型，从好到坏 const、eq_ref、ref、range、index、ALL，出现 ALL 全表扫基本要优化；key——实际用的索引，NULL 就是没用上；rows——预估扫描行数，数量级对不对直接看它；Extra——Using index 是覆盖索引（好），Using filesort 和 Using temporary 是额外排序和临时表（坏，常见于 order by 和 group by 没吃到索引）。我的巡检 SQL 例子：status 等值过滤加索引后 type 从 ALL 变 ref、rows 从几十万掉到几百，这就是完整闭环。

**追问预演**：
- ↳ filesort 一定有害吗？→ 不一定，结果集小的时候内存排序无感；大结果集加磁盘临时文件才致命，配合 rows 列一起判断。
- ↳ 除了 EXPLAIN 还有什么工具？→ EXPLAIN ANALYZE（8.0，真实执行带每步耗时）、optimizer_trace 看优化器为什么没选某个索引、show profile 看时间分布。

### §10.18 分库分表什么时候做？你的四层模型怎么拆？🟡

**口语答案**：先说原则：分库分表是最后手段，代价是跨片查询、分布式事务、扩容迁移全来——单表几千万行以内、靠索引和归档冷热分层能扛就别拆。真要拆，先垂直后水平：垂直按业务域拆库、把大字段冷数据拆出去；水平按分片键哈希或范围拆。我项目的四层模型本身就是好的垂直拆分底子：Patient/Study/Series/Instance 各管各的查询模式，instance 表增长最快（日增 15 万行），水平分片键我会上 study_uid 哈希——同一检查的影像落同片，"按检查读影像"这条主链路不跨片；患者维度的跨片聚合查询走异构一份到 ES 或宽表，不在 OLTP 库里硬查。另外医疗数据不物理删除，按检查日期做冷热分层、老数据归档到对象存储，单表增速先压下来，可能根本轮不到分表。

**追问预演**：
- ↳ 分片键怎么选？→ 贴最高频查询的维度，避免大多数查询跨片；同时键要均匀（UID 哈希均匀，日期范围会热点）。
- ↳ 分布式 ID 怎么办？→ 自增 id 分片后冲突，换雪花或号段模式；我们真分片时主键策略要一起改。

### §10.19 主从复制原理？延迟怎么办？🟡

**口语答案**：原理三步：主库事务提交写 binlog；从库 IO 线程连上主库，主库 dump 线程推送 binlog，从库写进 relay log；从库 SQL 线程重放 relay log。默认异步——主库不等从库，丢主库就有丢数据窗口；半同步让至少一个从库 ACK 收到 binlog 才向客户端返回提交。复制方式从早期的语句复制演进到 8.0 默认的 ROW（按行变更重放，确定性最好）。延迟的根因多是 SQL 线程单线程重放追不上主库并发写，大事务、从库负载高都加剧；8.0 有基于 writeset 的并行复制改善。怎么办分三招：读写分离时"关键读"强制走主库——比如"写完立刻查"的场景；监控 Seconds_Behind_Master 告警，超阈值把读切回主库；治本是并行复制加控制大事务。我们生产是单实例 + 每日备份 + binlog 归档——医院内网峰值十几 QPS，单实例余量足够，主从在演进计划里；真要上读写分离，上面那三招就是我会提前铺的。

**追问预演**：
- ↳ 一主多从还能怎么用？→ 读写分离分摊读压力、多从互备；从库延迟参差时按 Seconds_Behind_Master 摘除。
- ↳ 主库挂了怎么办？→ 主从不等于高可用，需要 MHA/Orchestrator 或云上自动切换做故障转移，脑裂靠仲裁和 fencing 防——这块我们靠运维侧方案，我能讲原理。
