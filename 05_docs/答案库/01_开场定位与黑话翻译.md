## 🔴 请用两分钟介绍一下这个项目。（备 30 秒版 / 2 分钟版两个长度）

**口语答案**：

【30 秒版】我做的主线是医学影像归档系统，说白了就是一个海量小文件存储加异步云备份的服务：影像文件从上游网关进来，请求线程里完成落盘、解析、元数据入库，毫秒级返回；OSS 云备份走 RabbitMQ 异步链，靠本地消息表、confirm、手动 ACK、死信队列保证不丢不重。同期我参与了报告检索系统，本质是结构化文本的倒排索引检索。团队 6 个人，我负责归档链路和认证对接。

【2 分钟版】按四段讲：
- 背景：给医院做的影像归档系统，已上线 3 家医院，日均导入约 15 万个影像对象、日增 120GB。两个项目：归档 PACS 和报告检索 RIS。
- 角色：项目组 6 人、后端 3 人含我。我负责归档链路——四层存储建模、导入事务、SHA-256 判重、消息可靠性，外加认证对接；RIS 参与分词索引和在线服务的部分模块。
- 归档设计两句话：同步链做减法——staging 落盘、手写 DICOM 解析遇像素即停、两个短事务入库，P99 300ms 以内；异步链保可靠——OSS 上传交给独立消费者，本地消息表和归档状态同事务，加 confirm、手动 ACK、task_id 幂等、有界重试、死信队列，消息不丢不重。幂等键是 SOPInstanceUID 唯一索引，同 UID 同哈希幂等返回、异哈希 409 拒绝。
- 收尾拉回通用：RIS 是倒排索引加 TF-IDF 检索，存量 80 万份报告、峰值约 20 QPS、P99 80ms。这套东西您可以完全当通用后端问题看——存储、事务、消息、缓存、索引，没有一项是医疗专属的。

**追问预演**：
- ↳ 两个项目分别一句话概括是什么？——"海量小文件归档存储 + 异步云备份" / "结构化文本倒排索引检索"，就在 30 秒版里，脱口而出。
- 先讲哪个？——先 PACS（我是负责人，素材最深），RIS 等面试官问或一句话带过。
- "毫秒级"具体多少？——同步链 P99 300ms 以内（不含备份），别顺口说成"几毫秒"。

**雷点**：两分钟版讲成需求说明书（谁用、多少功能）而没有一句设计取舍，面试官会判定"只会做不会想"——每段必须带一个"为什么这么设计"。

## 📐 部署：几台机器？怎么部署的？配置怎么管理？

**口语答案**：生产 4 台 4C8G 虚机：PACS 主服务（兼 HTTP 入口）、备份消费者、RIS 检索服务各一台，加一台运维监控机（Zabbix/日志），消费者和 RIS 可横向扩。MySQL 单实例加每日备份（主从为演进）、Redis 单实例、RabbitMQ 单实例带死信队列，都在院内网机房，公司实施团队驻场部署和升级。配置管理是三级合并：环境变量优先于 INI 文件优先于默认值，密钥只从环境变量注入、日志打码；启动时全量校验、fail-fast。开发测试环境各一套 Docker Compose。

## 🟡 项目里遇到最难的问题？

**口语答案**（90 秒故事，背熟）：讲 mysql_insert_id 的 bug。做导入链联调时我发现一部分实例卡在 PARSED 状态、本地消息表插不进去，日志报外键错误 instance_fk=0。定位：事务一里 INSERT 实例之后，我先发了 COMMIT 再调 mysql_insert_id 取 id——而 insert_id 绑定的是"本连接最后一条语句"，COMMIT 之后它返回 0，事务二就拿 0 去插消息表，被外键拒绝。修复只有一行顺序调整：INSERT 后立即取 id 再 COMMIT。但收获很大：一是吃透了 MySQL C API 的会话语义；二是验证了状态机设计——卡在 PARSED 的实例第二次导入时靠续传分支自动收尾，没有产生脏数据，幂等设计反过来兜住了我自己埋的 bug。

**追问预演**：
- 怎么发现的？——联调日志里外键错误 + 实例状态不符合预期，顺着 instance_fk=0 反查调用时序。
- 为什么测试没拦住？——只在"特定语句顺序"下触发，正常单测路径都过；之后补了对账检查。
- 还有别的候选故事吗？——备选：排他消费僵尸进程（SIGTERM 等不到检查点，信号处理器直接 _exit，幂等吸收重复）；按面试官口味切换。

**雷点**：讲成"我查了半天不知道为什么，改了就好了"——没有根因的故事是负资产。

## 🔴 这些医学名词我不熟——PACS/RIS/DICOM 是什么？用外行话讲讲系统解决什么问题。

**口语答案**：给您翻译一下：PACS 就是医院里管影像的"网盘加文件服务器"，核心矛盾是海量小文件的归档存储；RIS 是检查报告的"搜索引擎"；DICOM 是医学影像的标准文件格式，可以理解成"带元数据头的图片容器"；一次检查、一个序列、一张图，是天然的三级目录结构。翻译完了拉回技术：这两个系统您完全可以按通用后端问题理解——一个是"海量小文件存储 + 异步云备份"，一个是"结构化文本倒排索引检索"，里面的事务、消息可靠性、缓存、索引全是通用话题，您随便挑一个往深里问。

**追问预演**：
- 一次检查数据量多大？——CT 一次 100–500MB、几百张图，DR 一张 30–50MB（回数字，不回医学）。
- 为什么要备份两份？——医院数据法规要求可追溯，本地是热存储、OSS 是异地容灾（一句带过，不展开合规）。
- 医生怎么用？——工作站调阅，低频查询、峰值约 20 QPS（顺势把话题引到性能）。

**雷点**：顺着医学展开讲设备原理、病种术语=自爆，通用岗面试官不感兴趣——三秒翻译完必须回技术。

## 三秒翻译表（黑话 → 通用语言）与使用示范

| 简历词 | 外行翻译 |
|---|---|
| PACS | 医院里管影像的"网盘+文件服务器"：海量小文件归档存储 |
| RIS | 医院检查报告的"搜索引擎"：结构化文本检索 |
| DICOM | 医学影像标准文件格式，类似"带元数据头的图片容器" |
| Study/Series/Instance | 一次检查 / 一个序列 / 一张图——天然的三层目录结构 |
| CT/MR(MRI)/DR | 三种拍片设备，产出不同大小的影像文件 |
| Modality | 影像里的"设备类型"字段 |
| SOPInstanceUID | 一张图的全局唯一 ID（幂等键的来源） |

**使用示范**（模拟对话，练到条件反射）：

- 面试官："你简历里这个 Modality 是什么？"
  我："就是影像里的设备类型字段，标记这张图是 CT 还是 DR 拍的，类似消息里的 type 字段。我们主要用它做查询过滤，技术上没有特殊点。"——三秒翻译，立刻归位，不恋战。

- 面试官："SOPInstanceUID 是什么？"
  我："一张影像文件的全局唯一 ID，类似一条消息的消息 ID——我们整个导入幂等就建在它的唯一索引上，这个可以展开讲。"——把黑话翻译成通用类比，顺势把话题钩回自己最熟的幂等设计。

- 面试官："DR 是什么设备？"
  我："一种拍片设备，单张文件 30 到 50MB、是我们最大的对象，长尾延迟主要来自它。"——连医学词都往性能数字上挂。

**使用要点**：①任何黑话出现，先给一个"通用后端类比"再回技术；②绝不主动展开医学知识；③每个黑话都提前挂好一个自己最强的技术钩子（UID→幂等、Study→数据建模、Modality→查询过滤），让翻译变成引战工具而不是解释负担。
