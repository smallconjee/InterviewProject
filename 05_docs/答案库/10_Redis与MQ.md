## 一、Redis 专项（题库 §11）

### §11.1 Redis 为什么快？单线程为什么反而快？🔴

**口语答案**：四个原因叠出来的：第一，纯内存操作，读写是百纳秒级，跟磁盘差四五个数量级——这是根本；第二，命令执行单线程，没有锁竞争、没有线程上下文切换、没有并发数据结构的设计复杂度；第三，网络层 IO 多路复用，单线程靠 epoll 同时挂几万个连接，哪个就绪处理哪个，这个和 muduo 的 Reactor 是同一套思想；第四，数据结构针对场景做了优化——SDS 字符串 O(1) 取长度、预分配、二进制安全，zset 用跳表，小 hash/list 用 listpack 紧凑编码。要强调"快的前提是内存"，瓶颈通常在内存容量和网络带宽而不是 CPU。6.0 的多线程 IO 说的就是最后一块：命令执行仍然单线程保住无锁语义，但网络读写和协议解析放给多线程，大 value 和高 QPS 场景吞吐明显提升——是把"慢在 IO"和"执行要无锁"拆开处理。

**追问预演**：
- ↳ 单线程有什么代价？→ 一个慢命令阻塞所有请求（keys * 这类 O(n) 是大忌，用 scan）；这也解释了删大 key 要 UNLINK 异步删。
- ↳ 我们项目哪里体现了这套设计？→ L2 命中路径就是"一次 GET 加一次 1ms 内网往返"，20 QPS 的检索流量下 Redis 连零头都算不上；缓存的是整串 JSON 结果，value 几 KB，用的就是普通 string。

### §11.2 RDB 和 AOF 的区别？恢复速度/数据安全怎么权衡？混合持久化？🔴

**口语答案**：RDB 是全量二进制快照：bgsave 时 fork 子进程，子进程把那一刻的数据写成压缩快照文件，靠操作系统写时复制保证主进程继续服务。优点是文件小、恢复快（直接载入内存）；缺点是两次快照之间的数据崩溃就没了。AOF 是增量命令日志：每条写命令追加到文件，回放恢复；关键是 fsync 策略三档——always 每条都刷最安全最慢，everysec 每秒刷是默认、崩溃最多丢一秒，no 交给操作系统最快最险。缺点是文件大、恢复慢（逐条重放），所以有 AOF 重写：fork 子进程按当前数据生成最小等价命令集。混合持久化是 4.0 之后把两者合体：AOF 重写时，子进程先把当前全量数据以 RDB 格式写进新 AOF 文件开头，之后新的写命令以 AOF 格式追加——恢复时先快照载入再重放尾部增量，恢复速度接近 RDB、丢失窗口又是 AOF 级（秒级），现在 5.0 起默认开启。我们生产的取舍很直接：Redis 只做结果缓存，数据丢了走索引重建，几分钟自愈，所以用默认的 RDB 就够，还省 AOF 的磁盘 IO——"缓存丢得起"本身就是架构决策的一部分。

**追问预演**：
- ↳ bgsave 的 COW 细节？→ fork 后父子共享物理页、都标只读，谁写谁触发缺页复制；快照时间取决于写入量，大量写时子进程看到的旧数据和内存翻倍风险都要评估。
- ↳ 什么时候必须 everysec 甚至 always？→ Redis 里放的是真数据（分布式锁、计数器、未落库的业务数据）时；纯缓存 RDB 足矣——先问数据丢了重建成本，再选策略。

### §11.3 主从复制的流程？全量/增量同步？哨兵做什么？Cluster 怎么分片？🟡

**口语答案**：先交代口径：我们生产是单实例（缓存定位、可降级），主从和哨兵是我准备的演进方案，原理我完整讲。主从复制：从库执行 replicaof 后连接主库发 psync。第一次是全量同步：主库 bgsave 生成 RDB 发给从库，同时把生成期间的新写命令攒在复制缓冲区，从库清空旧数据载入 RDB，再把缓冲区命令追上。之后进入命令传播；断线重连时从库带上自己的复制偏移量，如果偏移量还在主库的 repl_backlog 环形缓冲区里就走增量同步只补差量，被覆盖了就退化成全量——所以 backlog 大小决定了"多久的断线能增量"。哨兵解决高可用：一组哨兵进程持续 ping 主库，单个哨兵认为挂了是主观下线，超过 quorum 个哨兵都认为挂才客观下线，然后哨兵之间选 leader 执行故障转移——从库按"优先级、复制偏移量新、runid 小"挑一个提升为主，其余改挂到新主。Cluster 解决容量和写扩展：数据按 CRC16 分到 16384 个哈希槽，每节点负责一段槽，客户端可以直连任意节点，键不在本节点返回 MOVED 重定向；节点间 gossip 协议通信，主挂了它的从自动补位。

**追问预演**：
- ↳ 我们为什么要演进到哨兵？→ 单实例是缓存的单点，挂了所有实例 L1 miss 时都直查索引，P99 从 80ms 内退化到全走索引、Redis 恢复后自愈——可接受但降级期变慢；哨兵把这段窗口消掉。
- ↳ 主从复制是强一致吗？→ 不是，异步复制，主库提交不等从库——主库刚确认写、还没传到从库就挂，提升新主后这笔写就丢了；金融级要 WAIT 或别的方案。
- ↳ Cluster 和哨兵怎么选？→ 容量没到瓶颈只要高可用，哨兵加主从最简单；数据量大或写吞吐要分片才上 Cluster，代价是运维和多键操作受限。

**雷点**：别说"哨兵也存数据"——哨兵只做监控仲裁和故障转移，不代理数据面。

### §11.4 你的 Redis 客户端怎么实现的？并发调用安全吗？💣🟡

**口语答案**：自写的薄封装，几个设计点：hiredis 同步 API；懒连接——构造不连，第一次 get/setex 时 ensure_connected 才建；建连用 redisConnectWithTimeout 2 秒，建完再 redisSetTimeout 把读写超时也设成 2 秒——这里有个注释里写明的理由：connect 超时只管握手阶段，Redis 卡顿时不设读写超时，redisCommand 可能长时间阻塞；断连自愈——redisCommand 返回 NULL 说明连接断了，释放旧上下文、置空，下次调用重连；降级——连不上只 WARN 一次（warned_ 标志防刷屏），缓存层返回 false，检索直查索引。并发安全这题我主动交底：hiredis 的 redisContext 是非线程安全的，而这个对象被 4 个 muduo IO 线程并发调用，一开始实现里没锁、头文件注释还声称有锁——是我复盘时发现的真 bug，后来加了 mutex 成员，get/setex 整体上锁修复的。取舍也想清楚了：临界区含一次约 1ms 的网络往返，4 线程的缓存查询会串行化，当前长连接低频查询的量级可接受；演进方向是每 IO 线程独立连接或小连接池，消掉串行化。

**追问预演**：
- ↳ 为什么不像 LruCache 那样细锁？→ 锁粒度跟临界区性质走：LRU 临界区是纳秒级纯内存操作，单锁够；RedisCache 锁内是网络往返，锁的策略完全不同——要么缩小临界区（不该持锁做 IO），要么让并发路径不共享（每线程连接）。
- ↳ hiredis 有没有线程安全的用法？→ 有独立上下文模式——每线程各建一个 redisContext 就互不干扰，不用加锁；我们单上下文加锁是连接数和实现简单的折中。
- ↳ 为什么不用连接池？→ 缓存读 QPS 低，一条连接加锁够用；连接池是为高并发拿连接准备的，等演进时和"每线程连接"一起评估。

**雷点**：别顺着说"一开始就考虑了线程安全"——真实经历是"注释声称有锁、实现没有"，主动讲"发现-修复-写进注释"反而是加分项。

### §11.5 Redis 还能干什么？🟡

**口语答案**：拿数据结构对能力：string 做缓存、计数器（INCR 原子自增，接口限流计数）、分布式锁（SET NX EX）；hash 存对象字段级读写；zset 跳表加分数序，天然排行榜（ZADD/ZREVRANGE）；list 做简单队列和最新列表；set 做共同关注、标签交集；pub/sub 做轻量广播——但它不持久化消息、离线收不到，正经消息要上 MQ；再加 bitmap 签到、hyperloglog 的 UV 基数估算。结合我项目说一个真用例加一个演进用例：真用的是 string 缓存检索结果（版本化键加 SETEX 300 秒）；演进用例是 JWT 注销——当前短 TTL 自然过期，真要即时注销就 Redis 记 jti 黑名单，每次验签查一次，这也是 string 的典型场景。

**追问预演**：
- ↳ 计数器为什么不用 MySQL？→ 高频自增是反 OLTP 的（行锁热点），Redis 单线程内存 INCR 无竞争；定时把计数回落库里即可。
- ↳ pub/sub 和 MQ 怎么选？→ pub/sub 在线广播、不保证送达；我们备份链要求不丢不重，所以用 RabbitMQ——消息可靠性决定选型。

### §11.6 分布式锁怎么实现？有什么坑？🟡

**口语答案**：基础版一条命令：SET lock_key unique_value NX EX 10——NX 保证只有一个客户端能设置成功，EX 防止持有者崩溃后死锁，value 放"实例加线程"的唯一标识，释放时不能直接 DEL——要用 Lua 脚本先 GET 比对是自己的再 DEL，把"判断和删除"原子化，否则会删掉别人的锁。坑一串排着讲：业务没跑完锁先过期——别的客户端进来，自己回来又删错，解法是看门狗续期（Redisson 的做法：后台线程定时把 TTL 续上，直到显式释放）；主从切换丢锁——异步复制下主库确认了锁还没同步就挂，新主上锁不存在，两个客户端同时持锁；Redlock 用多数派多个独立实例投票试图解决，但它对时钟跳变和进程停顿的假设被 Kleppmann 质疑过，Antirez 有回应，业内没有共识——能讲出这场争论本身就是加分。务实建议：锁的正确性要求没那么高时用单实例锁加 fencing token（锁带版本号，下游拒绝旧版本）；要求严格正确就用 ZooKeeper/etcd 这类共识系统。我项目没有分布式锁用例——幂等全部靠数据库唯一索引裁决，这比锁更简单可靠，真到要协调多写者再加。

**追问预演**：
- ↳ fencing token 是什么？→ 锁服务每次授锁发递增令牌，存储侧只接受不小于已见最大令牌的写——把正确性从"锁的持有假设"转到"存储的版本裁决"，比完美锁现实。
- ↳ 为什么释放必须 Lua？→ GET 和 DEL 两步之间可能过期被别人抢到，DEL 就误删；Redis 单线程执行脚本天然原子。

### §11.7 缓存与数据库一致性的通用解法？🟡

**口语答案**：通用套路是 Cache Aside：读——先查缓存，miss 查库回填；写——更新数据库，再删除缓存（不是更新缓存：并发写下更新缓存会乱序覆盖，删了等下次读回填最安全）。顺序上主流是"先更新库再删缓存"：反过来先删缓存，删完到回填之间另一个读请求 miss、把旧值读出来又填回去，脏数据就驻留了；先更新库再删缓存也有个小窗口（读请求在删之前 miss 读到旧值回填），概率低但存在。补救有延迟双删——写完删一次，延迟几百毫秒再删一次，把回填的旧值清掉；更彻底的是订阅 binlog（canal）异步删，把"删"和业务写解耦。但我们项目把这个题从根上绕开了：我缓存的失效源只有一个——索引重建，而索引不可变、重建即换版本号，版本号烧进缓存键（ris:v{版本}:{FNV-1a(查询)}），新查询天然落新键、读新索引算的新结果，旧键靠 TTL 300 秒自然过期。没有"删缓存"这个动作，就没有删漏删错的窗口——先想清楚失效源是什么，再选一致性方案。

**追问预演**：
- ↳ 为什么删除缓存而不是更新缓存？→ 并发写时更新缓存的先后序不可控（后写的库先更新缓存就脏了），懒加载式删除天然规避；缓存是计算结果时（像我们）甚至可能"更新"本身很贵。
- ↳ 延迟双删的延迟怎么定？→ 大于一次读 miss 回填的耗时（主从延迟也要算），几百毫秒经验值；只能缩小不能消除窗口，这是概率方案。

### §11.8 大 key / 热 key 的问题和处理？🟡

**口语答案**：大 key 是 value 过大或集合元素过多——string 几十 KB 以上、集合几万元素就该警惕。问题：网络带宽被单 key 打爆（Redis 单线程收发，慢客户端拖所有人）、删除阻塞（DEL 一个百万元素集合是 O(n) 的主线程卡顿，4.0+ 用 UNLINK 异步删）、内存倾斜和迁移卡顿。处理：拆（大 hash 按字段哈希拆成多个小 key）、压缩 value、过期淘汰代替显式删、用 redis-cli --bigkeys 或 RDB 离线分析巡检。热 key 是单个 key 的访问集中在单节点（比如秒杀商品），把该实例 CPU 打满。处理：本地缓存挡一层（我们架构里 L1 LRU 干的就是这个——热查询词在进程内 512 条 LRU 命中，根本到不了 Redis）、key 加后缀打散多副本随机读、读写分离扛读。落到我项目自检：缓存的 value 是 Top10 结果的 JSON 串，几 KB 量级，离大 key 红线远；热查询词（常见病种术语）由 L1 承接，两级合计命中率 ~70%，Redis 侧压力很小——这两类问题在设计时就已经被分层消化了。

**追问预演**：
- ↳ 怎么发现热 key？→ 客户端埋点统计 key 频次、redis-cli --hotkeys（LFU 模式）、代理层聚合；我们更简单——L1 命中日志按查询词聚合就是现成的热点榜。
- ↳ UNLINK 为什么不阻塞？→ 把释放大内存的动作丢给后台线程异步做，主线程只摘引用——又是"慢操作移出关键路径"的通用原则。

## 二、MQ 与消息中间件延伸（题库 §12）

### §12.1 RabbitMQ 的核心概念？🟡

**口语答案**：核心是"生产者从不直接投队列"这个解耦设计。概念链：producer 把消息发到 exchange（交换机）；exchange 根据类型和 binding（绑定关系，常带 routing key）决定把消息路由到哪些 queue；consumer 从 queue 取消息消费。exchange 四种类型：direct 精确匹配 routing key；fanout 广播到所有绑定队列；topic 按 `*.#` 通配模式匹配（我们备份链用的就是 topic，routing key 按业务维度区分）；headers 按消息头匹配，少用。外围概念：broker 是服务节点；vhost 做逻辑隔离（权限和拓扑的命名空间）；channel 是 TCP 连接上的虚拟链路——一个 TCP 上开多条 channel 并发收发，省握手又复用连接，这是和"每请求一连"的关键区别。我们链路的配置：durable exchange 加 durable queue 加 delivery_mode=2 持久化消息，绑定到 DLQ 的死信交换机——这些概念在可靠性那题串起来讲。

**追问预演**：
- ↳ 为什么生产者不直接投队列？→ 解耦发布方和消费方的拓扑——消费方增删队列、换路由规则，发布方零感知；直接投队列等于把路由决策焊死在发布端。
- ↳ 我们为什么选 topic？→ 备份任务按对象类型/优先级做路由键扩展的余地大，topic 的通配语义最灵活，性能和 direct 差距可忽略。

### §12.2 一条消息"成功投递"分几层？🟡

**口语答案**：我按链路拆成四层，每层有自己的确认机制和丢失窗口——这也是我们链路设计的骨架。第一层，生产者到 broker：靠 publisher confirm——channel 上 confirm.select 后，broker 收到并路由成功回 basic.ack，路由不到按 mandatory 标记退回；我们的发布端是手写 rabbitmq-c 实现：confirm.select、等 basic.ack、3 秒超时。第二层，broker 内存到磁盘：exchange/queue 声明 durable，消息 delivery_mode=2，broker 刷盘后才算安全——纯内存队列 broker 宕机消息蒸发。第三层，broker 自身高可用：单实例宕机靠镜像队列或仲裁队列多副本——我们是单实例加 DLQ，这一层靠"消息表能补发"兜住：confirm 前崩溃，本地消息表里事件还是 PENDING，扫描线程超时补发。第四层，broker 到消费者：手动 ACK——消费者处理完成（OSS 上传成功、状态同事务更新）才 basic.ack，中途崩溃没 ack，broker 重投给其他消费者。四层合起来配消费端幂等，净效果是 at-least-once 不丢、重复被吸收。

**追问预演**：
- ↳ confirm 和 RabbitMQ 自带事务的区别？→ RabbitMQ 的 tx 是同步阻塞的 AMQP 事务，性能差一个数量级；confirm 是异步确认，生产实践一律 confirm。
- ↳ mandatory 干什么？→ 路由不到任何队列时把消息回退给生产者（basic.return），配合备份交换机使用——防止"发成功了但没人收"的静默丢失。

### §12.3 RabbitMQ / Kafka / RocketMQ 选型各看什么？🟡

**口语答案**：一句话定位：RabbitMQ 是路由丰富、可靠投递的业务消息中间件；Kafka 是超高吞吐的分区日志流平台；RocketMQ 是功能最全的国产业务消息中间件。展开看三个维度。吞吐：Kafka 顺序写加零拷贝加批量，百万级 TPS，为日志流和事件溯源而生；RabbitMQ 万到十万级；RocketMQ 十万级。功能：RabbitMQ 的 exchange 路由模型最灵活、DLQ 和 confirm 开箱即用、管理台好用；RocketMQ 有事务消息、延迟消息、消息轨迹，电商味十足；Kafka 功能最少但重放（按 offset 回读）和顺序性（分区内有序）独一档。运维：Kafka 依赖 ZK（新版本去了）、资源吃得多；RabbitMQ 单机轻。我们的决策：备份链的消息量小（日均 15 万条，峰值几十任务每秒）但对可靠性要求极高（医疗影像不能丢），需要 confirm、DLQ、死信路由这些能力——RabbitMQ 全都现成且团队熟；Kafka 的吞吐优势在这个量级完全用不上，它的分区日志模型反而是杀鸡用牛刀。选型先看量级和可靠性，再看功能，最后才是流行度。

**追问预演**：
- ↳ Kafka 怎么保证不丢？→ 三件套：producer acks=all 等全部 ISR 副本确认；replication.factor≥3 多副本；min.insync.replicas≥2 防止 ISR 收缩后 acks=all 退化成单副本；消费端手动提交 offset。
- ↳ 用 Kafka 重做这条链怎么设计？→ 按 SOPInstanceUID 做 key 分区（同对象保序），producer acks=all，消费组并行消费，重试用单独 topic 加 DLQ topic——模型能映射，但事务消息语义要自己用本地消息表补。

### §12.4 RocketMQ 事务消息的原理？对比你的本地消息表？🟡

**口语答案**：RocketMQ 事务消息两阶段加回查：producer 先发"半消息"到 broker——消息已落盘但对消费者不可见；然后执行本地事务（我们的场景就是归档状态更新）；成功则 commit 让消息可见，失败 rollback 删掉半消息。关键一手是兜底：producer 宕机或没回报状态，broker 定时回查 producer 的本地事务状态接口，由 producer 查自己的事务结果再答复——最终消息一定达成"本地事务成功则消息必达"。对比我的本地消息表方案：思路同源，都是"把业务变更和消息落地放进同一个保证里，再异步确认"；差别在协调者位置——事务消息把协调逻辑放在 broker（半消息加回查），业务库里不引入额外表；本地消息表把协调放在业务库和自己的扫描线程（事件和业务状态同事务插入，PENDING 超时补发），不依赖 MQ 的特有功能。我选本地消息表的理由：一是 MQ 无关性——我们是 RabbitMQ，没有事务消息能力，将来换 Kafka 也不用改业务库；二是可观测——消息表就是一张普通表，堆积多少、重试几次、何时 DEAD，巡检 SQL 一查便知，"积压 >2 万且持续 1 小时"就是建在这上面的。代价是业务库多一次同事务写入加扫描线程，这个量级下完全可接受。

**追问预演**：
- ↳ 两种方案的失败路径？→ 事务消息怕回查接口不可用（producer 集群全挂时消息悬着）；本地消息表怕扫描线程和主库一起出问题——但那种情况业务本身也停了，一致。
- ↳ 还有别的分布式事务方案吗？→ 2PC 强同步但阻塞、协调者单点；TCC 业务层三段补偿，侵入大；Saga 长流程逐步补偿；本地消息表/事务消息本质都是最终一致的 outbox 族——可靠性要求下我倾向 outbox。

### §12.5 延迟消息怎么做？🟡

**口语答案**：RabbitMQ 有两条路。经典做法 TTL 加死信交换机：消息带 TTL 投进一个没有消费者的"等待队列"，过期后变成死信，按队列上配置的 x-dead-letter-exchange 路由到真正的业务队列——消费端拿到的就是"到点执行"的消息。这个方案有个经典坑：RabbitMQ 只检查队头消息的过期，TTL 不同的消息混在一个队列里，前面一条 10 分钟的会阻塞后面一条 10 秒的——队头阻塞；工程解法是按 TTL 分档，每档一个等待队列。新做法是官方插件 rabbitmq_delayed_message_exchange，交换机自己存延迟消息到点投递，支持任意延迟，但插件是单机的，可靠性要自己评估。RocketMQ 原生支持：4.x 是 18 个固定延迟等级（1 秒到 2 小时），消息先存进内部的定时主题，定时服务到点搬回真实主题；5.x 放开了任意时间。我项目里有个等价实现：备份任务的重试就是延迟消息——失败后写 next_retry_at = NOW() 加 2 的 n 次方秒（指数退避），主服务的扫描线程轮询到期的任务补发——数据库轮询版延迟消息，可靠性就是消息表的可靠性，量级小的时候最简单。

**追问预演**：
- ↳ 为什么重试要指数退避？→ 故障时（比如 OSS 限流）固定间隔重试等于持续给故障组件压力，指数退避让重试密度随时间衰减，恢复期不雪上加霜。
- ↳ 分档 TTL 方案档位怎么定？→ 按业务延迟需求取离散档（30 秒、1 分、5 分、30 分），档内取最长 TTL——精度换简单。
