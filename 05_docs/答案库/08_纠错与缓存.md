## 一、BK-tree 与纠错

### §9.1 BK-tree 的原理讲一下？为什么能避免遍历整个词典？🔴

**口语答案**：BK-tree 是把词典组织进"度量空间"的数据结构，靠编辑距离满足三角不等式来剪枝——d(a,c) 不超过 d(a,b) 加 d(b,c)。结构上：每个节点存一个词，子树按"子词与父词的编辑距离"分桶，边权就是距离。查询词 q、允许距离 n 时，先算 q 与当前节点的距离 d，然后只有边权落在 [d-n, d+n] 区间内的子树才可能藏有距离不超过 n 的词——区间外的子树被三角不等式排除，整棵剪掉。效果：35 万词项的词典，暴力是 35 万次 O(L²) 的 DP；剪枝后典型只访问一成上下的节点。构建就是逐词 insert：从根往下，算与途经节点的距离，落进对应孩子桶，没有就挂一个新的。复杂度没有严格的多项式上界，最坏（树退化、n 大）还是全遍历，但平均剪枝率非常高，词典几千以上、纠错高频的场景收益明显。

**追问预演**：
- ↳ 查询的剪枝条件怎么推的？→ 目标词 t 与 q 距离 ≤n、与当前节点距离是边权 e，由三角不等式 |d(q,node) - e| ≤ d(q,t) ≤ d(q,node)+e，只有 e ∈ [d-n, d+n] 才可能满足。
- ↳ 什么量级的词典才值得上 BK-tree？→ 几百词直接暴力就行；几千到百万级、且查询高频，剪枝收益才开始盖过树遍历开销——我们演示词典 182 个词其实是边界情形，生产 35 万词项是它的主场。
- ↳ 构建顺序影响树形吗？→ 影响，插入顺序不同树高不同，性能有波动但剪枝性质不变；介意可以对词频排序让高频词靠近根。

**雷点**：别把 BK-tree 说成"二叉树/前缀树"——它按键的整体距离分桶，不是按字符前缀。

### §9.2 编辑距离的 DP 怎么算？复杂度？🔴

**口语答案**：编辑距离是把 a 变成 b 的最少单字符操作数——增、删、改。DP 定义 f[i][j] 是 a 前 i 个字符变 b 前 j 个字符的最小代价：边界 f[0][j]=j、f[i][0]=i；转移三选一——删 a 的一个字符 f[i-1][j]+1、插一个 f[i][j-1]+1、替换或相同 f[i-1][j-1]+cost。时间复杂度 O(n×m)，空间用滚动数组两行交替压到 O(min(n,m))，我们实现里就是 prev、cur 两个 vector 交替 swap。有个必踩的中文坑我是真踩过：UTF-8 一个汉字 3 字节，按字节算距离，"肺节结"到"肺结节"是 3——一个字的替换等于 3 次字节操作，超过我们 max_dist=2 直接不召回，中文纠错整个失效。修法是先用 utfcpp 把两个串切成 Unicode 码点序列，DP 在码点维度做，距离就是正常的 2。多字节文本的任何字节级操作都要过一遍这个检查。

**追问预演**：
- ↳ 还知道什么字符串相似度算法？→ 最长公共子序列 LCS（序列对齐视角）、字符 n-gram 的 Jaccard（集合视角，可进 MinHash）、汉明距离（等长限定）、Soundex 音译码（发音相似，英文人名场景）。
- ↳ DP 能再优化吗？→ 上下界剪枝（带状 DP，距离上界为 n 时只算对角带内）、位向量版 Myers 算法把复杂度压到 O(n·m/64)——纠错场景 n≤2，带状剪枝性价比最高。
- ↳ 非法 UTF-8 输入怎么办？→ utfcpp 切码点会抛异常，我们 catch 后返回一个大距离 64，等效于不参与召回，不能让纠错路径崩掉。

### §9.3 Top-K 建议词为什么用优先队列/小顶堆？🟡

**口语答案**：小顶堆维护 size=k 的候选集：堆顶永远是当前第 k 名，新元素只有比堆顶大才挤掉它——整体 O(n log k)；对比全排序 O(n log n)，n 是全部候选、k 只要 5 或 10，n 大时堆完胜，而且不用把 n 个元素全留在内存。说个代码事实层面的诚实版本：我们项目里小顶堆用在**检索打分**路径——所有命中文档的分数流过 size=10 的 priority_queue 选 TopK，这个是堆的标准应用；BK-tree 建议词路径因为剪枝后候选就几十个，当前实现是 sort 加 resize，量小两者没差别。如果候选规模上去——更大的 max_dist 或更宽的剪枝窗口，同样换堆。这道题的本质是"只需要前 k 个时别做全排序"。

**追问预演**：
- ↳ 堆和部分排序（nth_element）怎么选？→ 只要集合不要序用 nth_element O(n)；要按名次输出用堆；我们的候选还要按 (距离, 词频) 排好序返回，堆弹出天然有序。
- ↳ priority_queue 底层是什么？→ vector 上的 std::push_heap/pop_heap，二叉堆，无序容器迭代不算坑（根本不该迭代它）。

**雷点**：别声称"建议词路径用了优先队列"——代码里是 sort，堆在检索打分路径；被追到代码就诚实讲规模差异。

### §9.4 同距离候选怎么排序？为什么 df 高的优先？🟡

**口语答案**：排序键是 (distance 升序, freq 降序)：先近后远，同样距离内文档频率高的词优先。为什么 df 优先：纠错的目标是猜"用户最可能想打的词"，编辑距离只衡量形近，语言先验要靠词频补——"肺结节"df 几千，冷门术语 df 个位数，医生打错字时 overwhelmingly 是前者。df 的来源很顺：构建 BK-tree 时把索引的 term_df 一起灌进去，每个词条带频次；同词合并时频次累加。这是个很典型的"检索系统的信号融合"小样本：形近（编辑距离）加热门（词频）两个正交信号，一个管候选集一个管排序。

**追问预演**：
- ↳ 为什么不用查询日志共现频次？→ 更好但要有日志闭环；当前用文档频率做无监督代理，是零额外数据的近似。
- ↳ 建议词还能拿去做什么？→ 顺带当"词不存在"的提示——查询零命中时前端展示建议条，引导用户改词（我们的 Web 端就有这个交互）。

## 二、LRU 与两级缓存

### §9.5 🔴 手写一个线程安全的 LRU（"边写边讲"口播稿）

> 这题是手撕高发。下面是口播稿：一边在白板上写，一边按段落讲。总时长控制在 5 分钟内。

**【第一段：先说结构选型，再动笔】**

"写之前先说结构：两个容器配合——std::list 存 pair<Key, Value> 维护**访问序**，队头是最近使用、队尾是最久没用；std::unordered_map<Key, 链表迭代器> 做索引，O(1) 定位到任意节点。为什么这么选：LRU 两个核心动作，'查得快'交给哈希表，'挪得快'交给双向链表——链表删改中间节点只要改前后指针，O(1)。单用哈希表没法维护顺序，单用链表查找 O(n)，所以是组合拳，这也是 LeetCode 146 的标准解。"

**【第二段：写 get，讲 O(1) 的来历】**

"get：先查 map，miss 直接返回 false；命中拿到链表节点迭代器，关键一步是 items_.splice(items_.begin(), items_, it)——把节点从当前位置摘下来接到队头。splice 的珍贵之处是**只动指针不搬数据不拷贝 pair**，所以是 O(1)，这是整个设计里最值得说的一步；如果写的是 erase 加 push_back，pair 被拷贝一次，功能对但白费一次构造析构。然后写出值返回 true。"

**【第三段：写 put，讲淘汰和那个顺序坑】**

"put：key 已存在就更新值、splice 到队头，等价于一次访问；不存在先看容量，满了淘汰 items_.back()——最久未用的天然沉在队尾。这里有个顺序细节：**先 index_.erase(back().first) 再 items_.pop_back()**。反过来的话，pop_back 一执行那个 key 就取不到了、指向节点的 map 迭代器也悬垂了——必须先在链表还活着的时候拿到 key 删索引，再删节点。然后 push_front 新节点，map 里记下 items_.begin() 这个迭代器。"

**【第四段：上锁，讲锁的设计】**

"最后线程安全：一个 std::mutex 护住所有操作，get 进门锁一次、put 进门锁一次，临界区内没有任何 IO。这里有两个高频追问我先答掉：第一，能不能换读写锁？不能——get 也要 splice 改链表，'读'操作本质是写，读写锁没收益反而多开销；要细粒度就是分段锁，哈希分片、每片一段 list 加 map，多线程高并发才值得。第二，这把锁在我们项目里为什么可接受：临界区是一次哈希查找加一次指针搬移，百纳秒级，4 个 IO 线程的检索流量下锁占用率可以忽略——对比 RedisCache 那把锁住网络往返的锁，锁策略要跟着临界区性质走。"

**追问预演**：
- ↳ splice 之后迭代器还有效吗？→ 有效，splice 只重连节点指针，节点本身没销毁，map 里的迭代器继续可用——这正是选 list 的原因之一。
- ↳ get 和 put 各锁几次？→ 各一次，进门 lock_guard 到函数返回；绝不嵌套加锁，避免死锁面。
- ↳ 淘汰回调（比如淘汰时写回）怎么加？→ pop_back 前在锁内拷出 pair，锁外做回调——锁内不做任何可能慢的事。

**雷点**：别用 erase+push_front 替代 splice（暴露不了解 list 特性）；淘汰顺序说反（先 pop_back 再 erase map）当场翻车。

### §9.6 为什么两级缓存？L1/L2 分工？容量和 TTL 各是多少？🔴

**口语答案**：两级是按访问成本排的梯子：L1 是进程内 LRU，容量 512 条、访问百纳秒级，挡最高频的热词；L2 是 Redis，跨进程共享、内网一次往返约 1 毫秒，既挡 L1 没接住的部分，更是为将来 RIS 水平扩实例做铺垫——多个实例共享一份 L2，不重复算；两级都 miss 才走索引，分词加倒排加关联查询是几十毫秒级。效果数字：两级合计命中率约 70%（L1 约 30%、L2 约 40%），命中路径 P99 从索引的 80ms 级降到 L1 的约 5ms。回填顺序：索引 miss 后结果同时写 L1 和 L2（SETEX 300 秒）；L2 命中则回填 L1 再返回。一致性：两级用**完全相同的键**（同一个版本化键字符串）、值是同一份 JSON 串，而值只在索引重建时才会变、重建换版本号换键——所以两级之间不存在新旧值分叉；L1 没有 TTL，512 条很小，靠 LRU 容量淘汰自然翻篇。

**追问预演**：
- ↳ L1 命中但 L2 已过期，算不一致吗？→ 不算——同一个键的值是不可变的（索引不可变），L1 多留一会儿只是多缓存一会儿同一个值。
- ↳ 512 条怎么定的？→ 热词分布集中（病种术语），512 条足以覆盖 L1 那 30% 的命中；大了每条结果串几百字节到几 KB，进程内存要设预算。
- ↳ 为什么 LRU 不是 LFU？→ 医生查询热点跟病种、时段漂移，LRU 贴近期性；LFU 有老化问题，要额外衰减机制才好用。

### §9.7 缓存一致性：版本号进缓存键的原理？不放进键会出什么 bug？🔴

**口语答案**：原理：我们缓存的是"索引的查询结果"，而失效源只有一个——索引重建（索引本身不可变、报告变更走新版本目录）。所以把索引版本号烧进键里：key = "ris:v{版本}:{FNV-1a(查询)}"，重建后版本号变了，所有查询天然落新键、读新索引算的新结果，一致性不需要任何失效逻辑。不放进键的 bug 想象一下：切换后第一次查询命中旧键，返回旧索引的结果——旧文档集、旧权重、被删掉的报告还在里面；更糟的是这个错误结果还会被回填和续期，新旧结果在缓存里按命中顺序交替污染，极难排查。旧键回收靠 TTL 300 秒自然过期，不做主动清理——SCAN 匹配前缀在生产键量级下有开销还跟正常流量抢 Redis，TTL 到期零成本，代价只是旧键多占 5 分钟内存。切换瞬间"一半旧一半新"：单次查询在入口 atomic_load 一次快照、全程用同一个版本，查询内部自洽；跨查询短暂混版本是最终一致，医生重查一次就是新结果，业务可接受。

**追问预演**：
- ↳ 版本号从哪取的？→ 每次检索入口从索引全局槽位 load 当前快照，键和检索用同一个 snap->version，不会错位。
- ↳ 报告当天改了要等凌晨重建？→ 是，当前是准实时换新、凌晨全量的节奏；要实时就上增量段（tombstone + merge），是演进项。
- ↳ TTL 到期前旧键还在被读吗？→ 不会——新查询都带新版本，旧键根本不会再命中，躺着等过期而已。

**雷点**：别把这题答成"先删缓存再更新数据库"那套通用话术——我们的场景失效源是版本切换，版本键是从根上绕开了删缓存问题。

### §9.8 缓存穿透/击穿/雪崩分别是什么？各自怎么防？🔴

**口语答案**：三个都是"缓存没挡住、流量打到后端"的病，病因不同。穿透：查**根本不存在**的键，缓存永远 miss、每次打穿到索引——防法是空结果也缓存（我们的实现天然如此：0 命中的结果串照样进 L1/L2，短 TTL 挡住重复穿透），再加布隆过滤器在词典层挡一道。击穿：某个**热点**键过期瞬间，大量请求同时回源重建——防法互斥重建，一个请求拿锁去算、其他请求等或返回旧值；我们峰值 20 QPS、miss 代价几十毫秒，击穿风险本来就低，这块没做专项，诚实说。雪崩：**大批**键同时到期或 Redis 整体挂掉——防法 TTL 加随机抖动（当前 300 秒固定，是改进点）、多实例打散；Redis 挂的降级我们做了：连接失败静默降级直查索引、只 WARN 一次——缓存是加速器不是依赖，挂了慢一点但服务不倒。

**追问预演**：
- ↳ 布隆过滤器原理？→ 位数组加 k 个哈希函数，插入置 k 个位，查询全 1 才"可能在"；特点是"说没有就一定没有、说有可能误判"，适合挡不存在。我们演示词典 182 个词用不上，生产 35 万词项可以考虑挡"词不在词典"的无效检索。
- ↳ 空结果缓存会不会把错误也缓存住？→ 会——所以空结果 TTL 要短、且只缓存"正常计算出的空"，异常路径不落缓存。
- ↳ 热点 key 怎么发现？→ L1 命中日志按查询词聚合计数，TopN 就是热点榜；真有超级热 key 就本地常驻不过期。

### §9.9 缓存里存的是什么？💣（简历措辞 vs 实现口径）

**口语答案**：实现缓存的是**完整的 JSON 结果串**：query、版本号、count，加 hits 数组——每条含 report_id、患者信息、日期、score、has_image、摘要。为什么是整串：miss 路径贵的不只是检索打分，每条命中还有一次 has_image 的 MySQL 关联查询、摘要生成、JSON 组装——缓存整串让命中路径退化成一次哈希查找加一次 send，收益最大化。如果只缓存 ID 列表，命中后还得回正排表取元数据、重新做关联和组装，命中优势砍掉一半。这里有个口径要主动对齐：简历上写的是"缓存高频查询结果 ID"，准确说缓存的是**含 ID 列表在内的完整查询结果**，本质都是"高频查询结果缓存"，被追问到 value 结构我就按上面讲为什么不存裸 ID。

**追问预演**：
- ↳ 缓存整串，字段需求变了怎么办？→ 响应结构演进靠版本号：索引版本变、键就变，新结构落新键，不存在旧结构污染。
- ↳ value 多大会不会成 Redis 大 key？→ Top10 结果串几 KB 量级，远低于大 key 红线（几十 KB 以上才要警惕）。
- ↳ ID 方案什么时候反而好？→ 结果集巨大、或需要按 ID 二次加工（分页、二次过滤）的场景——我们 Top10 定长，不需要。

**雷点**：面试官问"value 到底是什么"时别含糊——直接说完整结果串并给理由；简历措辞建议改成"缓存高频查询结果"消除偏差。

### §9.10 为什么键里用 FNV-1a 不用 std::hash？🟡

**口语答案**：因为 std::hash 对 string 是**实现相关**的——libstdc++、libc++、MSVC 各算各的，同一版本间也可能变。而我们的 L2 是跨进程共享缓存，多实例、多批次编译部署，今天这个进程算的键明天那个进程必须算得出同一个——键的算法必须跨实现稳定。FNV-1a 64 位正好满足：算法一段乘加循环、分布均匀、任何平台任何编译器结果一致。输出格式化成 16 位十六进制拼进版本化键。碰撞问题也核过：64 位的生日界约 2 的 32 次方次查询才有可观碰撞概率，我们日查询几千次，可以忽略；真要绝对稳可以在键尾拼原查询，代价是键变长、Redis 内存上涨——当前量级不换。

**追问预演**：
- ↳ 碰撞了会发生什么？→ 两个不同查询共用一个键，后写的覆盖先写的、先写的读到别人的结果——概率低到可忽略，但值得知道失败模式。
- ↳ 为什么不用 MD5/SHA？→ 结果要的是稳定散列不是密码学抗碰撞性，FNV 快一个数量级且无依赖。

### §9.11 📐 缓存命中率多少？怎么观测的？📐

**口语答案**：两级合计约 70%，拆开是 L1 约 30%、L2 约 40%。观测是打点日志：每次查询三类 INFO 之一——L1 命中、L2 命中（含回填 L1）、走索引（含耗时），按天聚合就能算出各层比例和走势；L2 写入是 SETEX 带 300 秒 TTL，Redis 侧还能 SCAN 抽样验证版本化键共存。这套数字的用途有两个：一是验证容量和 TTL 配置——L1 命中率上不去先看容量 512 是不是被结果串大小顶爆，二是做变更回归——重建索引后观察命中率回落再爬升的曲线。生产上这些计数应该进 Zabbix 自定义项配告警，比如命中率跌破 50% 就查容量配置和查询模式变化，这是我们监控清单里的项。

**追问预演**：
- ↳ 命中率 70% 意味着什么？→ 70% 的查询在 5ms 内返回，剩下 30% 才吃索引的 80ms P99——平均延迟被大头拉低。
- ↳ 怎么提命中率？→ 加 L1 容量、TTL 调优、查询归一化（大小写/全半角折叠）减少键碎片——最后一条往往收益最大。
