## 🔴 为什么认证拆成独立服务？不拆行不行？

**口语答案**：不拆能跑——把验签和权限判断写进主服务一个中间件函数就够了。拆出去是三个理由：一是横切复用，认证是多个后端共用的能力——归档服务、Web 控制台、以后别的网关接的是同一套账号体系，独立服务加 Consul 发现，谁要谁接入；二是变更隔离，账号、角色、权限矩阵归认证服务管，调权限不用重新发布主服务——后来加 RIS 检索桥接时复用 studies:read 动作，认证服务一行没改；三是接口形态，Login 和 Verify 两个 RPC 用 srpc 加 Protobuf 定义，强类型、接口小而稳定。代价是每个请求多一次同步 RPC——内网毫秒级、当前量级没压力，演进方向是网关本地验签。

**追问预演**：
- 网关每次请求都调认证服务，性能？——同步 RPC 内网约 1 毫秒，导入峰值请求 QPS 才个位数，余量大；上量后演进：JWT 本地验签（secret 配到网关，验签本来就是纯计算）加权限缓存 TTL，只在登录和权限变更时打认证服务。
- 认证服务挂了系统什么表现？——Verify 调不通返回 503 拒服务，fail-closed 是安全默认；AuthGate 把发现结果置失效、下次重查 Consul——服务恢复后自愈。
- 为什么不直接上 APISIX/Kong 这类网关产品？——规模没到；自研 srpc 加 RBAC 代码量不大、和 workflow 生态贴合，可控可调试。

**雷点**：说"认证挂了只影响登录、已登录不受影响"——我们的 Verify 也在认证服务里，每个请求都要调它，挂了是 503 拒服务；能那么说的是"网关本地验签"的演进形态，别把演进当现状讲。

## 🔴 srpc 是什么？和 gRPC 什么关系？为什么选它？

**口语答案**：srpc 是搜狗开源的 C++ RPC 框架，基于 workflow 的任务调度做通信层，支持多协议、其中和 gRPC 兼容——IDL 都是 Protobuf，可以互调。选它的理由很实际：主服务已经是 workflow/wfrest，srpc 和它同家族、共享线程池和任务模型，加一个认证服务不用引入第二套运行时。用法上：proto 文件定义 AuthService 两个方法——Login 进用户名密码出 JWT，Verify 进 token 加 action 出允许与否——srpc 工具生成客户端服务端骨架，我填业务逻辑；网关侧拿生成的 client 同步调用，两端强类型，字段名写错编译期就报错。

**追问预演**：
- ↳ Protobuf 为什么比 JSON 快/小？（varint、字段编号、二进制、无需解析成 DOM）——字段编号替代字段名、varint 变长编码（小整数一字节）、二进制无需文本解析、不用建 DOM 树；同一个 LoginRequest，JSON 带可读字段名几十字节，proto 十几字节。
- ↳ Protobuf 的缺点？（不可读、自描述差、int64 精度坑）——二进制不可读，调试要工具解码；自描述差，没有 schema 读不懂数据；int64 到 JavaScript 有精度丢失的经典坑；不适合写给人看的东西。
- C++ 侧接入 Protobuf 有什么实际体会？——生成代码提交仓库（auth.pb.h/.cc、auth.srpc.h），团队克隆即编；生成命令收在 scripts/gen_proto.sh，接口变更走重新生成加 review。

### ↳ proto 文件怎么写的？字段编号有什么规则？协议怎么向后兼容？（reserved）

**口语答案**：proto3 语法，package pacs.auth。两个请求两个响应加一个 service 定义：LoginRequest 就是 username 加 password 两个字段；VerifyRequest 是 token 加 action——action 是 RBAC 的动作串，比如 images:import、studies:read。字段编号的规则：编号是线上二进制格式的锚点，1 到 15 只占一字节 varint，所以高频字段放小编号；编号一经发布不能改语义。向后兼容两条路：新增字段用新编号，旧代码读新消息按 proto3 语义忽略未知字段，双向兼容；废弃字段用 reserved 把编号和名字都锁掉，防止后人复用踩线格式冲突。

**追问预演**：
- 字段编号用完了怎么办？——proto3 从 19000 到 19999 是保留段不能用；真用完开新 message 拆分，或者上 extensions 思路——实际到不了那个量级。
- required/optional 在 proto3 怎么处理？——proto3 砍了 required（历史教训：必填字段让兼容变成灾难）；字段都有默认值，业务校验挪到服务端代码里做——Login 的空用户名就是服务里判的。
- 同一编号改类型行不行？——不行，wire type 变了线格式就崩；要么新编号要么新 message。

## 🔴 Consul 在链路里做什么？服务注册和发现的完整流程？

**口语答案**：两个动作。注册：认证服务启动后向 Consul 注册 pacs-auth——服务名、自报地址（环境变量注入，容器网络里是主机名）、端口、tags，配 TCP 健康检查：间隔 10 秒、超时 3 秒，Consul 主动连端口探活，连不上就标不健康。发现：网关侧 AuthGate 解析认证服务地址走三级回落——第一级环境变量 PACS_AUTH_ADDR 显式指定，部署调试最直接；第二级查 Consul 的 health 接口，只返回通过健康检查的实例，下线节点自动剔除；第三级都失败回落默认本机地址。发现结果缓存着用，调用失败返回 503 时置失效、下次重查——服务漂移能自愈。

**追问预演**：
- ↳ 健康检查怎么配的？为什么 TCP 检查不是 HTTP？（✅§9：srpc 二进制无 HTTP 端点）——srpc 是二进制 RPC 没有 HTTP 端点可探，TCP 探活判进程加端口的存活；局限是探不到应用层假死（线程卡死但端口还在 accept），应用层健康要业务心跳，是已知演进点。
- ↳ Consul 挂了怎么办？（✅§9：三级回落：env > Consul health > 默认地址）——网关回落默认地址照样调，存量流量不受影响；影响的是新实例注册和失效节点剔除——所以发现链路是增强不是硬依赖，这是设计时刻意保的降级路径。
- ↳ 为什么 Consul 不是 etcd/ZooKeeper/nacos？——Consul 开箱带健康检查和 HTTP/DNS 接口，服务发现场景最省事；etcd 强一致更适合当元数据存储；ZooKeeper 客户端重、运维老；nacos 偏 Java 生态。内网服务发现对 CP 的极端要求不高，选运维面最顺的。

**雷点**：C++ 接 Consul 有一个可讲的坑——ppconsul 的 Health 和 Agent 是独立构造不是 consul.xxx 访问器、Tags 是 std::set 不是 vector——API 形态和直觉不一样，被追问"接入有什么坑"时拿这个垫。

## 🔴 JWT 的结构？三段分别是什么？

**口语答案**：三段点分：base64url(header).base64url(payload).signature。header 声明算法类型，我们固定 {"alg":"HS256","typ":"JWT"}；payload 放声明——我们签了四个：sub 用户名、role 角色、iat 签发时间、exp 过期时间，TTL 两小时；第三段是 HMAC-SHA256(secret, 前两段拼接)，对 header 和 payload 整体防篡改——改任何一个字节签名就对不上。base64url 是换 URL 安全字符表、去掉填充的标准变体。验签流程：拆三段、重算 HMAC 比对——比对用 CRYPTO_memcmp 常数时间比较，防时序侧信道逐字节猜签名——再解 payload 校验 exp。这套是我们手写的约 150 行：OpenSSL 出 HMAC 和安全比较，不引 jwt-cpp，每个字节都看得懂。

**【事故叙述·token 里混进了换行】**（60–90 秒）
认证链路我踩过一个"工具输出污染数据"的坑。做联调时用 --login 命令拿 token 再塞进 Authorization 头，请求一律 400 非法头。curl 手动放 token 是好的，脚本不行——排查发现 token 变量末尾带了个换行：Logger 往 stdout 打日志，脚本把 stdout 整个捕获当 token 用，日志行混了进来。修复是给 Logger 加 set_log_output(stderr)，CLI 工具的 stdout 从此只有机读结果。这件事我提炼成一句话记着：**工具的 stdout 就是它的 API**——结果走 stdout、诊断走 stderr，这是契约不是习惯，输出通道混用迟早污染数据流。

**追问预演**：
- 为什么手写而不用 jwt-cpp？——JWT 本质就是三段拼接加一次 HMAC，约 150 行可控可讲；OpenSSL 出 HMAC 和安全比较，不引额外依赖；手写还顺带免疫了 alg:none 这类库的算法分派漏洞（见雷点）。
- base64url 和 base64 差在哪？——字符表把 + / 换成 - _（URL 安全）、去掉 = 填充；JWT 三个部分都可能出现在 URL 或头里，所以必须 URL 安全变体。
- payload 加密吗？——不加密只签名：payload 是明文（base64 可逆），不能放敏感信息；我们只放 sub/role/iat/exp，role 本来就不是秘密，需要保密就走 JWE，那是另一套。

**雷点**：两个经典 JWT 攻击要接得住：alg:none 攻击（header 的 alg 改成 none 骗不校验的库放行）——我们的手写实现根本不解析 header 声称的算法、固定按 HS256 验，天然免疫；RS256/HS256 混淆攻击（拿服务端公钥当 HMAC 密钥）——同理不存在，因为算法不分派。但别把"手写"吹满——补一句"生产会用成熟库并锁算法白名单"。

### ↳ JWT 和 session 的对比？为什么说 JWT 无状态？

**口语答案**：session 的状态在服务端（内存或 Redis），请求带 sessionId 回查一次；JWT 的"状态"全在 token 里，验签是纯计算、不查任何存储——这就是无状态。好处直接：服务水平扩容不用粘会话、不用共享会话存储，网关本地就能验。代价也直接：注销难——token 发出去在 TTL 内就一直有效，服务端单方面作废需要额外机制；权限变更不能即时生效，只能等 token 过期或短 TTL 缓冲。所以我的总结是：JWT 和 session 不是谁更安全，是用"无状态的可扩展性"换"状态管理的灵活性"，按场景选。

**追问预演**：
- 多系统单点登录 JWT 是不是更顺？——是，同一个 token 谁能验签谁就能认——这正是我们拆认证服务加多接入方的场景。
- token 泄露和 sessionId 泄露后果差多少？——session 泄露可以服务端踢（删 session 即失效）；JWT 泄露在 TTL 内没法低成本作废——所以 JWT 要配短 TTL。
- 无状态是不是就不用 Redis 了？——验签不用；但注销黑名单、refresh token 管理还是绕回 Redis——"无状态"指的是验签路径，不是整个体系。

### ↳ JWT 怎么注销/续期？（✅§9：短 TTL / Redis 黑名单记 jti / refresh token）

**口语答案**：诚实讲现状：当前靠短 TTL 两小时自然过期，没有主动注销——演示和内网场景下够用，这是我明确知道的边界。真要做注销，标准方案是黑名单：签发时给 token 加一个 jti（令牌唯一 ID），注销时把 jti 写进 Redis 并设不长于 TTL 的过期，验签时多查一次 Redis——等于只对"注销过的 token"重新引入状态，绝大多数请求还是无状态。续期用 refresh token 双令牌：access token 短 TTL 管安全，refresh token 长 TTL 管体验、可撤销可轮换——登录换 access、快过期拿 refresh 换新 access。这两个方案的取舍我能画图讲清楚，不是背名词。

**追问预演**：
- 黑名单会不会把"无状态"优势全吃掉？——不会：黑名单只存注销过的少数 jti，容量小、查询快；且 TTL 到期自动清理——是"按需付费"的状态。
- jti 现在有吗？——当前 payload 只有 sub/role/iat/exp，做黑名单前要先在签发侧加 jti（见文末发现的问题第 3 条，面试就按"加 jti 之后"讲）。
- refresh token 存哪、怎么防偷？——存 httpOnly cookie 或安全存储、绑定设备指纹、一次性使用加轮换——偷到旧 refresh 立刻失效。

### ↳ secret 泄露怎么办？HS256 和 RS256 的区别与演进？

**口语答案**：泄露的第一反应是轮换 secret：换成新值，所有旧 token 签名全部失效，业务上等价于强制全量重新登录——可以接受，但这是粗粒度的核弹。根本性演进是 HS256 换 RS256：HS256 对称密钥，签和验是同一个 secret，验签方多了 secret 就扩散了，泄露面大；RS256 非对称，私钥只在签发方（认证服务）手里，公钥随便发——网关们拿公钥本地验签，既解决了"每请求 RPC"的性能问题，又把签发权集中——这是我们这套架构明确的演进方向，两件事是同一个演进。

**追问预演**：
- 多服务各自验签后权限矩阵怎么办？——RBAC 判定可以留在 token 的 role 加本地缓存的矩阵快照，变更时推失效——权限集中管理、判定分布执行。
- 轮换期间新旧 secret 并存怎么做？——验签按 kid（key ID）试一圈：header 带 kid 指明用哪把钥匙，灰度期双钥并存、过期撤旧。
- 我们 secret 现在怎么管的？——环境变量 PACS_JWT_SECRET 注入，不进代码库；没设置时回落开发默认值并打 WARN 拒绝静默——配置红线和口径一致。

### ↳ 签名防篡改，防重放吗？传输是 HTTPS 吗？

**口语答案**：要分清：签名防的是"内容被改"，不防"原样重放"——同一个合法 token 在 TTL 内原样重发，每次都验签通过，防重放要 nonce 加时间戳窗口、或 mTLS 这类通道级手段，我们没做，这是已知边界。传输层面诚实讲：当前是内网 HTTP——医院内网封闭环境的现实取舍，加签不加密在内网也不能算安全完备，中间人可以读到 token 再重放；演进路径是内网 TLS（服务间 mTLS 或至少网关到认证服务加密），上了 TLS 之后防重放的问题也小一大截——攻击者拿不到 token。这两条我主动摆出来，不等面试官戳。

**追问预演**：
- 为什么当时不做 TLS？——内网封闭、证书管理和性能成本、攻击面判断——是排序结果不是遗漏；诚实的说法是"威胁模型里排后"。
- 真要防重放最小改动是什么？——敏感接口加 nonce 缓存去重加时间戳容差窗口（比如正负 30 秒），Redis 一张表的事。
- JWT 放 URL 里传过吗？——没有，一律 Authorization 头——URL 会进访问日志和浏览器历史，是 token 泄露的经典途径。

### ↳ 前端 token 存哪？localStorage 的 XSS 风险 vs cookie 的 CSRF？

**口语答案**：当前是 localStorage 加 Authorization Bearer，401 全局拦截清会话跳登录。两个方案的账要对着算：localStorage 能被 XSS 脚本读走——一旦有注入，token 就漏；httpOnly cookie JS 读不到，天然挡 XSS 偷 token，但又打开 CSRF 的门——cookie 会随请求自动带出，要配 SameSite 加 CSRF token 才干净。我们的取舍：演示场景自控前端、无第三方脚本，选了简单的 localStorage；生产演进是 httpOnly cookie 加 SameSite=Strict 加 CSRF token。关键认知：**两种方案只是换了要防的攻击，没有免费的安全**——能这么对比着讲，比站队任何一个都值钱。

**追问预演**：
- XSS 怎么防？——输出转义、CSP、不 innerHTML 插用户数据——token 存储只是 XSS 的最后一道损失控制，第一道是防注入本身。
- 401 拦截和 token 过期的预检？——前端按 exp 预检提前静默续期或直接弹登录，避免请求打到一半才发现过期。
- 多标签页会话同步？——storage 事件广播登录态，一端登出全端登出。

## 🔴 RBAC 怎么设计的？角色-权限矩阵放哪？

**口语答案**：最简两级模型：角色到动作。动作是"资源:操作"格式的字符串——images:import 导入、studies:read 检索、backup:manage 备份管理；角色两种：radiologist 有导入和检索，admin 全放行，未知角色默认拒绝。矩阵放在认证服务的 Verify 里：网关把 token 和想做的 action 传过来，验签通过后按矩阵判 allowed——网关只传不判。放这里的好处是权限变更不动网关代码：加 RIS 桥接时复用 studies:read，admin 和 radiologist 都能检索、备份页仍只有 admin 能看，认证服务的矩阵一行没改。"集中判定、网关无脑"这个分工是这套设计里我最满意的点。

**追问预演**：
- ↳ 为什么权限放认证服务不放网关？（✅§9：权限变更不动网关代码）——放网关，每个接入方都要复制一份权限逻辑，改一次权限发一圈服务，还会漂移出不一致；集中到验签的同一处，权限跟着 token 的 role 走，单一事实源。
- ↳ 新增一个角色要改几处？——诚实讲三处：role_allows 加分支、user_account 的 CHECK 约束扩枚举（DDL）、种子数据，还要重新编译认证服务——矩阵挪进数据库或配置是明确演进点；当前两角色五六个动作，一个纯函数直白到一眼看穿，量级没到不值得上策略引擎。
- 为什么不是 ABAC / Casbin？——属性级权限和策略引擎在多租户、复杂授权时才回本；两级角色加默认拒绝，可审计性最好。

**雷点**：吹"权限矩阵配置化、可热更新"——代码是编译期硬编码加数据库 CHECK 约束，没有配置化；主动讲"矩阵入库"是演进点，比吹破了被追问强。

## 🟡 PBKDF2 为什么选它？和 bcrypt/argon2 比？（✅§9）

**口语答案**：直接原因：OpenSSL 原生提供 PKCS5_PBKDF2_HMAC，不引新依赖——和 bcrypt、argon2 比安全性同一档：argon2 更现代（抗 GPU、可调内存硬度），bcrypt 应用最广，但都要加库。参数：HMAC-SHA256、10 万次迭代、每用户 16 字节独立随机盐、输出 32 字节，盐和哈希以十六进制存 user_account 表。安全逻辑两条：独立盐让同样的密码在不同用户那存出的哈希不同，彩虹表（预计算的密码-哈希对照表）直接失效；10 万次迭代把单次校验拖到几十毫秒，人肉登录无感，GPU 批量猜测的成本被抬高几个量级。哈希比对同样用 CRYPTO_memcmp——密码比较也要防时序。

**追问预演**：
- ↳ 盐的作用？为什么每用户独立盐？彩虹表原理？——彩虹表是预计算"密码→哈希"的大对照表，撞库直接反查；加盐让哈希输入变成"密码加盐"，表只能针对固定盐预计算——共享盐等于给攻击者一次计算打全库，独立盐把成本乘以用户数。
- ↳ 10 万次迭代不慢吗？（登录低频 vs 每请求验签——两层分开讲）——登录是低频人肉操作，几十毫秒无感；要和每请求验签分开：验签是 JWT 的一次 HMAC，微秒级——两个成本差三四个数量级，别混为一谈。
- 迭代次数以后要提升怎么办？——登录成功时懒重哈希：用新参数重算存回，老用户无感迁移，不用批量刷库。

## 🟡 登录接口防暴力破解/限流做过吗？（⚠️ 未做，备演进口径）

**口语答案**：诚实说，系统性的限流当前没做，这是已知缺口，不装。已有的两道弱防线：PBKDF2 单次校验几十毫秒，在线爆破天然被拖慢；登录失败有日志（带用户名）可事后审计。演进口径我能完整讲：按用户名和来源 IP 两个维度限流——Redis 计数器加 TTL 窗口，比如 5 次失败锁 10 分钟；再加失败递增延迟或验证码；对外暴露的话上风控。它排后的原因是场景：医院内网、低频人肉登录，威胁模型里爆破优先级不高——但这个权衡我会主动摆出来，不等面试官戳。

**追问预演**：
- 限流具体怎么实现？——Redis INCR 加 EXPIRE 固定窗口最简单；要平滑用滑动窗口（ZSET 存时间戳）；超阈值返回统一文案，别把"被限流"和"密码错"做成可区分的响应。
- 按用户名锁会不会被恶意利用？——会：攻击者故意输错把别人账号锁死，是 DoS 面；组合拳是 IP 维度硬锁、用户名维度软限制（延迟递增），锁定提示统一。
- 内网是不是就不用做？——不是"不用"是"优先级后排"——威胁模型决定排序，不代表零风险（内网也有社工和横向移动），分寸要讲准。

**雷点**：硬吹"做了限流"——追问 Redis 键怎么设计、阈值多少、误锁怎么办，三个问题就穿帮；诚实缺口加完整演进口径才是这道题的正确打开方式。

## 🟡 为什么登录错误文案是统一的"用户名或密码错误"？（✅§9：用户枚举防护）

**口语答案**：防用户枚举。如果"用户不存在"和"密码错误"分开返回，攻击者就能批量探测哪些用户名有效，把爆破的搜索空间砍掉一个量级——统一文案把两条路径抹成一样的。配套细节：参数校验失败（为空）返回同款文案；查无此人和密码错误走同一个响应；用户名带引号这类异常输入也返回同一句。日志里则区分记录（密码错误记 user），人能查、接口不泄露——"接口不区分、日志区分"的分层是安全设计的基本功。

**追问预演**：
- 时间侧信道怎么回事？——若用户不存在就跳过 PBKDF2 快速返回，响应耗时差就成了存在性 oracle——彻底做法是查不到也跑一遍哑哈希把耗时拉平；我们当前"查无此人"确实少算一次 PBKDF2，严格说有微小时差，哑计算列在改进项里。
- 注册、找回密码这些接口同样适用吗？——适用，凡是"按用户名查库再返回"的接口都要过一遍枚举检查——找回密码尤其经典（"该手机号未注册"）。
- 和限流是什么关系？——枚举防护让每次探测都要付全价（密码也要试），限流让探测被切断——两层叠加才完整，单独任何一层都能被磨穿。

## 发现的问题

1. **Login 的 SQL 是拼接不是参数化**：`auth/main.cpp` 用 snprintf 把 username 直接拼进 SQL，防线是执行前"用户名含单双引号即拒绝"。引号被拒后 OR 注入没有空间，但**反斜杠未过滤**——MySQL 默认把反斜杠当转义符，用户名带反斜杠会拼出语法错误的 SQL、走"内部错误"分支，与"用户名或密码错误"可区分，构成一个弱存在性 oracle。改进：预处理语句或 mysql_real_escape_string。面试被问 SQL 注入防护时按"现有过滤加已知改进项"口径讲，不要说"我们参数化了"。
2. **RBAC 矩阵硬编码与"权限变更不动网关"的表述**：卖点成立（网关确实零改动），但变更不是零成本——要改认证服务代码（role_allows 分支）加 user_account 的 CHECK 约束（chk_role 限定 radiologist/admin 两值，扩角色是 DDL）再重新编译。答案已按"三处 + 演进：矩阵入库"口径处理。
3. **JWT payload 无 jti**：注销演进口径说"Redis 黑名单记 jti"，但当前签发侧 payload 只有 sub/role/iat/exp（`auth/Jwt.cpp`），没有 jti 字段——真做黑名单要先在签发侧加 jti。讲注销时用"加 jti 之后"的前置说法（本文件相应答案已按此表述）。
4. **AuthGate 全局互斥锁**：所有请求的鉴权在一把 mutex 后排队（srpc 同步客户端非线程安全，`AuthGate.h` 注释已自认）——当前 QPS 无压力，是明确的并发瓶颈演进点（客户端池或网关本地验签）。口语答案在"拆分理由"和"性能"追问里已有对应口径。
5. **Consul 多实例无负载均衡**：`AuthGate.cpp` 的 consul_lookup 取 health 结果的 front()，多实例部署时永远打第一个——当前单实例无影响，扩容要改轮询或随机。被问"多实例怎么分流"时按此坦白。
6. **时间侧信道未完全拉平**（"登录错误文案"题追问已展开）：用户不存在时跳过 PBKDF2，存在微小时差——弹药库 §9 未提这一点，本文件按"已知改进项（哑哈希拉平）"补充口径。
7. **secret 有开发默认值**："dev-only-secret-change-me"，仅当 PACS_JWT_SECRET 未设置时回落并打 WARN——与口径文件"凭据走环境变量"的红线一致（启动告警兜底，拒绝静默），可当正面小讲点使用，无矛盾。
8. **网关侧还有 POST /api/v1/auth/login 同步 srpc 调用**（`src/main.cpp`，Web 控制台登录链路，与 AuthGate::authorize 同为同步形态、占一个 handler 线程）：题库未单列此题，被问"登录入口在哪"时按"网关 HTTP 转发、认证服务执行校验"讲，与弹药库 §13 口径一致，无矛盾。
9. **口径核对**：TTL 2 小时（代码 ttl=7200）、PBKDF2 十万次迭代加 16 字节盐、Consul TCP 检查 10 秒间隔 3 秒超时、同步 RPC 内网约 1 毫秒（弹药库 §9）均与代码一致，无矛盾；题库 §5 标注的 ✅§9 参考答案与代码全部对得上。
