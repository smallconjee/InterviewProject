## 一、智能指针 / 移动语义 / Lambda / RAII

### §13.1 unique_ptr / shared_ptr / weak_ptr 分别什么语义？🔴

**口语答案**：三种语义对应三种所有权模型。unique_ptr 是独占所有权——同一时刻只有一个持有者，不能拷贝只能移动，没有引用计数，大小就是裸指针，零开销，默认首选；析构即释放，还支持自定义删除器（数组特化会调 delete[]）。shared_ptr 是共享所有权——多个 shared_ptr 指同一对象，靠控制块里的引用计数管理：拷贝加一、析构减一、归零析构对象，适合所有权不明确、多方可持有、生命周期要"最后一个放手的人关灯"的场景。weak_ptr 是观察不拥有——从 shared_ptr 构造但不增加强计数，专门解决两个问题：一是打破循环引用，二是"我想用但不决定它活多久"的观察者场景。我项目里 shared_ptr 是主角：索引快照用 shared_ptr<const IndexSnapshot> 全局持有，检索线程每次 load 一份；muduo 的 TcpConnectionPtr 也是 shared_ptr，连接生命周期由库和回调共同持有——最后一个放手才真正关 fd。

**追问预演**：
- ↳ 默认选哪个？→ 所有权能明确就 unique_ptr，零开销；真正需要共享再上 shared_ptr——它是"设计没想清楚所有权"的信号之一。
- ↳ shared_ptr 能线程安全地跨线程传吗？→ 移动/值传递的"不同实例"没问题；两个线程同时读写**同一个** shared_ptr 对象要用 atomic 自由函数，见 §13.2。

### §13.2 shared_ptr 引用计数怎么实现？计数本身线程安全吗？控制块是什么？make_shared 的区别？🔴

**口语答案**：shared_ptr 除了对象指针，还有第二个指针指向堆上的控制块：里面有强计数（shared 数）和弱计数（weak 数），强计数归零析构对象，弱计数也归零才释放控制块内存。计数用的是原子操作，所以**计数本身**线程安全——多线程各持一份拷贝并发增减不会崩；但两层不安全要说清：所指对象不安全，两个线程同时写同一对象照样要自己加锁；同一个 shared_ptr 实例被一个线程读、另一个线程写（重置、赋值）也不安全——这种场景要用 C++ 提供的 atomic_load/atomic_store 自由函数，我项目里索引切换正是这么用的：构建线程 atomic_store 新快照，检索线程 atomic_load，两边操作的是同一个全局 shared_ptr 槽位，自由函数保证安全。make_shared 和 new 加 shared_ptr 的区别：后者两次堆分配——对象一次、控制块一次；make_shared 一次分配把对象和控制块放同块内存，更快更缓存友好，还是异常安全的（函数调用参数求值序里 new 可能泄漏的坑它天然没有）。缺点是反直觉的一点：有 weak_ptr 长寿时，对象虽然析构了，但那块合并内存要等弱计数归零才能释放——大对象加长期观察者的组合，反而该用 new 版。

**追问预演**：
- ↳ 引用计数是原子的，为什么 mutex 还需要？→ 计数原子只保证"指针管理不崩"，不保证数据访问互斥——并发写对象照样竞争，锁保护的是业务不变式不是指针。
- ↳ enable_shared_from_this 是什么？→ 对象内部需要拿到管理自己的 shared_ptr 时（比如异步回调里保活自己），直接用成员 shared_ptr 会造成两个独立控制块；它通过 weak_ptr 记录控制块，shared_from_this() 安全提升——muduo 的 TcpConnection 就是这套。

### §13.3 循环引用怎么破？weak_ptr 的 lock() 和 expired() 怎么用？项目里哪里用了 shared_ptr？🔴

**口语答案**：循环引用是 A 持有 B 的 shared_ptr、B 又持有 A 的，两边强计数互相托着永远到不了零，双双泄漏——典型场景是观察者回调和双向父子关系。破法是把"回指"的一方降级成 weak_ptr：父持子用 shared（父决定子生死），子回指父用 weak（我只是用，不参与决定），或观察者模式里被观察方对观察者持 weak。用法上 lock() 和 expired() 有个重要区别：expired() 只做判断，判断完对象可能在下一行就被别人释放——检查再用是竞态；正确姿势一律是 lock()：它原子地"判断计数加提升"，成功返回一个真 shared_ptr（这段时间对象被你保活），失败返回空。所以代码永远写 if (auto sp = wp.lock()) { 用 sp }。我项目里 shared_ptr 三个真实用例都能讲：第一，最得意的是索引版本切换——构建线程造新快照 atomic_store 进全局槽位，在飞的检索线程还持有旧快照的局部拷贝，继续查旧索引查完为止，析构时引用计数减一，最后一个使用者的那次析构自动释放整棵旧索引——不用任何锁实现"切换瞬间无撕裂、旧版本延迟释放"；第二，每连接一个 TLV 解码器存 map<string, shared_ptr<TlvDecoder>>，onMessage 先在锁内拷出 shared_ptr 再锁外使用，断连 erase 后若还有请求在用，对象照样活着；第三，muduo 的连接对象本身。

**追问预演**：
- ↳ atomic_store 和直接赋值的区别？→ 直接赋值是"读写同一个 shared_ptr 实例"，多线程下指针的两个字段（对象指针加控制块指针）撕裂就完了；atomic 自由函数内部用 CAS 或锁保证整个指针原子替换。
- ↳ 旧索引什么时候真正释放？→ 最后一个持有者析构时——通常是最后一个跨版本的检索请求返回后，new 出来的 80 万文档快照整棵析构，几 GB 级内存回收对分配器也是压力，所以重建在凌晨低峰做。

### §13.4 移动语义解决什么问题？std::move 实际做了什么？🔴

**口语答案**：解决"拷贝浪费"。C++ 里值语义默认拷贝，但很多资源型的东西——堆缓冲、文件句柄、连接、锁的所有权——复制既昂贵又语义错误，以前只能传指针绕开。移动语义给了语言级方案：对象可以把内部资源"移交"给新对象，自己变成空壳，移动 string/vector 是 O(1) 交指针，不是深拷贝。std::move 本身一句话讲透：它不移动任何东西，只是 static_cast<T&&> 把表达式变成右值——作用是让重载决议去选移动构造/移动赋值这个版本，真正搬资源的是移动构造函数里的代码（接管指针、源置空）。工程收益两个：第一，容器和返回值——vector 扩容时元素有 noexcept 移动就搬指针不拷数据，函数按值返回大对象零成本；第二，所有权类型设计——不可拷贝只可移动的类型把"唯一持有权"表达成类型系统约束。我项目里的实战就是 MySQLGuard：acquire 按值返回、Guard 在调用链传递，全程移动，连接从没被拷贝过。

**追问预演**：
- ↳ 移动构造为什么要标 noexcept？→ vector 扩容时只有 noexcept 移动才敢用移动搬元素——否则移动一半抛异常，旧数据已破坏无法回滚，会退化成拷贝；std::move_if_noexcept 机制。
- ↳ C++11 之前怎么模拟移动？→ auto_ptr 是失败的尝试（拷贝构造偷偷转移所有权），swap 惯用法、手工 reset——都是移动语义要解决的痛点。

### §13.5 MySQLGuard 为什么禁拷贝、只留移动？move 之后的源对象什么状态？🔴

**口语答案**：Guard 的语义是"独占一条借出连接的归还权"。拷贝的危害推一遍：两个 Guard 指向同一连接，各自析构都调 release，同一连接入队两次——之后两个线程同时借出它并发写同一个 MySQL 会话，会话状态错乱，这是正确性事故。所以拷贝构造和拷贝赋值 =delete，一步到位禁止。移动构造则是合法且必要的：接管 pool_ 和 conn_ 两个指针，源对象的两个指针立刻置 NULL，析构和 reset() 都先判空再动作——归还权完成交接，全程唯一。move 之后源对象处于"有效但未指定"状态（标准给的说法），在我们的实现里明确约定：置空后的 Guard 的 operator bool 返回 false，是个安全的空 Guard。这是标准库 unique_ptr 的同款设计模式，等于给"连接归还"这个动作手写了一个专用 unique_ptr；移动赋值还处理了自赋值和"先归还当前再接管"（先 reset 再偷指针）。acquire 按值返回时编译器自动选移动构造，这就是 C++11 之前做不到的零拷贝传递。

**追问预演**：
- ↳ =delete 和私有不实现有什么区别？→ =delete 是 C++11 的显式删除，任何代码尝试拷贝直接编译错（包括成员和友元）；私有不实现是老 hack，友元和类内还能绕。
- ↳ 如果 Guard 需要 put 进容器怎么办？→ 正好移动语义支持——vector<MySQLGuard> 用 push_back(std::move(g))，拷贝被禁止的约束在容器里同样成立。

### §13.6 右值引用和万能引用的区别？std::forward 干什么的？RVO/NRVO？🟡

**口语答案**：右值引用是 T&& 这个类型，但"长得像右值引用"的有两种：在模板推导语境 T&&（或 auto&&）里它是万能引用——传左值时 T 推导成 T&，引用折叠后整个变成左值引用；传右值时 T 是 T，保持右值引用。不在推导语境的 Widget&& 就是纯右值引用，只能绑右值。std::forward 配合万能引用做完美转发：转发函数把参数原样传给下一层时，用 forward<T> 保持调用方原本的值类别——原来是左值就还是左值（可以继续被移动前先使用），原来是右值就还原成右值（触发下游移动）；std::move 是无条件转右值，forward 是有条件转。RVO/NRVO 是编译器的拷贝消除：返回局部对象时直接在调用方的存储上构造，连移动都省了；NRVO 针对具名局部变量，非强制但主流编译器都做，C++17 起纯右值返回是语言保证。由此有个高频陷阱：return std::move(local) 是画蛇添足——它把返回语句从"NRVO 候选"变成"用一个 xvalue 初始化返回值"，反而禁用了消除，千万别写；按值返回局部变量写裸 return 就是最优。

**追问预演**：
- ↳ 引用折叠规则？→ 四种组合 T& &、T& &&、T&& & 都折成 T&，只有 T&& && 折成 T&&——"有一个左值引用就是左值引用"。
- ↳ 项目里用到完美转发了吗？→ C++11 项目里少，我的用例是移动构造本身；标准库内部的 forward（make_shared、容器 emplace、bind 的参数存储）大量在用——能指出来源就行。

### §13.7 Lambda 的捕获方式？[=] [&] [this] 的区别和坑？🔴

**口语答案**：捕获列表决定 lambda 外部变量怎么进闭包：[] 不捕获、[=] 按值拷贝局部变量、[&] 按引用、[this] 捕获 this 指针（成员函数里 [=] 默认也是捕获 this 指针，不是拷贝整个对象）、还能 [x, &y] 混合指定。三个坑按踩的概率排：第一，[&] 捕获引用后 lambda 异步执行——局部变量早死了，闭包里的引用悬挂，UB；同步场景（马上调用的回调）没事。第二，[=] 捕获 this 的陷阱——拷贝的是 this **指针**，不是对象；lambda 活得比对象久时，通过指针访问成员照样悬挂，C++11 没有解法（C++14 初始化捕获、C++17 的 [*this] 拷贝对象才解决）。第三，C++11 没有移动捕获——想把 move-only 对象给 lambda 只能靠 shared_ptr 包一层（C++14 的 [m = std::move(x)] 才补上）。我项目两个对照用例：连接池 acquire 的 wait_for 谓词 [this]{ return !idle_.empty(); }——同步、短生命周期，捕获 this 安全；muduo 的回调统一用 std::bind(&Server::onMessage, this, _1, _2, _3)——bind 同样持有裸 this，安全性靠"server 对象生命周期覆盖 loop"这个更强的前提保证，这是用 muduo 就要遵守的库约定。

**追问预演**：
- ↳ lambda 和 bind 怎么选？→ muduo 生态统一 bind（占位符风格、早期 C++11 代码的常态）；新代码能用 lambda 就用 lambda——类型更清晰、编译器优化更好、捕获语义显式。
- ↳ lambda 的本质是什么？→ 编译器生成的匿名闭包类，捕获变量是它的成员，operator() 按捕获方式访问——无捕获 lambda 可以转函数指针（C 回调桥接用）。
- ↳ 默认捕获 [=] 或 [&] 该用吗？→ 显式逐个捕获更好：读捕获列表就知道依赖了什么、生命周期风险一眼可见——Google 风格禁默认捕获就是这个理由。

### §13.8 RAII 的本质讲一下，项目里举三个实例。🔴

**口语答案**：RAII 的本质一句话：**把资源的生命周期绑定到栈对象的生命周期**——构造获取资源，析构释放资源，而 C++ 保证栈对象在离开作用域时析构（包括异常展开时），于是"每一条退出路径"——正常 return、提前 return、抛异常、作用域结束——都自动走释放逻辑，释放代码只写一次。它解决的是错误处理的老大难：手动 release 在任何一条忘记的路径上都是泄漏。我的项目里 RAII 是基础设施级的存在，举三个：第一，MySQLGuard——构造从池借连接，析构自动归还，SQL 抛异常连接也不泄漏，配合"只移动不拷贝"表达唯一归还权；第二，SHA-256 的 EVP_MD_CTX——OpenSSL 上下文 EVP_MD_CTX_new 分配、EVP_MD_CTX_free 释放，流式分块哈希整个文件的过程中任何一步出错，guard 析构保证上下文不泄漏，裸写 new/free 在多层提前 return 里必漏；第三，staging 临时文件句柄——fopen 拿到 FILE*，封装对象析构 fclose，进程任何路径退出都先关句柄（临时文件本身的清理由 staging 目录扫描兜底）。再送一个反向用例：PACS 的 Logger 一条日志就是一个临时 LogMessage 对象，析构时整行一次 fwrite——RAII 顺带买到了"行原子性"，这是 RAII 思想超出资源管理的延伸用法。

**追问预演**：
- ↳ RAII 和 try/finally、goto cleanup 比好在哪？→ 释放点和错误处理点解耦，编译器保证走析构，人不可能忘；Java 的 try-with-resources、Go 的 defer 都是在追这个保证。
- ↳ 析构函数里能抛异常吗？→ 不能——异常展开中再抛异常直接 terminate；析构里的失败只能吞掉或记日志，所以 RAII 类的析构都设计成 noexcept。

## 二、封装 / 继承 / 多态 / 虚函数

### §13.9 虚函数机制？vptr/vtable 怎么工作的？对象内存布局？🔴

**口语答案**：实现机制三层。编译器给每个**有虚函数的类**生成一张虚函数表 vtable——编译期就定好的只读数据，存该类所有虚函数的实际地址，通常还带 typeinfo；每个对象里塞一个隐藏指针 vptr，指向所属类的 vtable——vptr 在构造函数里被设置（这也是构造函数里多态失效的根源，见下题）。调用 base->f() 时编译器生成：取对象的 vptr、按 f 在表里的偏移取函数地址、间接调用——运行时按对象真实类型分派，这就是动态多态。单继承布局最简单：[vptr][成员变量]，派生类对象先是基类子对象再接自己的成员，所以基类指针能安全切过去；多继承会有多个 vptr（每个含虚函数的基类一份），虚继承还要加虚基类偏移信息。成本三笔：每对象多 8 字节；调用多两次内存间接（vptr 可能 cache miss），间接跳转打断流水线还难以内联——所以热点路径上虚调用可测（但绝大多数场景不构成瓶颈，别过度优化）。

**追问预演**：
- ↳ 虚函数表存在哪、几个对象共享？→ 每类一张（还要区分 most-derived 类），通常在只读数据段；同类所有对象共享，对象里只有 vptr。
- ↳ 构造函数可以是虚的吗？→ 不行——vptr 都靠构造函数设置，鸡生蛋问题；但析构强烈建议虚（下题）。

### §13.10 构造/析构里调虚函数会怎样？基类析构为什么 virtual？菱形继承？🟡

**口语答案**：构造和析构期间多态是"降级"的：基类构造函数执行时，vptr 指向的还是**基类**的 vtable（派生部分尚未出生），这时调用虚函数调到的是基类版本，不是派生类的重写——派生类还没初始化就调它的函数本来也不安全；若基类里是纯虚函数，直接UB（通常链接期报错）。析构对称：派生部分已销毁，vptr 回退到基类表，调的也是基类版本。经验法则：构造/析构里别调虚函数，要那个行为就把逻辑抽成非虚的私有函数显式调。基类析构函数要 virtual 的场景：会通过基类指针 delete 派生对象——不虚的话 delete 只执行基类析构，派生类的资源（堆成员、句柄）全部泄漏，且是未定义行为；反过来可以不加：类不做多态基类（没有虚函数、不被继承、或不通过基类指针删除）。标准库的	string 这类就是"设计上不让你多态继承"的例子。菱形继承：B、C 都继承 A，D 再继承 B、C——D 里有两份 A 子对象，访问 A 成员二义，编译器直接报错；解法是 B、C 虚继承 A（virtual public），让 D 里只保留一份共享的 A，代价是虚继承的实现机制（虚基类表/偏移）带来访问和大小开销，而且 A 要由最终派生类 D 直接初始化。工程实践是尽量不用——用组合或纯接口类替代多重实现继承。

**追问预演**：
- ↳ override 关键字干什么？→ 让编译器校验"确实重写了基类虚函数"——签名拼错、const 不一致时是藏而不是重写，override 把这类 bug 拦在编译期。
- ↳ final 什么时候用？→ 禁止再继承或禁止再重写——既表达设计意图，也帮编译器去虚化优化。

### §13.11 项目里多态用在哪？🟡

**口语答案**：最典型的是 workflow 自定义协议：RisTlvMessage 继承 protocol::ProtocolMessage，重写 encode()（发送方向：6 字节头加 payload 序列化进 iovec）和 append()（接收方向：增量半包解析状态机，告诉框架消费了多少字节）；框架内部拿着 ProtocolMessage 基类指针调我们的实现——它编译时根本不知道 RisTlvMessage 的存在，这就是"框架通过虚函数开放扩展点"的标准形态，等于手写了一个框架插件。另一个可以顺带讲的对照：muduo 的连接/消息回调用的是 std::function 加 bind，不是虚函数——这是多态的另一种形态"类型擦除"，任何签匹配的可调用物都能塞进去，不需要继承关系。被问"为什么这里用虚函数那里用 function"：虚函数适合"一族相关类型、框架定义接口层级"；function 适合"单点回调、注册什么就调什么"——我们两个项目正好一边一个。

**追问预演**：
- ↳ append 的多态契约谁定的？→ workflow 框架：基类声明 append(const void*, size_t, size_t*)，返回解析状态——子类遵守契约，框架回调时分派。
- ↳ 为什么头文件不暴露 jieba/hiredis 类型？→ 前置声明加 void*（Tokenizer 的 jieba_、RedisCache 的 ctx_）——减少编译传染，跟多态无关但常被连着问。

## 三、STL（简历原文句句是题）

### §13.12 vector 扩容机制？push_back 的均摊复杂度？🔴

**口语答案**：vector 维护三个指针：begin、end（已用尾）、capacity_end（容量尾）。push_back 时容量没满就在 end 处构造、指针后移；满了触发扩容：申请一块更大的内存（GCC 翻倍、MSVC 1.5 倍），把旧元素搬过去（元素类型有 noexcept 移动构造就用移动，否则拷贝），释放旧内存。均摊 O(1) 的证明一句话：按几何级数增长，n 次 push_back 的总搬移次数是 1+2+4+...+n < 2n，摊到每次是常数——如果是线性增长（每次加固定个），总代价是平方级，均摊 O(n)。为什么 1.5 或 2 倍：在"均摊常数"和"内存浪费上限"之间折中，1.5 倍还有个经典细节——历史释放的旧块拼起来有机会装下将来的新块（2 倍时永远装不下，黄金分割率是分界）。扩容后**所有**迭代器、指针、引用全部失效——内存搬家了，这是面试最爱考的一句；不扩容的插入只使插入点及之后的失效。reserve 和 resize 的区别：reserve 只保证容量、size 不变、不构造任何元素；resize 改变 size，多出来的元素被值初始化、少了的被析构。我项目里的实践：构建索引时词表、倒排的载入用 reserve 预分配（80 万文档的规模，避免反复扩容搬移），普通小容器交给默认行为。

**追问预演**：
- ↳ 搬移用移动还是拷贝谁决定？→ 元素移动构造是否 noexcept——不 noexcept 就退回拷贝保证强异常安全（搬一半抛了还能不丢数据），std::move_if_noexcept 机制。
- ↳ clear 会缩容吗？→ 不会，只析构元素，capacity 不变；shrink_to_fit 是非强制的请求。vector 的内存高水位要靠 swap 技巧或重新构造。

### §13.13 迭代器失效规则：vector / deque / list / map / unordered_map？🔴

**口语答案**：按"节点型还是连续型"分两半记。连续型 vector：扩容则全部失效；不扩容的插入/删除使**操作点及之后**的失效。deque：头尾插入使所有迭代器失效但**引用和指针仍有效**（分段结构没搬）；中间插入全部失效；删除头尾只使被删元素的引用失效。节点型 list/map（红黑树）：内存里是独立节点，插入不影响任何迭代器；删除只使指向被删元素的失效，其他照样活——erase 返回下一个有效迭代器，删着遍历的标准写法 it = m.erase(it)。unordered_map 要单独记：插入可能触发 rehash——桶数组重建，**迭代器全部失效**，但元素节点没动，**指针和引用仍然有效**（C++11 起保证）；即使不 rehash，标准也说任何插入都可能使迭代器失效，所以迭代器别跨插入持有。我项目里的实际应用全部踩在这套规则上：LruCache 的 map 存的是 list 迭代器——list 的 splice 只重接指针不销毁节点，迭代器始终有效，这正是选 list 做存储层的原因；RIS 的倒排 unordered_map 在构建期一次性填、检索期只读，构建和查询用 atomic 换版本隔离，彻底避开并发改容器这个深水区。

**追问预演**：
- ↳ unordered_map 迭代中插入元素会怎样？→ rehash 一发生就 UB——正确做法先收集后插入；C++17 有 extract 节点再 insert 的 API 可做无失效搬运。
- ↳ deque 为什么引用比迭代器耐用？→ 元素在分段缓冲区里不动，失效的只是"两端迭代器要重新对齐中控数组"这层簿记。

### §13.14 deque 的分段存储结构？为什么头尾插入都是 O(1)？🟡（简历原文点名）

**口语答案**：deque 是"分段连续、整体逻辑连续"的结构：底层是一块中控数组（一小段指针数组），每个指针指向一个固定大小的缓冲区（GCC 每段 512 字节），元素真正住在缓冲区里。头尾插入为什么 O(1)：push_back 时当前尾段还有空位就直接在段内构造；段满了才分配一个新缓冲区挂到中控数组尾部——O(1) 摊销。push_front 对称地在头段前面放，头段满了就新开一段挂前面。只有中控数组本身满了才需要扩容它（指针搬家，代价摊销后仍常数）。随机访问也是 O(1)，但是两级寻址：先按偏移算出"第几段加段内偏移"再做两次访问，所以常数比 vector 大，中间插入删除还要挪半程元素 O(n)。代价换来的就是两头都能高效进出。我项目里现成的用例：MySQL 连接池的空闲队列 idle_ 就是 std::deque<MYSQL*>——归还 push_back、借出 pop_front，两头操作；这里有个选型小讲点：vector 的 pop_front 是 O(n) 全体前移，直接排除；list 也满足，但 deque 的分段存储缓存更友好、每元素没有链表节点的额外指针开销，等价场景下我选 deque。

**追问预演**：
- ↳ deque 迭代器长什么样？→ 比 vector 复杂得多：记着当前段、段内位置、还存中控数组位置以便跨段跳——所以迭代器失效规则也和 vector 不同。
- ↳ 为什么 stack 默认用 deque 不用 vector？→ 标准库 stack 的默认容器就是 deque——头尾操作均衡、且扩容时不需 like vector 的整体搬移策略适配；vector/list 也都能配。

### §13.15 STL 空间配置器的基本原理？🟡（简历原文点名，经典老题）

**口语答案**：以 SGI STL 的经典实现讲，双层结构，按 128 字节分界。一级配置器处理大块（大于 128 字节）和分配失败：内部直接调 malloc/free，malloc 失败时不立刻返回空，而是循环调用 new-handler——用户设置的"内存不够时的处理函数"（释放点缓存、打日志、或直接抛 bad_alloc），给程序自救机会后再重试。二级配置器才是精髓，针对小对象频繁 malloc 的开销和碎片：内部维护 16 条 free list，分别管 8、16、24…128 字节的内存块（需求向上取整到 8 的倍数）。分配时查对应链表，有空闲块直接摘下——零 malloc 调用；没有就向底层的内存池批量要：一次申请 20 个该规格的块（chunk allocation），不够就给能给的，内存池也空了再向一级配置器（最终是 malloc）要堆内存，顺手把余料切给邻近规格。释放不是 free 回系统，而是把块挂回对应 free list 复用。两个漂亮细节能加分：一是 free list 节点用 union 复用空间——空闲时这块内存的前 8 字节当 next 指针用，分配出去后整块都是用户数据，零额外元数据开销；二是配套的 construct/destroy 用 placement new 和显式析构，把"内存分配"和"对象构造"分离。补充一句现状：现代 libstdc++ 的 std::allocator 默认就是 new/delete 的薄封装，池化配置器作为扩展（__gnu_cxx::__pool_alloc）保留可选——所以这题按"经典设计思想"答最稳。

**追问预演**：
- ↳ 为什么 128 字节这个分界？→ 经验值：比这小的对象 malloc 的元数据和管理开销占比过高，且碎片化严重；比这大的块复用收益下降。
- ↳ 这套思想现在还在哪？→ 内存池思想无处不在：tcmalloc/jemalloc 的 size class、Redis 的 zmalloc、我的连接池某种意义上是"连接的池化配置器"——把昂贵资源的创建摊销掉。

### §13.16 unordered_map 哈希冲突怎么解决？什么时候 rehash？负载因子？🔴

**口语答案**：STL 的 unordered_map 用链地址法：一个桶数组，每个桶挂一条单链表（libstdc++ 实现里整张表其实是一条全局 singly-linked list，桶只记各自的起始位置，方便迭代）。哈希冲突的键进同一个桶，查找退化成链表遍历，所以性能的关键是控制链长。负载因子 = size / bucket_count，默认上限 1.0——平均每桶一个元素；插入使负载因子超限时触发 rehash：桶数组扩大（libstdc++ 按内部素数序列约翻倍），所有元素重新散列挂到新桶，迭代器全部失效但指针引用有效。rehash 是一次性的 O(n) 重建，可以 reserve 预分配桶避免；load_factor 接口可查、max_load_factor 可调。迭代过程中插入是高危动作：标准规定任何插入都可能使迭代器失效（rehash 时全失效），先收集后插入是铁律。我项目里 unordered_map 是主力容器：倒排索引 term → 倒排表、词项 df 表、LruCache 的索引层——选它不选 map 的理由很硬：检索路径只需要"按键取值"，O(1) 和 O(log n) 在 35 万词项规模上差着量级，而且不需要有序遍历；索引构建时知道规模，能 reserve 就 reserve。

**追问预演**：
- ↳ 链地址 vs 开放寻址怎么选？→ 链地址删除方便、对负载因子容忍高，但有节点指针开销；开放寻址缓存友好但删除要做墓标、容易聚集。Redis 的 hash 渐进式 rehash 是把 rehash 摊到每次操作的第三条路。
- ↳ 哈希函数怎么影响？→ 分布均匀性直接决定链长；std::hash 对 string 的实现是编译器相关的——所以我缓存键用 FNV-1a 自己算，跨进程稳定才能做共享缓存键。

### §13.17 map 为什么用红黑树不用 AVL？红黑树性质？和 B+ 树的本质区别？🟡

**口语答案**：先背红黑树五条性质：节点非红即黑；根是黑；NIL 叶是黑；红节点的孩子必须黑（不存在连续红）；任一节点到其所有叶子的路径上黑节点数相同（黑高相同）。它用"近似平衡"换维护成本：最长路径不超过最短两倍，保证 O(log n)；对比 AVL 树严格平衡（任一节点左右子树高度差不超过 1），AVL 查询略快（树更矮），但插入删除可能引发从底到根 O(log n) 次旋转，红黑树插入最多 2 次旋转、删除最多 3 次就能修复——增删改查的综合频率下红黑树赢了，STL 的 map/set、内核（epoll 管理 fd、CFS 调度器）都选它。和 B+ 树的本质区别一句话：**红黑树是内存树，B+ 树是磁盘树**。红黑树二叉、节点小、指针密集，访问是随机内存跳转，一次比较一次跳；B+ 树把一个 16KB 页做成一个多路节点，一次 IO 读一大段键，树高三四层就是三四次 IO，节点大小对齐磁盘页和预读，叶子还用链表串起来支持范围扫。数据结构都是为存储介质的访问特性服务的——内存随机访问廉价所以二叉树行；磁盘随机访问昂贵所以要把扇出做大、把树压矮。

**追问预演**：
- ↳ 红黑树的插入修复思路？→ 新节点染红（不动黑高），父黑直接完事；父红分叔叔红/黑几种情况，靠变色和旋转把连续红消掉——能讲出"变色优先、旋转兜底"的层次即可，现场推导别硬上。
- ↳ hash、红黑树、B+ 树三者怎么选？→ 等值无序 hash；内存有序 map；落盘或超大规模 B+ 树——正好把我 LruCache（hash+list）、倒排（unordered_map）、MySQL（B+ 树）三个用例串成一句话。

### §13.18 Top-K 问题：priority_queue 和 sort 怎么选？🟡

**口语答案**：看 n 和 k 的关系与数据到达方式。只要前 k 个、n 又大：小顶堆维护 size=k 的候选集，堆顶是当前第 k 名，新元素比堆顶大才挤掉它，总代价 O(n log k)；全排序是 O(n log n) 还要全部驻留内存，n 大 k 小时浪费明显。如果数据是一次性全量在内存、只要"前 k 不要求有序"，nth_element 部分选择 O(n) 更优；要求按名次输出，堆弹出天然有序。我的项目里两个真实用例正好一题两面：检索打分路径——所有命中文档的分数流过 size=10 的 priority_queue（小顶堆）选 TopK，命中文档可能上千，堆是标准姿势；BK-tree 纠错建议路径——剪枝后候选就几十个，实现是 sort 加 resize，量小两者没差别，硬上堆是过度设计。这题的考点就是"只需要前 k 个时别做全排序"，再加一句量级判断就满分。

**追问预演**：
- ↳ 为什么小顶堆不是大顶堆？→ 要快速淘汰"当前最弱的前 k 候选"——堆顶必须是最弱的守门员，新来的打赢它才能进。
- ↳ 海量数据 Top-K（内存装不下）怎么办？→ 分治：各分片各自 TopK 再归并——堆是归并阶段的天然结构。

## 四、并发编程

### §13.19 互斥锁 / 条件变量 / 信号量各自的语义和使用场景？🔴

**口语答案**：三个原语解决三类问题。互斥锁 mutex 解决**互斥**——同一时刻只有一个线程进临界区，保护共享数据的不变式；语义最简单，默认不可重入（同线程重复加锁直接死锁，需要就 recursive_mutex），拿不到就睡。条件变量 cv 解决**等条件**——"队列非空"这种谓词成立才继续，它必须配一把 mutex 用：wait 时原子地"放锁加睡眠"，被唤醒后重新抢锁——本质是"睡眠等待某条件，醒来时不跟人抢着查"。信号量解决**资源计数**——允许最多 N 个并发（连接数、线程池工人配额），P 减一拿资源、V 加一还资源，计数天然表达"还剩几个"。关系上信号量可以用 mutex 加 cv 合成，C++11 标准库干脆没给信号量（C++20 才有 counting_semaphore），需要自己用 mutex 加 cv 搭。我项目三个都有落点：连接池是 mutex 加 cv 的教科书用例——deque 空闲队列加一把锁，acquire 里 wait_for 带谓词等"队列非空"；LruCache 是单 mutex 护两个容器的不变式；StudyLink 单连接配一把互斥，把并发查询串行化。

**追问预演**：
- ↳ 什么时候用 recursive_mutex？→ 基本不该用——可重入说明临界区边界设计混乱；接口回调重入的场景宁可拆小临界区。
- ↳ lock_guard / unique_lock / scoped_lock 区别？→ lock_guard 零开销不可解锁（默认选它）；unique_lock 可解锁、可移动、能配 cv 的 wait（wait 要求能中途放锁，必须它）；scoped_lock 一次锁多把并防死锁（C++17）。

### §13.20 condition_variable 为什么必须配循环/谓词？notify 没人等去哪了？wait 三步？🔴

**口语答案**：虚假唤醒是操作系统层面的现实：futex 的唤醒允许一次摇醒多个等待者、信号中断也会让 wait 无理由返回——醒来那一刻"条件满足"不成立是常态不是异常，所以醒来第一件事必须是**重新检查谓词**，不满足接着睡。写法就是谓词版 wait：cv.wait_for(lock, timeout, []{ return !idle_.empty(); })，它等价于 while 循环加裸 wait。第二个坑是通知丢失：条件变量没有记忆、不计数——notify 时没人在等，这次通知就蒸发了，它不会存起来给下一个人；所以纪律是**先改共享状态、再 notify**：等待者即使错过通知，下次醒来重查谓词也能看到状态已变。我连接池的 release 就是这么写的：锁内把连接 push_back 回队列、出锁域后 notify_one——被唤醒的线程重查"队列非空"必然成功；反过来先 notify 后改状态，等待者可能醒来查不到连接又睡回去，永远错过。wait 的三步机制：第一步原子地释放 mutex 并把自己挂进等待队列睡眠（这两件事必须原子，否则刚放锁还没睡下时别人 notify，又错过）；第二步被 notify、超时或虚假唤醒；第三步重新竞争 mutex，抢到锁才从 wait 返回——所以醒来时天然持锁，查谓词是安全的。这套三步加谓词循环就是条件变量的全部。

**追问预演**：
- ↳ notify_one 和 notify_all 怎么选？→ 归还一条连接唤醒一个等待者用 notify_one；广播"状态大变"（如退出标志置位）用 notify_all——惊群代价换正确性。
- ↳ spurious wakeup 的底层原因？→ futex 允许多路唤醒、中断返回等实现细节；POSIX 明文允许，所以是必须在应用层防御的契约。

### §13.21 你的线程安全 LRU 锁粒度怎么设计的？🔴

**口语答案**：全模块一把 std::mutex，get 和 put 各进一次门锁到函数返回，临界区里只有哈希查找和指针搬移，没有任何 IO——百纳秒级。为什么不做更细，我按"锁的粒度要跟临界区性质走"这个原则讲三档对比：第一档，LruCache——锁内是纯内存操作，4 个 IO 线程、峰值 20 QPS 的检索流量，争用概率本来就低，单锁的简单性完胜；换读写锁是负优化——get 也要 splice 改链表，"读"本质是写，读写锁的读共享根本用不上还多开销。要真上高并发，方案是分段锁：哈希分片、每片独立 list 加 map，锁冲突按片摊薄——这是量级上去了之后的事。第二档，RedisCache——锁内含一次约 1ms 的网络往返，锁策略就得权衡：为了 hiredis 上下文的线程安全整体互斥，4 线程缓存查询串行化，当前量级可接受，演进方向是每线程独立连接消掉锁。第三档，MySQLPool——干脆把 ping 和重连挪到锁外，锁只管空闲队列出入队，因为 real_connect 可能阻塞 5 秒，持锁执行会拖死全池。三个模块三档策略，比背"锁粒度越小越好"有说服力得多。

**追问预演**：
- ↳ 会不会死锁？→ 全模块单锁、绝不嵌套加锁——两把锁才有环，一把锁无环可成；跨模块调用时先释放自己的锁再调别人。
- ↳ get 返回的 Value 是拷贝，锁外用安全吗？→ 安全，值语义拷贝出来就与共享结构脱钩——这也是接口设计成传出参数而不是返回引用的原因。

### §13.22 std::atomic 是什么原理？CAS？内存序了解吗？🟡

**口语答案**：atomic 提供不可分割、且带跨线程可见性保证的读写。硬件层靠 CPU 原子指令：x86 的 lock 前缀指令（lock cmpxchg、lock xadd），ARM 这类 RISC 用 LL/SC（独占加载/条件存储）对；CAS 就是 compare-and-swap：比较内存值与期望值，相等则换成新值，失败返回失败——编程模型在 C++ 里是 compare_exchange_weak/strong，weak 版允许"值其实相等也失败"的伪失败，配循环用反而更高效。内存序控制的是原子操作**周围**的读写重排约束：默认 seq_cst 顺序一致，最直观最稳；acquire 用在load——后面的读写不能重到它前面；release 用在 store——前面的读写不能漏到它后面，acquire-release 配对形成同步关系；relaxed 只保证原子性不管顺序，用于纯计数。项目用例两个，都用的默认序：PACS 日志全局级别 atomic<int>，读线程过滤、管理接口写，语义就是"最终能看见新值"，默认序绰绰有余；RIS 索引切换用 C++ 的 atomic_store/atomic_load 自由函数操作 shared_ptr——它内部保证整个"对象指针加控制块指针"原子替换。要不要手调内存序：只有无锁算法才深入，业务代码一律 mutex 或默认 seq_cst——先正确后快。

**追问预演**：
- ↳ ABA 问题？→ CAS 之间值从 A 改成 B 又改回 A，CAS 察觉不到"变过"——无锁栈的经典坑；解法是版本号指针（带 tag 的指针），std::atomic 没内置，得自己包。
- ↳ atomic 和 mutex 性能差多少？→ 无竞争的 atomic 就是一条原子指令，纳秒级；mutex 无竞争也是快路径原子+慢路径睡眠——但竞争下 mutex 让出 CPU，atomic 自旋烧 CPU；计数器用 atomic，临界区用 mutex。

### §13.23 死锁的四个必要条件？怎么预防？项目里怎么避免的？🟡

**口语答案**：四个必要条件：互斥（资源独占）、持有并等待（拿着 A 等 B）、不可剥夺（不能抢走别人的）、循环等待（等待关系成环）——四条同时成立才死锁，破掉任何一条就免疫。对应预防手段：破持有等待——一次性申请全部资源；破循环等待——全局规定加锁顺序，所有线程按同一序拿锁；破不可剥夺——try_lock 拿不到就放掉已持有的重来；再加上工程性的：缩小持锁范围、锁内不做慢操作（IO、日志格式化）、避免嵌套加锁。我项目里的实践就是后面这几条：连接池、LruCache、decoders_ 各是一把独立 mutex，模块内单锁、模块间不嵌套——一把锁构不成环；onMessage 先在 decoders_ 的锁内把 shared_ptr 拷出来就释放锁，之后用解码器不再持锁；连接池把 ping/重连这种 5 秒级操作放锁外，持锁时间从秒级压到微秒级。真要排查：gdb attach 后 thread apply all bt，找两个都停在 futex/lock wait 的线程，p 一下各自 mutex 的 owner 字段交叉比对就是互等实锤。

**追问预演**：
- ↳ 活锁和死锁区别？→ 活锁都在动都在让，谁也进不去（两个 try_lock 互相谦让）；解法加随机退避。
- ↳ 哲学家就餐怎么解？→ 按序拿筷子（奇数号先左偶数号先右）破循环等待；或一次拿齐两根（waiter 信号量）破持有等待。

### §13.24 线程池的基本实现（手撕候选）：任务队列 + cv + 固定 worker + 退出语义 🔴（简历原文点名）

**口语答案**：我按"边写边讲"的结构说。**结构**：一个任务队列 queue<function<void()>>、一把 mutex 加一个 condition_variable、固定 N 个 worker 线程、一个停止标志（bool 加 mutex 保护或 atomic）。**enqueue**：加锁、任务 push 进队列、notify_one。**worker 主循环**：unique_lock 加锁，cv.wait(lock, [&]{ return stop || !tasks.empty(); })——谓词里带 stop 是退出语义的关键；醒来后先判：stop 且队列空就 return 退出；否则取任务，**先解锁再执行**——任务执行绝不能持锁，否则并发度归一。**退出**：析构时 stop 置 true、notify_all 唤醒所有人，worker 各自醒来看谓词决定退——这里有个语义选择要主动讲：任务队列还剩活儿时是 drain（排干再退，优雅）还是丢弃（快停），两种都是合法设计，要按业务挑并写进注释。**升级项**：enqueue 返回 future 拿结果——用 packaged_task 包任务，注意它是 move-only 而 std::function 要求可拷贝，惯用法是 shared_ptr<packaged_task<...>> 再包一层塞队列，get_future 给调用方。**池大小**：CPU 密集约等于核数，IO 密集等于核数乘（1 加等待时间比计算时间）——和连接池公式同源，本质都是"别让等待中的工作者占着并发额度"。**队列满**：有界队列加拒绝策略——阻塞提交、丢弃、或调用者执行（CallerRuns，让提交线程自己跑，天然反压）。项目关联：简历写"线程池的基本实现"指掌握原理，工程上我用的两套现成模型更有意思——workflow 是任务调度线程组（任意线程产任务、worker 池消费）；muduo 是 EventLoopThreadPool，one loop per thread——固定线程各配**专属**队列，任务按连接哈希到固定线程，无锁无争用，是线程池的一种特化形态。

**追问预演**：
- ↳ 为什么 muduo 不用共享队列线程池？→ 连接的 IO 事件固定在同一线程处理，省掉每事件的锁和跨线程唤醒，还能顺带做单线程内免锁的业务状态——"线程池"和"每线程一个池"是吞吐与局部性的取舍。
- ↳ 任务抛异常怎么办？→ std::function 吞掉异常会 terminate——worker 里 try/catch 兜住打日志；要传回调用方就靠 packaged_task 把异常存进 future，调用方 rethrow。

### §13.25 volatile 是线程同步手段吗？🟡

**口语答案**：不是，斩钉截铁。volatile 只做两件事：每次访问真实读写内存（禁止编译器把它缓存进寄存器）、volatile 访问之间的编译器重排受限——但**不保证原子性**（64 位变量在 32 位机器上照样撕裂）、**不建立线程间的 happens-before**（一个核的修改另一个核什么时候可见没有约束）、也挡不住 CPU 层面的重排和store buffer 延迟。两个线程对同一个 volatile 变量读改写仍是数据竞争，UB。线程同步的正解是 std::atomic（带内存序的原子）或 mutex。volatile 的本职是内存映射硬件寄存器和信号处理标志（volatile sig_atomic_t）——告诉编译器"这个变量会被你看不见的势力改写"。我们信号处理的实践正是这个用法：SIGTERM 的 handler 只设置退出标志，主循环轮询——标志位是信号安全的写法，但它解决的是"信号路径安全"不是"多线程同步"，两个概念别混。顺带一句 Java 的 volatile 确实有内存序语义，C++ 的没有——跨语言经验带进 C++ 是这题最常见的翻车原因。

**追问预演**：
- ↳ 为什么编译器优化会坏事？→ 经典例子：while(!flag) 循环，编译器发现循环体不改 flag 就把它缓存进寄存器，外部改写永远看不见——volatile 修的是这个，只修这个。
- ↳ sig_atomic_t 是什么？→ 保证读写不可分割的整数类型，配 volatile 用在信号标志上——信号 handler 与主循环之间的最小同步约定。

### §13.26 多线程下 fork 有什么坑？🟡

**口语答案**：核心一句：fork 只复制**调用线程**，其他线程在子进程里直接蒸发——但它们持有的锁不会释放。如果蒸发的那条线程正好拿着 malloc 的堆锁、stdio 锁，子进程接下来调 malloc 或 printf 就直接死锁——锁的状态被复制了，持有者却不存在了。条件变量更糟：等待者消失后状态错乱。规避三板斧：一是 fork 后立刻 exec——子进程整个镜像被换掉，脏锁无所谓，这是最标准的姿势；二是 pthread_atfork 注册 prepare/parent/child 回调，在 fork 前后显式管理锁（拿全锁/放锁），侵入大易漏；三是架构上让可能 fork 的进程保持单线程。我项目没有多线程 fork 的场景，但有个相邻的真实故事：备份消费者 SIGTERM 收不掉——消费 API 无限阻塞等不到检查退出标志的时机，最后 handler 里直接 _exit——选择的理由正是退出路径不碰任何可能持锁的东西（malloc/printf/mutex），未 ACK 的消息由 broker 重投、消费端幂等吸收。async-signal-safe 的白名单思维和 fork 的"锁孤儿"是同一类问题：**在"世界可能不完整"的时刻，只做最小安全动作**。

**追问预演**：
- ↳ 为什么信号 handler 里也不能 printf/malloc？→ 同一个根因：handler 可能在 printf 拿着 stdio 锁时打断它，再调 printf 就自死锁；白名单只有 write 之类的可重入系统调用。
- ↳ vfork 和 fork 区别？→ vfork 不复制页、父进程挂起等子进程 exec/exit——历史产物，现代 copy-on-write 的 fork 已经让它基本退役。

### §13.27 内存泄漏怎么排查？Valgrind 的原理？和 AddressSanitizer 比？🟡（简历写了 Valgrind）

**口语答案**：先说工具原理。Valgrind memcheck 是用户态动态二进制翻译：把目标程序的机器码翻译成中间 IR、在每条内存访问前插入检查代码再执行，同时给每字节维护影子内存——记录这段内存是否已分配、是否已初始化。所以它能查未初始化读、堆越界、double free、泄漏（exit 时扫描指针可达性，分 definitely/indirectly/possibly lost 和 still reachable），而且不需要重新编译。代价是慢 10 到 50 倍——只适合测试环境跑回归，不能上生产。AddressSanitizer 是编译期插桩：-fsanitize=address 编译时在每次访存前后插入检查、给栈和全局变量加红区（越界写会踩进红区被逮到）、释放的内存进隔离区延迟复用（use-after-free 窗口内必被抓），影子内存比例 1/8；慢只有 2 倍左右，能查 Valgrind 查不到的**栈变量和全局变量越界**，可以进 CI 常开。选型口诀：有源码、要快、进流水线用 ASan；无源码或要查第三方库内部用 Valgrind；两者都是 Linux 容器跑（macOS 上 Valgrind 基本不可用）。我的排查习惯：长驻进程（RIS 的索引、连接、每连接解码器 map）在测试环境跑一轮"启动→压请求→退出"，valgrind --leak-check=full --show-leak-kinds=all 看报告，重点盯 definitely lost——still reachable 多半是全局单例的正常持有；线上则先看 RSS 趋势定位哪类对象在涨，再回测试环境复现。

**追问预演**：
- ↳ 一定查得出所有泄漏吗？→ 都查不出"逻辑泄漏"——容器只增不减、缓存无上限，内存都"可达"但业务上是漏；这类要靠指标和容量上限。
- ↳ 还有别的 sanitizer 吗？→ TSan 查数据竞争（加锁是否正确用它）、UBSan 查未定义行为——和 ASan 组合是 C++ 工程化的标配三件套。

### §13.28 new/delete 和 malloc/free 的区别？placement new？🟡

**口语答案**：四个层面。语义：malloc 只分配原始字节、返回 void*，不构造任何东西，失败返回 NULL；new 分配加**构造**——它先调 operator new 拿内存、再在这块内存上调构造函数，类型安全返回 T*，失败默认抛 bad_alloc（nothrow 版本才返回空）。行为可定制：operator new/delete 可以全局或按类重载——统计分配、打日志、对接自己的内存池都从这进，malloc 只能 hook。配对纪律：new[] 必须配 delete[]（数组头部存了元素个数，错配少析构或读坏 cookie）。placement new 是 new 的特殊形式：new (ptr) T(args)——在**给定的内存**上构造对象，不分配任何东西；对应地要**显式调用析构** p->~T()，析构不释放内存（内存归属给它的分配者）。它存在的意义就是把"内存管理"和"对象构造"解耦——三个经典用户：SGI 空间配置器的 construct（free list 摘下的内存上重建对象）、STL 容器的 reserve（分配 capacity 但只构造到 size）、对象池/arena。这也是标准容器 allocator 接口分成 allocate/construct 和 deallocate/destroy 的原因。

**追问预演**：
- ↳ new 的内存从哪来？→ operator new 默认调 malloc，之上 glibc 还有 ptmalloc 的 arena/桶管理——一层层往下就是第 §13.15 题那套配置器思想。
- ↳ 显式调析构函数合法吗？→ 对 placement new 构造的对象不但合法而且必须——但对普通 new 的对象直接调析构再重用内存是自找 UB。

### §13.29 std::string 的 SSO 了解吗？🟡

**口语答案**：SSO 是短字符串优化：string 对象里是个 union——短串直接存在对象内部的字符数组里，长串才用"堆指针加长度加容量"三件套。分界线实现相关：libstdc++ 15 字节、libc++ 22 字节上下（64 位平台），反正都覆盖"缓存键、字段名、短查询词"这类主力场景。收益两个：短串零堆分配——构造拷贝就是拷对象本身那 32 字节，省掉 malloc/free 的一次往返和分配器的元数据；内存局部性好——字符串数据和 string 对象在一处。另一个值得带一句的现代特性：C++11 起 string 支持移动——长串移动就是交接堆指针 O(1)，短串反正只有 32 字节、拷贝和移动等价。我项目里的相关性：缓存键 ris:v{版本}:{FNV-1a 哈希}、查询词、报告字段都是短串，SSO 全程生效——这也是我把键设计成短哈希串的顺带好处；FNV-1a 计算和 json 拼接都在 SSO 区间内零堆开销。

**追问预演**：
- ↳ SSO 对 string 被移动/拷贝的行为影响？→ 短串移动也得逐字节拷（数据就在对象里）——所以 string 的 move 不保证 O(1)，是"长串 O(1)"。
- ↳ c_str() 和 data() 一样吗？→ C++11 起都保证连续和 null 结尾，基本等价；传给 C API 前注意 string 析构/修改后指针失效。

### §13.30 C++11 特性你在项目里用过的数一遍 🟡

**口语答案**：我按"用在哪"数，不背清单。右值引用与移动语义——MySQLGuard 的移动构造、=delete 禁拷贝，连接的所有权传递；智能指针——shared_ptr 管理索引快照和每连接解码器，配合 atomic 自由函数；lambda——连接池 wait_for 的谓词 [this]{ return !idle_.empty(); }；bind 加 function 加 placeholders——muduo 的连接/消息回调注册；atomic——日志全局级别的 atomic<int>、索引切换的 atomic_store/atomic_load；thread 库全家——thread、mutex、condition_variable、chrono（wait_for 的 3 秒超时就是 chrono::milliseconds）；unordered 容器——倒排索引、词表、LRU 索引层；auto 和 range-for——索引构建、解析器里大量使用，类型长的时候可读性救星；to_string、nullptr；尾部还有 enum class 和 override 这些"小而正确"的——宁可少列，列出来的每个都能落到文件。整个项目锁死 C++11（CMAKE_CXX_STANDARD 11 加 STANDARD_REQUIRED），所以这套特性是"在约束内工作"的实战，不是清单背诵。

**追问预演**：
- ↳ C++14/17 有什么你想要的？→ 初始化捕获（move 进 lambda）、make_unique、结构化绑定、optional、string_view——但项目锁 11，能讲"想要什么、为什么现在不用"比追新更专业。
- ↳ auto 的缺点？→ auto 不错在隐式转换和代理类型（表达式模板）上会把引用类型切掉——该写显式类型的地方（接口边界）别 auto。

### §13.31 编译四阶段？静态库和动态库的区别？🟡

**口语答案**：四阶段按产物记：预处理——展开 #include、替换宏、处理条件编译，输出 .i 纯 C++ 文本；编译——词法语法语义分析加优化，生成汇编 .s；汇编——把汇编翻成机器码，输出 .o 可重定位目标文件（机器指令加符号表加重定位表）；链接——符号解析（把每个符号引用找到定义）加重定位（按最终地址修正），输出可执行文件。库的区别在链接期行为：静态库 .a 是一堆 .o 的打包，链接器从中**抽取用到的目标文件拷贝进**最终产物——产物自包含、部署就是拷一个文件；代价是体积大、库升级要重新链接、每个进程各带一份代码。动态库 .so 链接期只记录符号引用，运行时由动态链接器加载、重定位绑定（默认惰性绑定，函数第一次调用时才解析）——多进程共享一份物理内存、库可以独立升级；代价是启动加载时间、符号查找开销、以及 ABI 兼容这个大坑（库换了二进制不重编可能炸）。我项目的选择：workflow 和 muduo 源码编译安装出的就是 .a，我们静态链接——医院内网部署，单二进制自包含最稳，彻底没有 so 版本漂移问题；代价是库升级全量重编、产物大——两服务规模下这个交换划算。

**追问预演**：
- ↳ -l 在哪个阶段起作用？→ 链接期；-I 预处理期、-c 到汇编就停——报错"undefined reference"是链接期的符号解析失败，"No such file"多半是 -I/-L 路径问题，先分清阶段再排。
- ↳ RPATH 是什么？→ 写进可执行文件的"去哪找 .so"的路径——动态库部署的头号坑，ldd 一查便知。

### §13.32 模板：函数模板/类模板/特化？你在哪用了模板？🟡

**口语答案**：函数模板由调用实参推导（也可显式指定）生成针对具体类型的函数版本；类模板必须显式给参数（C++17 才有 CTAD 推导）；实例化是编译器按"用到的类型组合"生成代码——所以模板定义必须在头文件可见，且未用到的组合不会生成代码（这也是模板"零开销抽象"的来源之一）。特化分两种：全特化——template<> 给某个具体类型提供完全独立的实现；偏特化——类模板对"参数的某个子集"特化（比如 T* 指针族），**函数模板不能偏特化**，只能重载或全特化，这是高频陷阱。项目里的诚实版：自写代码刻意少用模板——我的组件是具体场景的（LruCache 的键值固定 string，用 typedef 收口类型；真要泛型化就是把两个 typedef 换成 template <typename K, typename V> 参数，改动五分钟，但在只有一个使用方的当下，泛型是超前抽象）；真正大量"用模板"体现在消费侧——vector/list/deque/unordered_map/priority_queue、std::function 的类型擦除、bind 的占位符、atomic 和 shared_ptr 的自由函数，全是模板设施。能把"用了什么、为什么自己不写模板、要写怎么改"讲清楚，比硬吹模板元编程可信。

**追问预演**：
- ↳ 模板代码为什么放头文件？→ 编译器在实例化点需要看到完整定义；分离到 .cpp 会导致别的地方用不了（显式实例化可以救，少用）。
- ↳ 代码膨胀？→ 每个新类型组合都生成一份代码——模板库里大量"把差异收敛到 void* 或基类实现、模板壳只做类型转发"的技巧（shared_ptr、std::string 的实现都这么干）就是在压膨胀。
