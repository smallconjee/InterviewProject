## 🔴 为什么拆成两个服务？合并成一个行不行？

**口语答案**：因为两边的负载模型和故障域完全不同。归档是写路径——重 IO、要事务、要消息可靠性；检索是读路径——索引常驻内存、追求低延迟。拆开后各自独立扩缩容（消费者和 RIS 都设计成可横向扩）、故障隔离（RIS 挂了归档照常收影像）。合并成一个进程技术上能跑，但 RIS 约 2GB 的索引内存和归档的写入洪峰会互相干扰，发布也只能绑在一起。所以拆是刻意的，代价是多了一跨服务调用的运维面。

**追问预演**：
- ↳ 两个系统怎么联动？——报告侧解析出 StudyInstanceUID 时，查一下归档库的 study 表，存在就给这条报告打 has_image 标记，医生检索时能看到"这条报告有影像"。
- ↳ 联动为什么直查库不走接口？——低频只读 exists 查询，走接口要多一层部署、超时和故障管理，当时不划算；我承认跨服务 DB 耦合是债，演进方向是 PACS 出一个批量 exists 接口。
- ↳ 两个库共用一个 MySQL 实例，业务上怎么隔离？——归档数据全在 pacs_db，RIS 的索引是本地版本目录文件、不占库；RIS 对 MySQL 只有联动这一条只读查询。库边界就是业务边界（口径：MySQL 单实例加备份，主从为演进）。

**雷点**：只说"微服务好"这种教条理由——面试官会追问"你这点量拆什么拆"，必须落到负载差异和具体数字（2GB 索引）上。

## 🔴 为什么 PACS 用 workflow/wfrest，RIS 用 muduo？

**口语答案**：跟着场景走。PACS 是 HTTP 网关加异步任务编排：wfrest 写 HTTP 接口省事，workflow 的 Task/Series 模型天然适合串联异步操作——我们做 RIS 桥接时就是把 TLV 客户端任务 push 进 HTTP 任务的 series，回调里写响应，全程不占 handler 线程；而且 srpc、Consul 这套生态都在 workflow 系里。RIS 是自定义二进制协议的常驻 TCP 服务，要对连接生命周期和读写缓冲做精细控制，muduo 的 one loop per thread 是最直接的模型。一边要"编排"，一边要"控连接"，所以用了两个库。

**追问预演**：
- ↳ 两个库的线程/调度模型分别讲一下？——workflow：线程池加任务队列调度，同步写法底层被调度器异步化，handler 不绑定固定线程；muduo：主 loop 只管 accept，4 个 sub loop 各自 epoll 一批连接、one loop per thread，连接固定绑定一个 IO 线程。
- ↳ 为什么不统一用一个库？——workflow 也能写自定义协议（桥接就是证据），但检索服务用不上它的 HTTP/RPC 生态；muduo 的 Buffer 和回调模型对 TLV 增量解码更顺手。统一成一个当然省心智，但两边都会用得别扭。
- ↳ 为什么不用 brpc/drogon/oatpp/asio？——drogon/oatpp 是全功能 HTTP 框架，我们的重点在任务编排和非 HTTP 链路；brpc 主场是内网 RPC；asio 太底层，用它等于自己造一个 muduo。团队对 workflow 已有积累，这个权重很高。
- ↳ 为什么用 C++ 写 HTTP 服务而不是 Java/Go？——团队技术栈和既有代码资产是 C++，医疗影像领域生态也以 C++ 为主；RIS 的 GB 级常驻索引对内存布局和延迟的控制要求高。Java/Go 写 HTTP 业务效率高，这是真实取舍，不是说 C++ 全面更好。

**雷点**：把两个库的优劣背成参数表（QPS、内存占用）却说不清"哪个特性击中了我们哪个需求"——选型题考的是需求匹配，不是跑分。

## 🔴 PACS 用 HTTP、RIS 用自定义 TCP 协议，为什么不对称？

**口语答案**：因为两端的消费方不同。PACS 的上游是影像网关和浏览器控制台，走标准 HTTP 加 multipart 是生态最顺的选择，通用性优先；RIS 的客户端是院内医生工作站，长连接、高频短请求，TLV 二进制帧头只有 6 个字节，HTTP 头随便就几百字节，协议开销占比太高。所以不对称是刻意的：对外的边用通用协议，内网的服务间调用用高效二进制协议——这本身也是个常见模式，网关对外 REST、内部 RPC。

**追问预演**：
- 帧格式具体什么样？——[type 1B][flags 1B][len 4B 网络字节序][payload]，len 用网络字节序解决跨平台字节序；载荷上限 1MB 防内存攻击。
- 为什么不用 protobuf 长度前缀帧？——也可以，TLV 更轻；协议演进靠 flags 和类型白名单（细节在 RIS 答案库）。
- HTTP 那边为什么不也上二进制？——上游对接的是第三方网关，遵循通用标准比自定义协议的维护成本低得多。

**追问预演**：
- 哪条链路延迟最敏感？——检索：P99 80ms 以内、L1 命中约 5ms；导入是 P99 300ms 以内。
- 图里最薄弱的点？——RabbitMQ 单实例（演进：仲裁队列）；MySQL 单实例的可用性单点（演进：主从）。

## 🟡 系统的单点在哪？各组件挂了分别什么表现、怎么恢复？

**口语答案**：逐个过：MySQL 挂——写接口失败，实施侧按流程从备份加 binlog 恢复（单实例是已知单点，主从在演进计划），服务侧连接池借出前 ping 加显式重连，恢复后自愈，测试环境杀掉 MySQL 容器实测过接口自动恢复；Redis 挂——只影响 RIS 缓存，静默降级直查索引、只告警一次，缓存是加速器不是依赖；RabbitMQ 挂——导入完全不受影响，事件躺在本地消息表，恢复后补偿扫描补发；Consul 挂——服务发现三级回落：环境变量显式地址、Consul 健康列表、默认地址，已解析的地址继续用、失败置重查；RIS 挂——归档照常，桥接接口 502，连接池在 RIS 恢复后自动重连；认证服务挂——网关每个请求都要 srpc 调它验签，会 503，这是已知取舍，演进是网关本地验 JWT 加权限缓存。最想优化的是 RabbitMQ 单实例。

**追问预演**：
- 认证挂了导归档还能导吗？——不能，每请求都过鉴权；短 TTL 的本地权限缓存是演进项。
- MySQL 真挂了怎么办？——实施团队按流程从每日备份加 binlog 恢复，应用侧靠连接池自愈；主从自动切换是演进项，医院内网倾向保守运维。
- 兜底的总原则？——同步链依赖的组件要少（落盘+MySQL），其余全部异步化、可降级、可补偿。

**雷点**：说"我们全都有高可用"——单实例 Redis、单实例 RabbitMQ 都是口径里写明的现状，吹高了被追问哨兵/仲裁队列细节就崩；诚实标注现状+演进方向反而加分。

## 📐 系统吞吐多少？导入接口 QPS？检索 QPS？压测过吗？

**口语答案**：导入侧：请求 QPS 峰值约 15——上游网关逐对象推送，请求吞吐即对象吞吐，设计余量是每秒 50 个对象，同步链 P99 300ms 以内。检索侧：峰值约 20 QPS——约 200 个医生工作站、低频查询，走索引 P99 80ms 以内、L1 命中约 5ms，两级缓存命中率合计约 70%。备份链：单消费者每秒约 10 个任务，高峰积压 1 到 2 万、通常 1 小时内回落。压测这块我如实说：专项压测报告在待补清单，上面数字是生产观测加设计目标，不是基准测试结果。

**追问预演**：
- 没压测怎么敢上线？——场景是院内网低并发（20 QPS 检索），设计余量大；上线靠测试环境全链路验证和灰度。
- 如果要压，压什么？——wrk 打导入接口看 P99 和连接池水位；构造词典和查询集打检索 QPS——已在计划里。
- 50 对象/秒怎么定的？——按日均 15 万对象集中在上午高峰的到达率加余量推导。

**雷点**：把生产观测说成"压测结果"——面试官一句"用什么压的、报告长什么样"就穿帮；"生产数字+诚实标注压测待补"是最稳的口径。

## 🟡 流量涨 10 倍，你先扩哪里？为什么？

**口语答案**：先扩备份消费者。算笔账：日增 15 万备份任务，单消费者每秒约 10 个任务，现在高峰已经会有 1 到 2 万积压、1 小时内回落——涨 10 倍这条链最先饱和，而且它一旦堆积会顶高消息表和队列，触发我们的堆积告警。好消息是消费者本来就是独立进程、按积压独立扩容的设计，拉起第二个实例分流是现成操作，生产处理 OSS 限流积压时验证过。其次才是 PACS 主服务多实例加网关分片。检索放最后：20 QPS 涨 10 倍也就 200 QPS，内存索引加 70% 缓存命中率，余量还很大。

**追问预演**：
- 消费者扩容消息会乱序吗？——备份任务天然无顺序依赖，task_id 幂等吸收乱序和重复。
- MySQL 扛得住 10 倍吗？——写入是短事务+唯一索引裁决，先看连接池和磁盘 IO；真不够上分库按 study 哈希，四层模型拆起来不难。
- 积压 100 万怎么办？——接消息可靠性板块：水平扩容、调 prefetch、批量确认。

**雷点**：答"先升机器配置"或"全都扩"——没有优先级判断的扩容答案等于没答；必须给出"哪条链先饱和"的算账过程。

## 发现的问题

1. **题库 §1"两个库共用一个 MySQL 实例"与代码有出入**：RIS 没有独立的 MySQL 业务库——倒排索引在本地版本目录文件，MySQL 只在联动时由 RIS 的 StudyLink 直连 pacs_db 查 study 表（`04_ris_report_search/src/main.cpp`）。本题答案按代码口径表述为"RIS 索引在本地文件、对 MySQL 仅一条只读联动查询"；若面试官追问"RIS 的库是什么"，同样按此口径答。
2. **口径"应用网关 ×1"与代码职责边界模糊**：口径部署节列了"应用网关"一台，但代码里鉴权（AuthGate 中间件）在 PACS 主服务进程内通过 srpc 调认证服务，架构图的"wfrest 网关"就是 PACS 服务自身（8080）。"应用网关"更接近上游 DICOM 网关/入口层。白板画图时建议按"上游网关（外部）+PACS 服务（含鉴权中间件）"表述，避免被问"网关上跑了什么"时与代码冲突。
3. 口径"检索峰值 ~20 QPS（~200 个医生工作站、低频查询）"与"P99 < 80ms、L1 命中 ~5ms、缓存命中率 ~70%"内部自洽，与代码结构无冲突（仅数字需人工校对）。
