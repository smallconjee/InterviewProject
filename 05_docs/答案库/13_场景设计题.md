## §15.1 🔴 导入接口 QPS 要到 500，你怎么改？

**口语答案**：先对约束：我们上游是逐对象推送，请求 QPS 就是对象速率，现在峰值约 15、设计吞吐余量 50 对象/秒——500 是三十多倍，日对象量线性外推要上千万，单家医院不可能，我会先确认这是不是多院区集中导入的设定，再动手。方案分三层：第一层只扩容不改架构——PACS 主服务从单实例扩多实例、前置负载均衡；导入幂等本来就建在 SOPInstanceUID 唯一索引和 FOR UPDATE 上，多实例并发导同一对象天然安全，地基是现成的；连接池按 MySQL 连接预算扩；备份消费者横向扩（本来就是可扩设计，多实例 broker 轮询分发）。第二层优化链路——消费者并发上传参数化、staging 与正式存储分盘。第三层才动架构——MySQL 按 study 哈希分库，四层模型天然好拆。还有一笔存储账要算：500 对象/秒乘平均 0.7MB 约 350MB/s 持续落盘，磁盘很可能先于 QPS 成瓶颈。我负责的消息链这时是保险：本地消息表天然削峰，导入洪峰先落库，备份按消费者自己的节奏消化。

**追问预演**：
- ↳ MySQL 扛得住 30 倍吗？——导入是短事务加自增主键顺序插入，先看连接数和磁盘 IO 水位；真不够按 study 哈希分库，Patient→Study→Series→Instance 四层按顶层键拆即可。
- ↳ 多实例同时导同一个对象怎么办？——唯一索引原子裁决加 FOR UPDATE 排队，本来就是并发安全设计，只是现在单实例没被压出来。
- ↳ 消息链会不会被打爆？——消费者可横向扩；消费者并发上传是事故复盘后列的改进项，这题里正好当"先做什么"讲。

**雷点**：不问约束直接堆方案（500 是峰值还是均值、对象还是请求都没对齐）；只盯 QPS 忘了算 350MB/s 的落盘和 MySQL 这两个真瓶颈。

## §15.2 🔴 检索服务要 P99 < 50ms、1000 并发长连接，你怎么改？

**口语答案**：先拆指标：1000 并发长连接和 1000 QPS 是两回事，要确认是连接数还是吞吐。现状：峰值约 20 QPS、约 200 个医生工作站，走索引 P99 80ms 以内、L1 命中约 5ms、两级命中率合计约 70%。先说结论：连接数不是瓶颈——4 个 sub loop，每个 epoll 挂 250 个连接毫无压力；**真正的风险是 IO 线程被慢操作占住**：现在检索加 Redis 加关联查询都跑在 onMessage 里，Redis 超时设 2 秒，最坏一个慢查询让一个 loop 上两百多个连接全体排队。方案分三层：第一层扩容——RIS 横向扩实例（本来就是可扩设计），L2 Redis 天然跨实例共享、缓存键用 FNV-1a 跨进程稳定，多实例直接分摊；第二层改造——把计算移出 IO 线程，onMessage 只做解码，检索投递到业务线程池，慢查询不再传染；第三层延迟优化——缓存预热（历史高频查询回填）、查询归一化提命中率、限制单次返回 TopK。P99 50ms 怎么达：命中路径本来 5ms 内，关键是把走索引那 30% 的比例往下压、慢的隔离住不拖别人。

**追问预演**：
- ↳ 业务线程池多大？——按"核数×(1+等待/计算)"起算，检索是毫秒级 CPU 加一次 Redis 往返，4 到 8 起步压测调。
- ↳ 索引每个实例一份 2GB，浪费吗？——是代价；多实例共享一份数据要么索引下沉成独立检索进程，要么接受冗余换简单——百 QPS 量级我选冗余。
- ↳ 1000 连接的假死怎么处理？——应用层心跳（TLV 的 ping 类型）加 idle 踢除，比 TCP keepalive 判得快。

**雷点**：把 1000 并发答成 1000 QPS；不提"计算移出 IO 线程"——这是代码里真实存在的债（题库 §8 已标），场景题正是还债的场合，主动讲反而加分。

## §15.3 🔴 海量小文件（亿级）存储方案怎么设计？

**口语答案**：先对齐量级：亿级对象乘我们平均 0.7MB 是 70PB，和现在在线 25TB 差四个数量级，方案必然不同，我先确认文件大小分布、读写比和删除语义——我们是归档后极少改写、读集中在近期、医疗法规不物理删除，这对方案影响很大。分四层讲：第一，**元数据与文件分离**——查询走 MySQL 四层模型不扫文件系统，这是我们现在就有的；亿级时元数据表按时间或院区分区、再按 patient 哈希分库。第二，**对象存储做主存储**——OSS 按 key 扁平、天然亿级，我们的 OSS 异步备份链路已经在跑，演进成主存储成本最低。第三，**本地热层小文件合并**——CT/MR 层图是小文件主力，按 study 合并成大段文件加偏移索引（Haystack 思路），一次大 IO 代替海量 open/close，减 inode 压力；目录要按 UID 哈希打散层级，单目录百万文件就该治理。第四，**冷热分层**——近期在线做热层，历史按需迁移，我们现在"历史影像留在医院旧 PACS 按需迁移"就是这个思路的天然版；DR 大文件和 CT 小文件分层策略分开。

**追问预演**：
- ↳ 合并后读单个对象怎么办？——段文件内 (offset, size) 定位，一次 pread；删除不回收空间，段文件标记碎片率、后台重写——和我们"不物理删除"的语义正好合拍。
- ↳ 哈希算谁验完整性？——我们入库时流式算 SHA-256 存库，备份前后可复验；亿级下抽验加全量对账任务。
- ↳ 为什么不用 HDFS？——HDFS 适合大文件流式读写，海量小文件恰恰是它最弱的场景（namenode 内存压力），小文件合并后用它才合理。

**雷点**：只谈文件系统不谈元数据层；说"一个目录放一亿文件加索引就行"——目录项遍历和 fsck 都会炸，必须打散。

## §15.4 🔴 报告量涨到 1000 万，索引和检索架构怎么演化？

**口语答案**：先算账：现在 80 万文档、约 35 万词项、内存约 2GB、全量重建约 12 分钟；涨到 1000 万是 12.5 倍，线性推算内存约 25GB、重建约两个半小时。先说两个关键判断：一是**词表不怎么涨**——分词去重加停用词过滤后，医学语料词表就这么大，35 万词项不会变成 400 万；二是**先爆的不是内存是重建窗口**——25GB 单机大内存还放得下，但两小时的全量重建把凌晨窗口吃掉了。所以演化分三步：第一步扩容——垂直加内存扛索引，重建并行化（分片并行构建再合并）把时间压回去；第二步**增量索引**（核心）——不可变段加 tombstone：新报告按小时或按天构建小段，删除修正记删除位图，查询时多段并查各取 TopK 再归并、tombstone 过滤，段数多了低峰 merge——Lucene 段合并同思路；我们的 shared_ptr 原子切换和版本化缓存键整套机制直接复用，版本号从"整索引"变"段集合"；第三步分片——按年份或院区切 shard，各 shard 本地 TopK、归并节点取全局 TopK，归并代价很小。1000 万在单机内存检索里是中等规模，先增量段后分布式，别跳步。

**追问预演**：
- ↳ 多段并查延迟会涨多少？——段数控制在几十内、每次归并的是 Top10 列表，毫秒级；段数涨了就是 merge 的信号。
- ↳ 增量段的缓存怎么失效？——版本键机制照旧：段集合变、版本号变、键就变，不用发明新机制。
- ↳ 分布式之后错误扩散怎么办？——shard 故障降级返回部分结果加标注，医疗检索宁可少给不可全挂。

**雷点**：直接上分布式检索（这是最常见跳步）；忘算重建时间只算内存；不知道词表和文档数是弱相关的两个量纲。

## §15.5 🟡 消息积压 100 万条怎么办？（接第 4 部分）

**口语答案**：先分诊再动手，积压三类原因处理完全不同：下游故障、消费者挂了、流量真涨。我们真出过一次可控的：夜间批量导入叠加 OSS 限流，早高峰积压冲到 3 万多，消费者日志全是 OSS 429，单消费者吞吐从每秒约 10 个任务掉到约 3 个——这种下游问题扩容无效，处理是拉第二个消费者进程分流（前提是消费端非独占，否则第二个实例 403 连不上）加向 OSS 提工单提额。回到 100 万的假设：第一步水平扩消费者——独立进程多实例、broker 轮询分发，单实例约 10 任务/秒，10 个实例约 100/秒，100 万约 3 小时消化（推算）；第二步提单实例吞吐——瓶颈不是 CPU 是 OSS 单次上传约 50 毫秒的串行等待，消费者内并发上传加 prefetch 调大配批量确认；第三步极端情况——新起转储队列慢慢消化。底线是备份这条链可降速不可丢：本地消息表保证最终必发，队列清空这种操作在备份任务上绝对不做。

**追问预演**：
- ↳ prefetch 是什么？设多少？——消费者未 ack 消息的配额，broker 据此流控；我们用的库默认 1，匹配单线程逐条；批量场景按"单条耗时乘目标吞吐"调大。
- ↳ 扩到多实例消息乱序怎么办？——备份任务天然无顺序依赖，task_id 幂等吸收乱序和重复，这条链不需要保序。
- ↳ 怎么防止再犯？——双条件告警（积压超 2 万且持续 1 小时不回落）加每日巡检两个自建指标：消息表堆积数和队列深度。

**雷点**：开口就加机器（下游限流时无效，我们的事故就是反例）；说"临时清空队列"（备份任务一条都不能丢）；不先分诊就说方案。

## §15.6 🟡 MySQL 整个挂了，系统怎么表现？怎么降级？RTO 多少？

**口语答案**：按链路过一遍表现：导入——两个事务都依赖库，接口直接报错，上游网关逐对象重试，我们有幂等，恢复后自动补上，不会产生脏数据；认证——登录和权限依赖库，请求 503，这是已知取舍；备份消费者——状态回写失败就不 ack，消息留在 broker 重投，消费端以约 3 秒一轮的节奏慢速空转等恢复，不热循环；检索——**基本不受影响**：索引在本地内存、两级缓存照常，RIS 对 MySQL 只有一条 has_image 关联查询，失败就降级跳过徽章，把 MySQL 从检索关键路径上摘掉了。恢复：MySQL 是主从，实施团队按流程切换主，RTO 分钟级；应用侧不用动——连接池借出前 ping 加显式重连，测试环境杀 MySQL 容器实测过接口自动恢复、无需重启进程。降级哲学一句话：同步链依赖的组件尽量少，其余全部异步化、可降级、可补偿。

**追问预演**：
- ↳ 为什么不做自动切换？——医院内网保守运维，切换是实施团队按流程做；应用侧把自愈做好（ping 加重连、快速失败）就是后端该管的部分。
- ↳ 主从切换会不会丢事务？——取决于复制模式，异步复制极端情况丢最后一点已提交事务；导入有上游重试加幂等，丢了的重新导即可，这条业务容忍。
- ↳ 认证能不能也降级？——演进项：网关本地验 JWT 签名（无状态本来支持）加短 TTL 权限缓存，只有权限变更才查服务。

**雷点**：说"系统完全不受影响"（导入和登录是强依赖，睁眼说瞎话）；吹自动故障转移（口径是实施按流程切）；漏说消费者"不 ack 等恢复"这个正确姿势。

## §15.7 🟡 给这套系统设计监控告警：你采集哪些指标？

**口语答案**：先说现状再给设计。现状：Zabbix 看机器、进程、端口，日志按天切割收集；业务侧两个自建指标——**消息表堆积数（巡检 SQL）和队列深度**，每日巡检。完整设计我分四层：第一层业务指标——导入 QPS 和对象数、同步链 P99、备份队列深度加消费速率、消息表堆积数、DLQ 计数（非零即告警）、检索 QPS 和 P99、L1/L2 缓存命中率、索引版本与年龄（版本不往前走等于构建失败）。第二层中间件——MySQL 连接数和主从延迟、Redis 内存和命中、RabbitMQ 队列深度和 unack、磁盘水位——我们日增 120GB，**存储增速是这类系统最容易漏掉的容量雷**，必须配提前量告警。第三层告警哲学，这是事故换来的：深度加持续时间双条件——只看深度，早高峰正常潮汐（1 到 2 万、1 小时内回落）天天误报；只看持续时间，暴涨发现得晚。现在的规则是积压超 2 万且持续 1 小时不回落。第四层分级——页面级（进程挂、磁盘将满）、通告级（积压双条件、命中率下跌）、巡检级（DLQ、慢日志）。积压监控正是我负责迭代的部分，这套是实践过的不是纸面设计。

**追问预演**：
- ↳ 双条件告警怎么实现？——队列深度按分钟采样，连续 N 个采样超阈值才触发；比单点判断多一个状态机，误报少一个数量级。
- ↳ 缓存命中率怎么观测？——命中路径打点日志（L1 命中/L2 命中/走索引三类），按天聚合；跌破基线说明容量配置或查询模式变了。
- ↳ 为什么消息表堆积和队列深度两个都要？——前者反映"该发没发"，后者反映"该消费没消费"，一个盯发布端一个盯消费端，故障定位第一秒就能分边。

**雷点**：只报组件指标没有业务指标；告警规则只写阈值不写持续时间（正好踩过事故的坑还不用教训）。

## §15.8 🟡 索引每天全量重建 30 分钟，能接受吗？设计增量方案。

**口语答案**：先对现状：80 万文档全量重建约 12 分钟，每天凌晨 2 点定时、双版本切换不停服务——这个规模完全可接受。涨到 30 分钟（比如文档量涨到两百万级），我的判断是"还能接受但接近边界"：凌晨低峰没有查询压力，但三个代价在涨——维护窗口被侵蚀、失败重试成本翻倍、当天新报告要等凌晨才可检索的准实时性变差。增量方案四件套：一，**不可变段**——新报告按小时或按天构建小段索引，段小构建快，查询时多段并查、各段本地 TopK 归并；二，**tombstone**——删除和修正记在删除位图里，查询路径过滤，不回改旧段，保住"不可变"这个根基；三，**后台 merge**——段数多了查询开销涨，低峰合并小段成大段，段数控制在一个稳态；四，切换机制复用——段集合指针照样用 shared_ptr 原子切换，缓存键的版本号跟着段集合版本走，整套版本化基础设施不用动。这个设计就是 Lucene 段合并的思路，我们"报告当天改了要等凌晨重建"的现状正好是它的动机。

**追问预演**：
- ↳ 增量段多久构建一次？——按数据到达节奏定，我们报告日增约 1500 份，小时级一段、每段秒级构建，代价可以忽略。
- ↳ tombstone 会不会无限膨胀？——merge 时物理落地删除：重写段时跳过已删文档，位图随之清理。
- ↳ 为什么不干脆改成实时更新可变索引？——可变索引要处理并发读写锁、部分更新的一致性，复杂度陡增；不可变加段是工程上更稳的路径。

**雷点**：题设 30 分钟答"完全不能接受要重构"（凌晨低峰全量仍是正当方案）；增量方案里丢了 tombstone（只讲加不讲删）。

## §15.9 🟡 怎么做发布和回滚？

**口语答案**：先说现状流程：两周一个版本；内网 GitLab 走 MR、组长 review；数据库变更走 SQL 脚本评审；测试环境验证通过后，实施工程师驻场升级——医院内网没有云端那种 CI/CD 洒水，可靠性靠流程和"可回滚的单元尽量多"。回滚手段按对象分四类：服务二进制——workflow 和 muduo 静态链接、单二进制部署，回滚就是换回旧文件重启，分钟级；备份消费者是独立进程，可以单独回滚不动主服务。索引——版本目录 v1、v2 落盘共存，指回旧目录即回滚，不用重建，这是现成机制。数据库——变更做向前兼容设计：加列不删列、新列带默认值，旧代码跑新表不炸，回滚代码不用回滚库。灰度——3 家上线医院天然是灰度单元，新版本先上 1 家试点院观察一个迭代再推全量。另外发布消费者前先看队列深度，有积压先消化再发，避免发布动作叠加积压。

**追问预演**：
- ↳ 为什么不搭自动化发布？——院内网、驻场实施是这个行业的现实，自动化的收益先落在测试环境的流水线上，生产升级保守优先。
- ↳ SQL 变更出问题怎么回滚？——脚本评审时就要求附带回滚脚本；向前兼容设计保证代码回退后库不用动。
- ↳ 蓝绿发布了解吗？——两套环境切流量，院内网两套生产环境成本高；我们用"按院灰度"达到类似效果，粒度更粗但成本匹配场景。

**雷点**：答成 K8s 滚动更新那套通用八股（场景是医院内网驻场部署）；说不出任何一个具体回滚机制——索引版本目录就是现成答案。

## §15.10 🟡 多家医院多租户，数据怎么隔离？

**口语答案**：先说一个行业前提：医疗数据合规要求患者数据不出院，所以我们的现状就是**物理隔离的多租户**——每家医院院内网独立部署一套实例、独立一套库，实施驻场维护。这是最强隔离：故障不传染、合规好过、单院数据量小；代价是版本升级要逐院推、运维面随租户数线性涨。如果业务演化成区域影像中心或集团 SaaS、要做集中式部署，选项分三层：库级隔离——每租户独立 schema 或实例，隔离强、适合大租户，成本最高；行级隔离——全表加 tenant_id，所有查询带租户谓词、复合索引最左列放租户，成本最低，风险是漏写谓词就串数据，必须在 DAO 层统一注入、禁止手写 SQL 谓词；中间件配套——Redis 键加租户前缀、RabbitMQ 按租户分 vhost 或路由键、OSS 按租户分 bucket 或前缀，我们的缓存键要升级成"版本+租户+查询哈希"。我的取舍：中小租户行级、大租户库级的混合最现实，纯行级撑到几十家、再往上必出事故。

**追问预演**：
- ↳ 行级隔离怎么防漏谓词？——DAO 层拦截统一注入、代码评审卡手写、再加一道自动化用例：构造两个租户同 ID 数据互相查不到。
- ↳ 行级隔离下索引怎么设计？——租户列放复合索引最左，否则跨租户扫描；代价是每索引都多一列的存储。
- ↳ 为什么现在不做集中式？——不是技术做不了，是合规和医院话语权决定的：数据不出院是底线，行业里集中式多租户只在区域影像中心这类政策项目里出现。

**雷点**：上来就吹"一个库加 tenant_id 全搞定"（漏谓词串数据是医疗场景的重大事故）；不知道"每院独立部署"本身就是多租户的一种答案，反而显得没想过现状。
